# Оставшиеся точки интеграции

После частичной интеграции этапа 1 backend вызывает отдельный сервис при сдаче, read-only сервисные маршруты и вердикт доступны в основной карточке. Ниже — оставшиеся ограничения; исторические формулировки таблицы требуют дальнейшей актуализации по этапам.

| Пробел | Где нужен / минимальное изменение основного проекта | Работа отдельного ИИ-сервиса без него |
| --- | --- | --- |
| Ротация сервисной идентичности и ограничение объёма снимка | Уже есть `GET /api/ai-service/snapshot` и фото только для чтения с общим токеном; нужна ротация токена и пагинация | `BackendDataSource` использует `BACKEND_SERVICE_TOKEN`; старый пользовательский `BACKEND_TOKEN` остаётся совместимым вариантом |
| `GET /api/orders` ограничен 5000 без cursor/total; подробности только по одному ID | `backend/app/main.py`: пагинация и/или пакетный read-only экспорт с событиями, фото-ID и версиями | При ровно 5000 строк `BackendDataSource` выдаёт `IncompleteHistory`, не публикует неполную аналитику; для демо доступны меньшие наборы |
| Нет API отдельных `material_writeoffs`, исторических `ai_assessments` и версий сдачи | `backend/app/main.py`, модель попыток: авторизованное чтение полной истории и её идентификаторов | Текущий snapshot получает лишь накопленный `completion.materials` и текущий `ai_review`; точный повторный расход и история вердиктов помечаются неизвестными |
| В создании наряда нет нормы материала по шифру и связи `time_norm_id` | Новые справочные связи и контракт после решения Q05 | Правила перерасхода и поиск аномалий используют только нормы синтетического набора; реальные данные без нормы получают `unknown` |
| Фото не имеют достоверного `captured_at` и ID попытки сдачи | Модель/контракт фото после решения Q04; отличать съёмку, загрузку и сдачу | Можно проверять только `created_at` загрузки и содержимое защищённого JPEG; свежесть съёмки не подтверждается |
| Время текущего назначения выводится из событий, нет полной истории назначений | Отдельная история и `assigned_at` согласно D09 | Используется доступное событие выдачи/изменения с явно отмеченной неопределённостью для старых записей |
| Нет истинных интервалов остановки, пауз и календаря бригад/смен | Модель и API после Q04/Q05 | Отчёт не называет сумму `downtime_minutes` фактическим простоем; зависимые показатели `unknown` |
| Нет отдельного Flutter-экрана полного ИИ-отчёта | Веб-карточка и пользовательский backend gateway уже дают JSON/PDF/XLSX с ролевой проверкой; Flutter пока читает только базовую карточку | Отдельный сервис не выдаёт служебный токен клиенту; Flutter может использовать `/api/ai/reports/orders/{id}` после реализации UI |
| Черновик ввода из текста/голоса не встроен в основной UI | Ассистент и подсказка шифра уже доступны через ролевой backend gateway; для черновика нужны отдельный gateway, экран подтверждения перед `POST /api/orders` и показ неизвестных полей во фронте/Flutter | `/ai/intake/text` и `/ai/intake/voice` отвечают отдельно, **ничего не создают**; service-token нельзя передавать браузеру |
| Нет решения о передаче производственного аудио в STT и подтверждённой точности на речи | Q01: согласовать обезличивание, хранение и провайдера; собрать аудио с согласиями и независимой разметкой | STT доступен только на синтетическом режиме при явных ключе/модели; без него `needs_transcript`, текстовый ввод остаётся локальным |
| Бонусные LLM/STT-запросы не поставлены в сохраняемую фоновую очередь | В самом `ai_service/` нужна версионированная очередь и polling API, согласованные по Q06; gateway должен повторять запросы безопасно | Ассистент ограничен 40 с и выполняется асинхронно внутри HTTP-запроса; ввод тоже асинхронный, но после перезапуска незавершённый запрос теряется |
| Нет общего outbox для всех ИИ-задач | Сдача уже создаёт сохраняемое `AIReviewJob` и worker вызывает `/ai/reviews/{id}/evaluate` после фиксации; для аналитики, ассистента и уведомлений нужен отдельный механизм | Проверка конкретной сдачи работает; остальные задачи запускаются по API сервиса |
| Нет возможности внешнему сервису создать внутреннее уведомление или реальный push | Отдельный авторизованный endpoint/outbox и FCM/APNs по решению Q06 | `LogNotifier` явно сообщает, что доставка не выполнена; Telegram работает только при токене и карте чатов, не как push приложения |
| Нет триггера еженедельной сводки и подтверждения выводов аналитики | Защищённое расписание/очередь после Q06, экран мастера с отметкой «проверено» | `/ai/analytics/weekly` считает сводку только по запросу; статистические связи остаются гипотезами |
| Нет безопасного зеркала прав для внешнего REST `/ai/...` | Backend gateway с серверной проверкой пользователя, роли и доступности наряда; не пересылать service-token в браузер | Сервисный Bearer `AI_SERVICE_TOKEN` защищает служебные маршруты. Новый `/ai/reviews/{id}/master-override` сверяет существование мастера и версию, но без gateway не удостоверяет, что вызывающий действительно этот мастер; не открывать маршрут пользователям напрямую |
| Отдельная PostgreSQL БД и SELECT-only пользователь ещё не выданы | DBA: создать БД `ai` и пользователя только с SELECT на нужные таблицы НарядAI; секреты вне Git | Локально ИИ-сервис хранит **только свои** таблицы в `ai_service/state/ai.db`; основной PostgreSQL не меняется |
| Публичный API не умеет импортировать прошлые даты, события, закрытия, фото и исходный номер | Отдельный контролируемый импорт/экспорт с историей и проверкой прав, только по явному решению | `make data` создаёт полноценный 90-дневный локальный снимок. `make seed-backend` по явному подтверждению через API создаёт только новые текущие наряды; не использовать его для исторических метрик |

Выбор поставщика push, правил доступа к производственным фото/текстам и часть расчётных норм остаются открытыми в `docs/decisions.md`. Сервис не считает эти предложения согласованными.
# Фото-проверка оборудования в основном интерфейсе

Отдельный ИИ-сервис теперь возвращает `equipment_check` в `/ai/photos/{id}/review`, но текущая модель `backend/app/ai_service_client.py::ServicePhotoReview` не содержит этого поля и Pydantic отбрасывает его при преобразовании ответа. Для показа численных доказательств в основной карточке достаточно добавить необязательное `equipment_check` в эту модель и соответствующий тип/блок UI; схема БД не меняется. До этого мастер видит текстовую причину «вероятно другое оборудование», а полный структурированный результат доступен через служебный маршрут отдельного сервиса.
