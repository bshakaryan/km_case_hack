# Отдельный ИИ-сервис НарядAI

**Состояние: модули из `feature/ai-integration` перенесены в `master`; это не производственная приёмка.** Backend и веб теперь имеют ограниченный авторизованный шлюз к сервису, но старая схема ИИ не восстановлена и финальное решение остаётся за мастером. Исторический аудит: [FINAL_REPORT.md](FINAL_REPORT.md); новые ограничения: [INTEGRATION_GAPS.md](INTEGRATION_GAPS.md).

## Что реализовано сейчас

- Отдельный FastAPI с `/ai/health`, защищённым `/ai/source/summary` и Swagger `/docs` на порту 8090.
- Интерфейс `DataSource` с `BackendDataSource` (только авторизованные GET к существующему API) и `SyntheticDataSource` (локальный JSON). Оба возвращают одинаковую Pydantic-модель `Snapshot`; фото читаются отдельным методом. Достигнутый лимит 5000 нарядов отвергается как неполная история.
- Собственная SQLite-БД по умолчанию в `ai_service/state/ai.db`, таблицы `ai_results`, `ai_notifications`, `ai_llm_cache`. Конфигурация не позволяет случайно открыть SQLite вне `ai_service/state/`; внешний PostgreSQL требует явного подтверждения отдельной БД. Эти таблицы не связаны с БД НарядAI.
- Интерфейс `Notifier` и `LogNotifier`, который **не утверждает, что доставил уведомление**.
- `ai_service/.env.example`, Dockerfile, отдельный `docker-compose.ai.yml` и интеграционный `docker-compose.integration.yml`. Секреты, состояние и большой локальный снимок игнорируются Git.
- Фиксированный генератор `data_gen/generate.py`: 719 нарядов за 90 дней, JSON/CSV, нормы материалов и локальные иллюстративные изображения; эталоны проверки, сроков, дублей фото, ввода, ассистента и аналитики. Подробности — [data_gen/README.md](data_gen/README.md) и [eval/cases/README.md](eval/cases/README.md).
- Контроль сроков `app/deadlines.py`: `tick(now)`, пороги 30/10/3 минут, повторы, руководитель, подбор свободной замены, ключи дедупликации в собственной БД. Telegram отправляет только при заданных токене/чатах; иначе `LogNotifier` явно не считает сообщение доставленным.
- Проверка сдачи `app/verification.py`: полнота, шифр, фото, расход по нормам, время и срок считаются кодом. `app/llm_client.py` асинхронно сравнивает смысл через OpenAI/Anthropic при `DEMO_MODE=false`, валидирует JSON, повторяет невалидный ответ один раз, кэширует и возвращается к правилам при ошибке. Задание проверки привязано к версии сдачи и хранится в `ai_results`.
- Отчёты `app/reports.py`: исполнитель, мастер, смена; PDF/XLSX. Рейтинг `app/rating.py`: расчёт по шести компонентам, приоритет оценки мастера, неизвестное исключается из нормировки весов.
- Фото `app/photos.py`: наличие, время **загрузки** относительно работ, точные и технические дубли по pHash+SSIM+ORB, проверка предыдущих фото с ограничением в 1000 записей. Кодовая проверка другого оборудования использует CPU-эмбеддинги MobileNetV2+ORB+SSIM до vision API; при уверенном несовпадении LLM не вызывается. Отсутствующие или повреждённые веса теперь останавливают запуск сервиса и дают ошибку `503` в `/ai/health`, а не тихо отключают vision. Неизвестная давность съёмки и низкая уверенность не превращаются в ложную оценку. Vision через API доступен только при явном включении на синтетике; оценку 1–5 выставляет код по качественной категории модели. Фотоанализ хранится отдельно от текстового вердикта.
- Публичный фото-эталон `eval/photos/`: 180 пар четырёх типов и 200 пар дублей; бенчмарк `python -m eval.photo_benchmark --mode pilot|full --model <vision-model>` считает покрытие, точность среди решённых, матрицы, стоимость и время. `needs_master_review` не ошибка. Изображения, модель и архив не входят в Git. Это **не** точность на реальном ремонте; подробности — в [DATA_SOURCES.md](eval/photos/DATA_SOURCES.md) и [metrics.md](reports/metrics.md).
- Аналитика `app/analytics.py`: топ оборудования/участков, повторный дефект за 7 дней, поломка после ППР, сменная связь с тестом Фишера, многократный перерасход по IsolationForest+MAD, рост внеплановых нарядов. Выводы содержат рассчитанные числа, ссылки на наряды и рекомендацию; причинность не утверждается.
- Ассистент `app/assistant.py` вызывает только read-only инструменты и считает числа из снимка; `app/intake.py` готовит черновик из текста/голоса, но не создаёт наряд.
- `make eval` запускает отдельный офлайн-прогон по эталонам, записывает [metrics.md](reports/metrics.md) и [metrics.json](reports/metrics.json). Платные LLM-вызовы по умолчанию отключены.

В этой фазе **нет** экспертной оценки vision-accuracy, автоматической проверки после сдачи и автоматической еженедельной рассылки. Backend и веб вызывают рекомендации по явному запросу; Flutter пока нет. В режиме реального backend внешние LLM-вызовы отключены до решения Q01, даже если есть ключ. Таймер основного backend уже отправляет уведомления; второй таймер ИИ в интеграционном Compose выключен, чтобы избежать дублей. Наличие LLM-ключа не означает отправку данных: по умолчанию `DEMO_MODE=true`.

## Совместный запуск с основным приложением

Задайте одинаковый длинный случайный `AI_SERVICE_TOKEN` в корневом `.env`. Выполните из корня репозитория:

```bash
docker compose -f docker-compose.yml -f ai_service/docker-compose.integration.yml up -d --build
```

AI API слушает `127.0.0.1:8090`, Swagger — `http://127.0.0.1:8090/docs`; веб — `http://127.0.0.1:8080`. Проверка соединения: войдите мастером, откройте веб-аналитику или карточку сданного наряда. Сервисные `/ai/*` требуют токен; веб получает его только через backend. При отсутствии весов MobileNetV2 сервис явно не стартует. Отсутствие норм материалов в основной БД означает `unknown`, а не отсутствие перерасхода.

При использовании изображений с подтверждённой [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) указывайте автора, источник и факт преобразования. В наборе `semi_synthetic` применён `cv2.inpaint`, `real_same_image` — повтор исходного фото; эти метки не отражают настоящий ремонт.

Для презентации используйте только `python -m eval.photos.select_demo` и папку `eval/photos/demo_safe/` с манифестом источников. Старую `eval/photos/demo/` не показывайте: она содержит изображения `999-krc03` с непроверенной лицензией. Открытый бенчмарк включает их только для локальной оценки, не для распространения.

Повторить фото-бенчмарк из `ai_service/`: `make setup` скачает зависимости и проверенные веса; на Windows без `make` выполните `python -m pip install -r requirements.txt`, затем `python -m eval.fetch_equipment_model`. Задайте `LLM_MODEL_VISION` и ключ в `ai_service/.env`, выполните `python -m eval.photo_benchmark --mode pilot --tag strong --input-price-per-million 2 --output-price-per-million 8` и только после проверки пилота замените `pilot` на `full`. Числа цены в примере относятся к `gpt-4.1` на дату прогона; для другой модели обновите их по официальному тарифу. Для сравнения используйте `--tag mini --model gpt-4.1-mini` и его тариф. `python -m eval.run` объединит сравнение в `reports/metrics.md`. Изображения и локальная модель в Git не входят; без них тесты фото-эталона пропускают соответствующий реальный прогон.

## Запуск

Требуется Python 3.11+; Docker-образ использует 3.12. Из каталога `ai_service/`:

```bash
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8090
```

В Windows используйте `.venv\Scripts\python.exe`. В `.env` задайте случайный `AI_SERVICE_TOKEN`; для чтения живого backend также `DATA_SOURCE=backend`, `BACKEND_URL` и вручную полученный `BACKEND_TOKEN`. Токен backend имеет срок 12 часов. В режиме `synthetic` сначала создайте `data/snapshot.json` командой ниже; без него маршруты снимка вернут 503. Health и Swagger доступны без набора данных. Для непрерывной проверки сроков установите `DEADLINE_SCHEDULER_ENABLED=true`; по умолчанию фоновый опрос отключён, чтобы случайно не опрашивать весь backend каждую минуту. Ручной `POST /ai/deadlines/tick` работает без планировщика.

Для LLM задайте `DEMO_MODE=false`, `LLM_PROVIDER=openai|anthropic`, `LLM_MODEL_FAST` и соответствующий API-ключ в `ai_service/.env`; для фото также `LLM_MODEL_VISION`. Никакая модель не захардкожена. **Любой внешний LLM-вызов текста или фото заблокирован при `DATA_SOURCE=backend`**, даже при ключе: Q01 не решён. Без ключа или при ошибке провайдера фото получает `needs_master_review` и `score:null`, а текстовый вердикт остаётся доступен по правилам; реальные производственные данные во внешний API без решения Q01 не отправляйте. Для Telegram укажите `TELEGRAM_BOT_TOKEN` и JSON-карту `TELEGRAM_CHATS`, например `{"E-02":"<chat_id>","M-01":"<chat_id>"}`. Без карты доставка будет только в лог-заглушку.

## Фаза 2: данные и эталоны

Из `ai_service/`:

```bash
make data
# Windows без make: python -m data_gen.generate
```

Генератор **не** пишет в основной backend. Он создаёт `data/snapshot.json`, `data/material_norms.json`, `data/csv/*.csv`, `data/photos/orders/*.png` и `eval/cases/*.json`. Seed `20261007`; JSON/CSV воспроизводятся побайтово. Изображения процедурные и не проверяют качество ремонта; для vision-accuracy нужны 15–20 реальных размеченных пар «до/после» с независимой оценкой специалистов.

Необязательный **явный** импорт в локальный backend через публичный API:

```bash
BACKEND_TOKEN=<admin-token> SEED_WORKER_PIN=<4-12-digit-pin> make seed-backend ARGS="--base-url http://127.0.0.1:8000 --confirm IMPORT_SYNTHETIC_ORDERS"
# Windows без make: python -m data_gen.seed_backend --base-url http://127.0.0.1:8000 --confirm IMPORT_SYNTHETIC_ORDERS
```

Для Windows переменные задайте в среде или `ai_service/.env`; не добавляйте токен/PIN в Git. Команда не запускается при `make data`/тестах, принимает только loopback HTTP, требует admin-токен и подтверждение. Она создаёт справочники и **новые текущие** наряды с будущим сроком, пропуская повторные заголовки. Публичный API не позволяет импортировать исходные даты, события, фото и закрытия; результат не эквивалентен 90-дневному снимку и не подходит для оценки исторической аналитики. Не запускайте на рабочем backend.

## Фаза 4: метрики

Из `ai_service/` после `make data` выполните `make eval` или в Windows `python -m eval.run`. Отчёты появятся в `reports/`. По текущей синтетике: контроль сроков — 472/472 ожидаемых событий, precision/recall 1,0/1,0, дублей 0; правила проверки — accuracy и macro-F1 1,0 на 120 карточках; E-04 и E-11 в нижней трети рейтинга. Эталоны созданы тем же генератором по учебной политике, поэтому эти числа **не доказывают точность на реальных нарядах**. Отчёты содержат матрицу ошибок, recall флагов, чувствительность рейтинга к весам и неизмеренные модули. Не выдумываются ошибки там, где их в данном наборе нет.

LLM-прогон на синтетике — только по явной команде `python -m eval.run --with-llm`, при заполненных `LLM_PROVIDER`, `LLM_MODEL_FAST` и ключе в `ai_service/.env`. Он может стоить денег. Для оценки стоимости можно передать `--input-price-per-million` и `--output-price-per-million`; без цен стоимость остаётся `unknown`. Не используйте эту команду для производственных данных без решения Q01. Vision, ввод и ассистент без независимых эталонов остаются `unknown`, а не фиктивным нулём.

## Фаза 5: фото и история

`POST /ai/photos/{id}/review` ставит версионированное фоновое задание; `GET /ai/photos/{id}/review` возвращает результат или статус. Результат появляется и в отчёте мастера, но не переписывает текстовый вердикт. Фото после сравнивается с фото до и предыдущими фото через SHA-256, pHash, SSIM и ORB; после события доработки прежнее фото «после» не считается новым подтверждением. `make setup` скачивает модель в игнорируемый `models/mobilenetv2.onnx`; Dockerfile скачивает и сверяет SHA-256 при сборке. Веса лежат вне тома `state`, поэтому монтирование БД их не скрывает. Можно указать другой путь через `AI_IMAGE_EMBEDDING_MODEL`, но файл должен иметь закреплённый SHA-256. Порог косинусного сходства `0.586` выбран на половине публичных пар с нулём ложных отклонений same-image и проверен на другой половине; это **не** доказательство идентичности физического оборудования на производстве. Проверяется только серверное `created_at` загрузки, а не время съёмки: EXIF и время телефона не доказывают свежесть. При дубликате, отсутствии фото, неполной истории или недоступной/неуверенной vision-модели результат требует мастера; **даже уверенная визуальная оценка остаётся рекомендацией с обязательной проверкой времени съёмки человеком**. Vision-провайдер получает уменьшенный JPEG без исходных метаданных и обезличенное описание **только синтетического** наряда.

`GET /ai/analytics?start=...&end=...&area_id=...` возвращает факты и рекомендации по периоду, а также описательные разрезы по смене, часу, бригаде и исполнителю с тестом Фишера и поправкой Бонферрони; `GET /ai/analytics/weekly?end=...` считает последние 7 дней по запросу, но пока не рассылает сводку автоматически. `reported_downtime_minutes` остаётся введённой величиной, а не подтверждённым интервалом простоя. Материальные аномалии на реальном backend дают `unknown`, если в источнике нет норм расхода. В текущей синтетике `make eval` даёт precision/recall технических дублей 1,0/1,0 на 48 процедурных парах, находит 6/6 заложенных сигналов и 0/3 приманок, но также формирует **2 дополнительные неразмеченные гипотезы** о поломках после ППР. Их не следует выдавать за доказанные причины; см. [metrics.md](reports/metrics.md).

## Фаза 6: ассистент и ввод

`POST /ai/assistant/ask` отвечает на четыре класса вопросов через read-only инструменты: свободные исполнители, просроченные наряды, число нарядов и внеплановых проблем участка. Максимум один инструмент на ответ (предел — шесть), таймаут 40 с. Детерминированный выбор работает без ключа; для неоднозначного вопроса на **синтетике** доступен структурированный выбор инструмента через LLM, но число и итоговый ответ всегда вычисляются кодом. Неизвестный вопрос не превращается в действие: `needs_clarification`. Время в `now` — время расчёта по текущему снимку, не реконструкция исторического состояния.

`POST /ai/intake/text` возвращает **черновик**, не создаёт наряд. Оборудование, участок и шифр ограничены существующими ID снимка; связь шифра с нормативом определяется по совпадению кода в имени норматива, а срок «за/через N ч», «в течение N ч/мин» и «до HH:MM» переводит код. При конфликте участка или неизвестном поле нужна проверка мастером. `original_phrase` сохраняется. Неоднозначный текст может обрабатываться структурированным LLM-ответом только при `DATA_SOURCE=synthetic`, `DEMO_MODE=false` и настроенном ключе; перед вызовом ФИО/логины справочника и телефоны удаляются. В живом backend внешние LLM-вызовы текста заблокированы до решения Q01.

`POST /ai/intake/voice` принимает файл до 10 МБ. STT работает через `OpenAITranscriber` за интерфейсом `Transcriber` при тех же синтетических условиях и `STT_MODEL`; без него возвращается `needs_transcript`, а не придуманная расшифровка. Аудио невозможно гарантированно обезличить до STT: не отправляйте реальные записи, пока Q01 не решён. Для Anthropic STT-адаптера нет. Метрики на 40 шаблонных текстовых фразах и 25 шаблонных вопросах — по 1,0 для реализованных полей и выбора/чисел; это **не** точность реального голоса или свободных вопросов.

Для Docker сначала запустите основной `docker compose up -d` из корня, чтобы существовала сеть `naryad-ai_default`. Затем из `ai_service/`:

```bash
docker compose -f docker-compose.ai.yml up -d --build
```

Адрес: `http://127.0.0.1:8090/docs` (или `AI_PORT`). Контейнер подключён к сети основного Compose **только для API-чтения**; его БД — отдельный том `ai_state`. В Docker `BACKEND_URL` по умолчанию `http://backend:8000`; при необходимости задайте `AI_DOCKER_BACKEND_URL`. Существующий backend не запускает этот сервис автоматически.

## REST и безопасность

| Маршрут | Назначение |
| --- | --- |
| `GET /ai/health` | Проверить собственную БД и режим источника; без данных НарядAI |
| `GET /ai/source/summary` | Количество нарядов/сотрудников/оборудования/участков без ФИО; требует `Authorization: Bearer <AI_SERVICE_TOKEN>` |
| `POST /ai/deadlines/tick` | Явный проход монитора, тело `{now?: ISO-время}`; возвращает созданные уведомления и факт доставки |
| `POST /ai/reviews/{id}`, `GET /ai/reviews/{id}` | Поставить версионированную проверку в фон; затем прочитать результат или статус задания |
| `POST /ai/reviews/{id}/master-override` | Сохранить решение мастера рядом с рекомендацией; требует `{source_version,master_id,verdict,score,reason}` и актуальной версии сдачи |
| `GET /ai/reports/orders/{id}` | Отчёт `audience=worker|master`, `format=json|pdf|xlsx` |
| `GET /ai/reports/shift`, `GET /ai/ratings` | Период `start,end` в ISO-времени; отчёт смены поддерживает `format=json|pdf|xlsx` |
| `POST/GET /ai/photos/{id}/review` | Фоновый анализ фото с версией сдачи; отдельная рекомендация, не окончательная приёмка |
| `GET /ai/analytics`, `GET /ai/analytics/weekly` | Выводы по периоду и сводка последних семи дней по запросу |
| `POST /ai/assistant/ask` | `{question,now?}` → read-only ответ с `tool`, `tool_calls`, `facts`; максимум 40 с |
| `POST /ai/intake/text` | `{phrase,now?}` → черновик с допустимыми ID, исходной фразой и флагом ручной проверки |
| `POST /ai/intake/voice` | Multipart `file`, необязательный `now` → транскрипция и черновик либо `needs_transcript` |
| `GET /docs`, `GET /openapi.json` | Swagger/OpenAPI отдельного сервиса |

Если `AI_SERVICE_TOKEN` не настроен, защищённый маршрут возвращает 503; неверный токен — 401. `BACKEND_TOKEN` не выводится в HTTP. Публичная авторизация пользователей НарядAI через этот сервис **не реализована**: `master_id` в override проверяется по справочнику, но владение этим ID клиентом не доказывается. Маршруты предназначены только для доверенного backend/gateway с серверной проверкой роли; не открывайте их браузеру/Интернету без gateway/TLS. `BackendDataSource` делает только GET, а `SyntheticDataSource` не обращается к backend.

## Формат снимка

`SyntheticDataSource` ожидает JSON с массивами `areas,brigades,employees,equipment,fault_codes,materials,time_norms,orders`. Поля наряда соответствуют `GET /api/orders/{id}`, включая `events,photos,completion,ai_review`. Для локального фото допускается относительный `photos[].path` внутри каталога набора; для backend используется только защищённый `/api/photos/{id}`. Шифр и норматив связаны в синтетике по ID; в реальном backend связи нет. Нормы материалов лежат отдельно в `data/material_norms.json`.

В фазе 3 снимок также содержит необязательный `material_norms`; у `BackendDataSource` он пустой, потому что в основном API нормы материала не публикуются. Отсутствие нормы даёт `unknown`, а не нулевой расход или штраф.

## Правила вердикта

Числа и вердикт считает `app/verification.py`; LLM только сравнивает смысл текста и формулирует пояснения. Проверяются ID ссылок на материалы/события и отсутствие цифровых утверждений в пояснениях модели; недостоверный ответ не может сам принять наряд. Предлагаемая оценка — 1–5, `unknown` для ручной проверки.

| Условие, в порядке приоритета | Рекомендация |
| --- | --- |
| Нет описания работ, действующего шифра или обязательного фото «после» внеплановой работы | `needs_rework`, 1–2 балла |
| Ответ LLM с несуществующей ссылкой или неподтверждённым числом | `needs_master_review`, оценка `unknown` |
| Шифр явно противоречит описанию или работы явно не соответствуют проблеме | `needs_rework`, 1–2 балла |
| Смысл работ неоднозначен, уверенность низкая или время неизвестно | `needs_master_review`, оценка `unknown` |
| Расход материала >1,5 нормы, нетипичный материал, неуказанный ожидаемый материал, время выше нормы или просрочка | `accepted_with_remarks`, 3–4 балла |
| Остальные случаи при подтверждённом соответствии | `accepted`, 5 баллов |

Это **учебная политика отдельного сервиса**, не утверждённое правило основного backend: Q02/Q03 ещё открыты, а `complete` без фото там возвращает 422. Мастер сохраняет финальную приёмку. Фотоанализ 6.3 существует отдельно; его результат не переписывает текстовый вердикт автоматически. Наличие фото не доказывает свежесть или устранение дефекта.

## Рейтинг

Демонстрационные веса в `RATING_WEIGHTS`: качество 30%, своевременность 25%, отсутствие возвратов 15%, отсутствие повторного ремонта ≤7 дней 15%, объём × сложность 10%, отказы без причины 5%. Качество и срок имеют наибольший вес, чтобы количество не компенсировало плохой ремонт; остальные компоненты дают прозрачные предупреждения. Сложность пока приближена известными нормо-часами, плановый объём — `max(8, 4 × число дней периода)` нормо-часов. Неизвестная компонента исключается из знаменателя, не превращается в ноль. Приоритет оценки: override мастера → оценка закрытия в backend → прежняя ИИ-оценка → оценка правил нового сервиса. Веса, сложность, уважительные причины и бригадный вклад требуют решения Q05; это не производственный рейтинг.

Отчёт смены считает выдачу по `created_at`, выполнение по `completed_at`, просрочку по сроку внутри периода и отклонение/доработку по времени события. `reported_downtime_minutes` — сумма введённых в выданных за период карточках величин, **не** подтверждённый фактический простой: нет интервалов остановки/запуска и объединения пересечений по Q04.
