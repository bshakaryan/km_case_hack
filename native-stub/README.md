# Историческая TypeScript-заготовка мобильного контракта

Актуализировано **5 октября 2026 года**. Целевой мобильный клиент НарядAI создаётся на **Flutter: сначала Android, затем iOS**. Этот каталог сохранён как справочный пример существующего HTTP-контракта и проверяемая TypeScript-заготовка. Он **не является Flutter-проектом, мобильным приложением или базой для нового React Native клиента**.

Ранее здесь предполагался будущий React Native клиент. Это направление заменено решением о Flutter. В каталоге нет Android/iOS-сборки, экранов, мобильного runtime, фоновой синхронизации или настоящей доставки push. Первый Flutter-клиент реализован в [mobile/](../mobile/README.md); этот TS-каталог не используется как его runtime. Временная проверка действий работника доступна через веб-панель под логином worker.

Актуальные источники для команды: [решения](../docs/decisions.md), [полные требования](../docs/requirements.md), [план](../docs/implementation-plan.md), [контракт API](../docs/api-contract.md). При расхождении типов этого каталога с сервером и утверждённым контрактом сначала обновляются контракт и его проверки; старый пример не определяет поведение Flutter.

## Что находится в каталоге

- [src/api.ts](src/api.ts) — HTTP-клиент к текущему FastAPI: авторизация, наряды, статусы, завершение, уведомления, фото. При импорте запросы автоматически не отправляются.
- [src/types.ts](src/types.ts) — исторические TypeScript-типы контракта; их проверка не заменяет согласование схем Dart-клиента.
- [src/native.ts](src/native.ts) — явно не реализованные камера и push, а также непостоянная очередь. Камера сообщает об отсутствии реализации; push возвращает registered: false. Очередь живёт только в памяти и сама ничего не отправляет.
- [src/example.ts](src/example.ts) — пример HTTP-загрузки данных работника с переданными адресом API и учётными данными; это не экран приложения.

## Что требуется Flutter-клиенту

Нужны ролевые экраны мастера и исполнителя, безопасное хранение сессии, камера/галерея и сжатие до передачи, постоянное хранилище команд и фотографий, восстановление после перезапуска и синхронизация с идемпотентным API. Конфликты с переназначением и закрытием на другом устройстве должны обрабатываться явно. Настоящие push требуют регистрации устройств, серверной доставки и проверки звука/аварийного ответа на физических телефонах. Провайдер и детали интеграции определяются техническим решением, а не этой заглушкой.

Android проверяется первым; затем iOS, включая особенности камеры, уведомлений и работы после потери сети. Для iOS нужны соответствующая среда сборки, подпись и учётные данные. До появления проверенных сборок документация не должна заявлять готовое приложение или измеренную мобильную производительность.

Для проверки исторического HTTP-клиента адрес API на физическом устройстве должен быть доступен по сети, например `http://<IP-компьютера>:8080`; `localhost` на телефоне означает сам телефон. Текущий Compose привязан к loopback, поэтому пример адреса сам по себе не открывает доступ с устройства. При внешнем развёртывании нужен HTTPS. В этот TypeScript-клиент передают базовый адрес без `/api` — префикс добавляется самим клиентом.

Проверка типов заготовки установленным компилятором веб-панели из корня проекта:

```bash
./frontend/node_modules/.bin/tsc -p native-stub/tsconfig.json
```

Это проверка только TypeScript-файлов. Она не проверяет Flutter, APK, iOS, push или офлайн.
