# НарядAI · Костанайские минералы

Обновлено 8 октября 2026 года.

НарядAI — система управления ремонтными нарядами: выдача задания, работа исполнителя, контроль сроков и простоев, приемка мастером, аналитика и справочники. **Цель проекта — полный кейс**, включая Flutter-приложение, реальные ИИ-проверки, push и офлайн. Сейчас есть обновлённая React-панель в едином стиле с первым Flutter-клиентом, сервер и БД. Онлайн-сценарии используют существующий API; ИИ пока остаётся заглушкой. Это описание текущей готовности, а не ограничение дальнейшего объёма.

**Команде начинать с [docs/README.md](docs/README.md):** [решения и открытые вопросы](docs/decisions.md), [требования](docs/requirements.md), [архитектура](docs/architecture.md), [API](docs/api-contract.md), [план реализации](docs/implementation-plan.md). Старый [чек-лист](docs/case-checklist.md) сохранён как исторический аудит; его прежний объём с заглушками заменён текущими решениями.

Стек существующей реализации: **React + TypeScript + Vite**, **Python + FastAPI + SQLAlchemy**, **PostgreSQL 17**. Мобильный клиент в `mobile/` — **Flutter: Android, затем iOS**; веб-панель сохраняется. Веб-панель работает на русском языке. Даты показываются в часовом поясе **Asia/Almaty**; сервер хранит время в UTC. Все работники и производственные записи в начальном наборе вымышлены.

## Быстрый запуск с PostgreSQL

Нужны Docker Engine/Desktop и Docker Compose v2. Из корня проекта:

```bash
docker compose up --build -d
```

- Веб-панель: [http://localhost:8080](http://localhost:8080).
- Документация API: [http://localhost:8000/docs](http://localhost:8000/docs).
- Проверка сервера: [http://localhost:8000/api/health](http://localhost:8000/api/health).

Первый запуск скачивает образы, собирает приложения, создает схему и демонстрационные данные. Сначала запускается PostgreSQL; веб-панель стартует после успешной проверки сервера. Состояние видно через `docker compose ps`, журналы — `docker compose logs -f --tail=100`.

Параметры по умолчанию предназначены для локальной демонстрации. При необходимости скопируйте `.env.example` в `.env` и измените порты, имя базы и пароль перед первым запуском. Значения `POSTGRES_*` определяют подключение контейнера API; отдельный `DATABASE_URL` из `.env` не переопределяет их. Для пароля с символами `@`, `:`, `/` нужно отдельно адаптировать URL подключения либо использовать длинный случайный пароль из букв и цифр.

База и фотографии хранятся в томе `postgres_data`; обычный `docker compose down` сохраняет данные. Изображения после проверки и сжатия записываются в БД, отдельный каталог uploads не нужен. Повторный старт не пересоздает существующие демонстрационные данные. `docker compose down -v` **удаляет всю базу и фотографии**; выполняйте эту команду только для намеренного сброса демо.

## Учетные записи

Общий демонстрационный PIN — **1234**.

| Логин | Роль | Доступ |
| --- | --- | --- |
| `master`, `master2` | Мастер | Создание и изменение нарядов, назначение, приемка, возврат на доработку |
| `worker`, `worker2` … `worker15` | Работник | Свои наряды, прием/очередь/отказ, выполнение, фотографии и отчет |
| `manager` | Руководитель | Просмотр производства, аналитика и выгрузки |
| `admin` | Администратор | Полный доступ и изменение справочников |

Права проверяет сервер на каждом действии. Вход возвращает случайный токен сессии; сервер хранит его хэш в БД. PIN используется только для упрощенного демонстрационного входа.

## Что можно показать

1. Войти как `master`: просмотреть сменные показатели, производственную доску и загрузку работников; применить фильтры по участку, оборудованию, исполнителю, приоритету и статусу.
2. Создать наряд с оборудованием, исполнителем или бригадой, сроком и приоритетом. Для проверки роли работника назначить его пользователю `worker`.
3. Войти как `worker`, принять наряд и начать работу. При необходимости поставить его в очередь, приостановить с причиной и возобновить.
4. Для внеплановой работы добавить фотографию «После»: без нее сервер не позволит завершить наряд. Заполнить выполненные работы, дефект и фактические материалы.
5. Завершить наряд: появятся результат **заглушки ИИ** и запись в истории. ИИ не закрывает наряд автоматически. Под `master` принять результат с оценкой или вернуть на доработку с причиной.
6. Открыть аналитику: сравнить плановые и внеплановые работы, простои оборудования, расход материалов и рейтинг работников. Экспортировать отфильтрованные данные. Под `admin` проверить справочники.
7. Открыть два окна браузера с разными учетными записями: изменения приходят по WebSocket, дополнительно каждые 5 секунд работает опрос. Сейчас он не отключается при активном WebSocket. Для разных пользователей удобны отдельные профили браузера или обычное и приватное окно.

История хранит изменения статусов и параметров, авторов, время и причины. Просрочка вычисляется отдельно от статуса. Фоновый монитор формирует уведомления о приближении срока, просрочке и непринятых заданиях; повтор одной проверки подавляется по ключу дедупликации. Изменение срока или назначения может создать новое уведомление. Сообщения о новых действиях и статусах сохраняются отдельно.

Рейтинг исполнителя по закрытым нарядам: **60% — средняя оценка мастера, 30% — выполнение в срок, 10% — отсутствие доработок**, итог в шкале 0–100. Время приемки мастером не ухудшает своевременность работника: со сроком сравнивается завершение работ. Принципы расчёта и ограничения полного рейтинга приведены в [docs/architecture.md](docs/architecture.md).

Начальное заполнение содержит 540 исторических и 16 текущих нарядов примерно за 89 дней, 4 участка, 25 единиц оборудования, 2 мастеров, 15 работников, 3 бригады, 20 кодов дефектов и 40 материалов. В истории заложены повторные отказы конвейеров, проблемы после обслуживания и повышенный расход материалов. Полные три месяца, согласованную историю и демонстрационные фотографии ещё нужно подготовить по плану.

## Локальная разработка

Рекомендуется Python **3.12**, Node.js **24** и pnpm **11.25.0**. PostgreSQL используется в Compose; для быстрой локальной проверки поддерживается SQLite.

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
npm install --global pnpm@11.25.0
cd frontend
pnpm install --frozen-lockfile
cd ..
./scripts/run-local.sh
```

Локальная панель: [http://localhost:5173](http://localhost:5173). Скрипт запускает API на порту 8000 и Vite на 5173; `Ctrl+C` завершает оба процесса. Он использует базу `data/naryad.db`. Существующую виртуальную среду можно указать через `PYTHON_BIN=/absolute/path/to/python ./scripts/run-local.sh`. Скрипт не читает `.env` автоматически: передавайте переменные окружения явно или экспортируйте их в оболочке.

Для разработки с внешним PostgreSQL:

```bash
DATABASE_URL='postgresql+psycopg://user:password@localhost:5432/naryad_ai' ./scripts/run-local.sh
```

Сервисы можно запускать раздельно:

```bash
# Терминал 1, каталог backend/
../.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

# Терминал 2, каталог frontend/
pnpm dev
```

Vite и nginx проксируют `/api` и WebSocket к FastAPI; адрес API не зашит в браузерный bundle. Основной адрес WebSocket — `/api/ws?token=...`; `/ws` оставлен совместимым псевдонимом.

## Схема и миграции

При старте API обновляет схему через Alembic с проверкой совместимости до и после миграций. `0001_initial` теперь фиксирует самостоятельную исходную схему, `0002_client_commands` — результаты команд, `0003_assignment_time` — время текущего назначения. Для отдельного запуска обновления с тем же подключением:

```bash
docker compose exec backend alembic upgrade head
```

Локально команду выполняют из `backend/` с тем же `DATABASE_URL`, что использует сервер; обычный старт API использует тот же путь обновления. Пустая БД и распознанная полная старая схема обновляются без слепого `stamp`; неизвестная ревизия, неполная или изменённая схема останавливает запуск. Проверяются таблицы, столбцы, ограничения и индексы; SQLite также проверяется на нарушенные внешние ключи. `create_all()` рабочих моделей больше не выполняется при старте. Доказанные проверки конкретной БД и ограничения PostgreSQL — в [verification](docs/verification.md). Откат исходной миграции удаляет таблицы и предназначен только для disposable-среды.

Этот путь требует подключения к БД для проверки её состояния: автономная генерация SQL через `alembic upgrade head --sql` не поддерживается. Проверку исторического SQL из старого журнала испытаний нельзя переносить на новый механизм обновления.

`assigned_at` хранит время текущего назначения отдельно от `created_at`; переназначение, в том числе тому же исполнителю, начинает новый отсчёт непринятия 3/10 минут. При обновлении старых записей используется достоверное последнее событие назначения, а при недостаточной истории — время создания. Это консервативное заполнение, не восстановление полной истории назначений.

## Push-уведомления (FCM, Android)

Push доставляет Firebase Cloud Messaging через HTTP v1 API по решению [D20](docs/decisions.md): Android первым, iOS/APNs пока не подключены. Конфигурация Android-клиента `mobile/android/app/google-services.json` закоммичена и отслеживается Git: проект `km-case-hack` (номер `716637680468`), пакет `kz.km.naryad_ai`. Это публичная клиентская конфигурация — идентификаторы проекта и приложения плюс Android API-ключ, без серверного секрета. Файл заменяем: чтобы переключить Firebase-проект, сгенерируйте его заново для `applicationId kz.km.naryad_ai` и одновременно обновите серверный ключ сервисного аккаунта и `FIREBASE_PROJECT_ID`.

Сервисному аккаунту нужен отдельный секретный JSON, которого в репозитории нет:

1. В Firebase Console: **Project settings → Service accounts → Generate new private key** (нужны права на редактирование проекта).
2. Положите файл в `backend/secrets/` (для проекта уже лежит `km-case-hack-firebase-adminsdk-fbsvc-43f1ce1b97.json`). Каталог `backend/secrets/*` (кроме `.gitkeep`) и шаблон `*service-account*.json` исключены из Git через `.gitignore`; ключ нельзя коммитить, встраивать в образ и показывать в журналах.
3. Передайте ключ серверу одним из двух каналов:
   - `FIREBASE_CREDENTIALS_JSON` — JSON сервисного аккаунта целиком, имеет приоритет над путём. Значение многострочное, поэтому удобнее всего экспортировать его в оболочке перед запуском; для Docker Compose это основной канал.
   - `FIREBASE_CREDENTIALS` — путь к файлу ключа, например `secrets/firebase-service-account.json` при запуске из `backend/`.

Передайте `FIREBASE_CREDENTIALS` или `FIREBASE_CREDENTIALS_JSON` явно и установите `PUSH_ENABLED=true`. По умолчанию отправка выключена; файл из каталога секретов автоматически не выбирается. Скрипт по-прежнему не читает `.env` автоматически — остальные переменные экспортируйте в оболочке.

| Переменная сервера | Назначение | По умолчанию |
| --- | --- | --- |
| `FIREBASE_CREDENTIALS_JSON` | Inline JSON сервисного аккаунта (приоритет) | не задана |
| `FIREBASE_CREDENTIALS` | Путь к JSON сервисного аккаунта | не задана |
| `FIREBASE_PROJECT_ID` | Firebase-проект | `km-case-hack` |
| `PUSH_ENABLED` | Явное включение реальной отправки | `false` |
| `PUSH_DISPATCH_SECONDS` | Пауза цикла диспетчера push | `3` |
| `PUSH_MAX_ATTEMPTS` | Максимум попыток одного задания | `8` |

Если обе переменные учётных данных не заданы (или путь не существует), сервер работает как раньше: `GET /api/integrations` отдаёт для `native` режим `stub/demo`, отправки на устройство нет. При настроенном push там же `native: {mode:"fcm", status:"active"}`. Серверу нужен исходящий HTTPS-доступ к `oauth2.googleapis.com` (получение токена доступа) и `fcm.googleapis.com` (отправка сообщений).

`psycopg[binary]` в `backend/requirements.txt` обновлён до `3.3.6` для установки на Python 3.14; PostgreSQL нужен только полному запуску/Compose, не тестам на SQLite и не FCM-смоуку.

Серверная сторона, команды смоук-прогона и границы проверки — [docs/verification.md](docs/verification.md). Доставка на физическом устройстве и push на iOS ещё не принимались: нужны телефон и отдельная приёмка.

## Проверка

```bash
# Серверные тесты
cd backend
../.venv/bin/python -m pytest -q
cd ..

# Проверка типов и production-сборка веб-панели
cd frontend
pnpm test
pnpm exec tsc --noEmit
pnpm run build
cd ..

# Проверка типов нативного контракта
./frontend/node_modules/.bin/tsc -p native-stub/tsconfig.json

# Сквозная проверка HTTP API при работающем сервере
python3 scripts/smoke_api.py
```

`Makefile` содержит сокращения `make up`, `make down`, `make logs`, `make local`, `make build`, `make test`. Сквозная проверка создает отдельные тестовые наряды в текущей базе: запускайте ее в демонстрационной среде.

`pnpm test` использует Node.js 24 и изолированные проверки API-клиента/выборок (`frontend/tests/`). Он не заменяет браузерный сценарий, испытание камеры или реального переподключения сети. Результаты конкретной версии и окружение фиксируются в [docs/verification.md](docs/verification.md).

## Текущая готовность и ограничения

**Обновлённый веб-клиент.** Общая с Flutter светлая производственная тема, главные задачи мастера и исполнителя, контекстная выдача с поштучной отправкой до пяти фото, сравнение задания/отчёта/снимков при приёмке. На компьютере сохранены канбан и таблицы, на узком экране журнал использует вертикальные списки. Есть переподключение WebSocket с задержками 1/2/4/8/15 секунд, непрерывный опрос раз в 5 секунд с объединением запросов, защита от ответов прежней сессии и обновление открытой аналитики. [Решения и сценарии](docs/web-ux.md). Список ограничен 5000 записями с предупреждением; это не серверная пагинация. Интерфейсный пакет D16 не менял HTTP/БД; последующие серверные изменения описаны отдельно. Учёт переходящих работ и фактического простоя ещё требует исправления модели и метрик.

**ИИ — заглушка.** Ответы проверки качества и аналитические подсказки создаются детерминированной логикой с `is_stub=true`. Нейросеть, компьютерное зрение, LLM/RAG, распознавание дефектов по фото и внешние ИИ API не подключены. Фотографии сохраняются и доступны уполномоченным пользователям, но не анализируются моделью. Окончательное решение принимает мастер.

**Первый мобильный клиент — Flutter в `mobile/`.** Вход, рабочие места мастера и исполнителя, выдача, переходы, фото/материалы, сдача/приёмка, уведомления, push для Android через FCM и базовые отчёты. На Android добавлены постоянные снимки ранее полученных данных, кэш просмотренных фото и очередь команд/медиа с повтором по серверному ключу; локально сохранённая команда ещё не подтверждена сервером, конфликты показываются отдельно, несохранённый ввод формы не является постоянным черновиком. [Запуск и ограничения](mobile/README.md), [UX/UI](docs/mobile-ux.md), [фактические проверки и их границы](docs/verification.md). Доставка push на физическом устройстве не подтверждена, iOS-push и iOS-приёмка не реализованы; полная бригадная работа и версии записей остаются впереди. `native-stub/` — историческая TS-заготовка; веб-панель сохраняется.

**Производительность.** События WebSocket и постоянный опрос с интервалом 5 секунд поддерживают актуализацию панели. Интервал запуска запроса не является измеренной гарантией доставки за 5 секунд. Цели кейса по числу нажатий и загрузке фото на мобильной сети не являются проведенными нагрузочными или полевыми замерами. Срок загрузки зависит от устройства, размера снимка и сети.

**Развертывание.** Текущая конфигурация предназначена для локального MVP с одним процессом API. Вход ограничен десятью неуспешными попытками за минуту для пары адрес/логин; лимит хранится в памяти процесса. Перед внедрением нужны учетные записи и парольная политика предприятия, HTTPS, централизованный лимит попыток, резервное копирование с проверкой восстановления, миграции для дальнейших изменений схемы, мониторинг и нагрузочная проверка. `SEED_DEMO=false` отключает заполнение демо; создание реальных пользователей и исходных справочников требует отдельной процедуры. Для нескольких процессов API понадобится общий канал событий, например Redis, и единственный планировщик уведомлений; диспетчер push сейчас тоже работает в одном процессе API.
