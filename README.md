# НарядAI · Костанайские минералы

Веб-панель управления ремонтными нарядами: выдача задания, работа исполнителя, контроль сроков и простоев, приемка мастером, аналитика и справочники. Сервер и база данных реализованы; ИИ и нативное приложение оставлены явными заглушками по условиям задачи.

Стек: **React + TypeScript + Vite**, **Python + FastAPI + SQLAlchemy**, **PostgreSQL 17**. Веб-панель работает на русском языке. Даты показываются в часовом поясе **Asia/Almaty**; сервер хранит время в UTC. Все работники и производственные записи в начальном наборе вымышлены.

## Быстрый запуск с PostgreSQL

Нужны Docker Engine/Desktop и Docker Compose v2. Из корня проекта:

```bash
docker compose up --build -d
```

- Веб-панель: [http://localhost:8080](http://localhost:8080).
- Документация API: [http://localhost:8000/docs](http://localhost:8000/docs).
- Проверка сервера: [http://localhost:8000/api/health](http://localhost:8000/api/health).

Первый запуск скачивает образы, собирает приложения, создает схему и демонстрационные данные. Сначала запускается PostgreSQL; веб-панель стартует после успешной проверки сервера. Состояние видно через `docker compose ps`, журналы — `docker compose logs -f --tail=100`.

Параметры по умолчанию предназначены для локальной демонстрации. При необходимости скопируйте `.env.example` в `.env` и измените порты, имя базы и пароль перед первым запуском. Значения `POSTGRES_*` определяют подключение контейнера API; отдельный `DATABASE_URL` из `.env` не переопределяет их. Для пароля с символами `@`, `:`, `/` нужно отдельно адаптировать URL подключения либо использовать длинный случайный пароль из букв и цифр.

База и фотографии хранятся в томе `postgres_data`; обычный `docker compose down` сохраняет данные. Изображения после проверки и сжатия записываются в БД, отдельный каталог uploads не нужен. Повторный старт не пересоздает существующие демонстрационные данные. `docker compose down -v` **удаляет всю базу и фотографии**; выполняйте эту команду только для намеренного сброса демо.

## Учетные записи

Общий демонстрационный PIN — **1234**.

| Логин | Роль | Доступ |
| --- | --- | --- |
| `master`, `master2` | Мастер | Создание и изменение нарядов, назначение, приемка, возврат на доработку |
| `worker`, `worker2` … `worker15` | Работник | Свои наряды, прием/очередь/отказ, выполнение, фотографии и отчет |
| `manager` | Руководитель | Просмотр производства, аналитика и выгрузки |
| `admin` | Администратор | Полный доступ и изменение справочников |

Права проверяет сервер на каждом действии. Вход возвращает случайный токен сессии; сервер хранит его хэш в БД. PIN используется только для упрощенного демонстрационного входа.

## Что можно показать

1. Войти как `master`: просмотреть сменные показатели, производственную доску и загрузку работников; применить фильтры по участку, оборудованию, исполнителю, приоритету и статусу.
2. Создать наряд с оборудованием, исполнителем или бригадой, сроком и приоритетом. Для проверки роли работника назначить его пользователю `worker`.
3. Войти как `worker`, принять наряд и начать работу. При необходимости поставить его в очередь, приостановить с причиной и возобновить.
4. Для внеплановой работы добавить фотографию «После»: без нее сервер не позволит завершить наряд. Заполнить выполненные работы, дефект и фактические материалы.
5. Завершить наряд: появятся результат **заглушки ИИ** и запись в истории. ИИ не закрывает наряд автоматически. Под `master` принять результат с оценкой или вернуть на доработку с причиной.
6. Открыть аналитику: сравнить плановые и внеплановые работы, простои оборудования, расход материалов и рейтинг работников. Экспортировать отфильтрованные данные. Под `admin` проверить справочники.
7. Открыть два окна браузера с разными учетными записями: изменения приходят по WebSocket, с резервным обновлением через опрос. Для разных пользователей удобны отдельные профили браузера или обычное и приватное окно.

История хранит изменения статусов и параметров, авторов, время и причины. Просрочка вычисляется отдельно от статуса. Фоновый монитор формирует уведомления о приближении срока, просрочке и непринятых заданиях; повторные уведомления одного типа для наряда не дублируются.

Рейтинг исполнителя по закрытым нарядам: **60% — средняя оценка мастера, 30% — выполнение в срок, 10% — отсутствие доработок**, итог в шкале 0–100. Время приемки мастером не ухудшает своевременность работника: со сроком сравнивается завершение работ. Подробная формула приведена в [docs/architecture.md](docs/architecture.md).

Начальное заполнение содержит не менее 520 исторических нарядов за 90 дней и актуальные задания смены, 4 участка, 25 единиц оборудования, 2 мастеров, 15 работников, 3 бригады, 20 кодов дефектов и 40 материалов. В истории заложены повторные отказы конвейеров, проблемы после обслуживания и повышенный расход материалов для демонстрации аналитики.

## Локальная разработка

Рекомендуется Python **3.12**, Node.js **24** и pnpm **11.25.0**. PostgreSQL используется в Compose; для быстрой локальной проверки поддерживается SQLite.

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
npm install --global pnpm@11.25.0
cd frontend
pnpm install --frozen-lockfile
cd ..
./scripts/run-local.sh
```

Локальная панель: [http://localhost:5173](http://localhost:5173). Скрипт запускает API на порту 8000 и Vite на 5173; `Ctrl+C` завершает оба процесса. Он использует базу `data/naryad.db`. Существующую виртуальную среду можно указать через `PYTHON_BIN=/absolute/path/to/python ./scripts/run-local.sh`. Скрипт не читает `.env` автоматически: передавайте переменные окружения явно или экспортируйте их в оболочке.

Для разработки с внешним PostgreSQL:

```bash
DATABASE_URL='postgresql+psycopg://user:password@localhost:5432/naryad_ai' ./scripts/run-local.sh
```

Сервисы можно запускать раздельно:

```bash
# Терминал 1, каталог backend/
../.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

# Терминал 2, каталог frontend/
pnpm dev
```

Vite и nginx проксируют `/api` и WebSocket к FastAPI; адрес API не зашит в браузерный bundle. Основной адрес WebSocket — `/api/ws?token=...`; `/ws` оставлен совместимым псевдонимом.

## Схема и миграции

Первый старт API создает отсутствующие таблицы. В `backend/migrations/` также есть исходная миграция Alembic `0001_initial`; ее можно применить к новой или уже инициализированной демонстрационной БД:

```bash
docker compose exec backend alembic upgrade head
```

Для локального запуска выполняйте `alembic upgrade head` из `backend/` с тем же `DATABASE_URL`, что использует сервер. Миграция фиксирует исходную схему. Автоматическое создание таблиц не изменяет уже существующие столбцы: последующие изменения моделей должны сопровождаться отдельными проверенными миграциями. Откат исходной миграции удаляет таблицы и предназначен только для disposable-среды.

## Проверка

```bash
# Серверные тесты
cd backend
../.venv/bin/python -m pytest -q
cd ..

# Проверка типов и production-сборка веб-панели
cd frontend
pnpm run build
cd ..

# Проверка типов нативного контракта
./frontend/node_modules/.bin/tsc -p native-stub/tsconfig.json

# Сквозная проверка HTTP API при работающем сервере
python3 scripts/smoke_api.py
```

`Makefile` содержит сокращения `make up`, `make down`, `make logs`, `make local`, `make build`, `make test`. Сквозная проверка создает отдельные тестовые наряды в текущей базе: запускайте ее в демонстрационной среде.

## Границы реализации

**ИИ — заглушка.** Ответы проверки качества и аналитические подсказки создаются детерминированной логикой с `is_stub=true`. Нейросеть, компьютерное зрение, LLM/RAG, распознавание дефектов по фото и внешние ИИ API не подключены. Фотографии сохраняются и доступны уполномоченным пользователям, но не анализируются моделью. Окончательное решение принимает мастер.

**Нативная часть — заглушка.** В `native-stub/` подготовлены TypeScript-контракты и HTTP-адаптер для будущего React Native клиента. Нет Android/iOS сборки, настоящей камеры, офлайн-синхронизации, FCM/APNs и регистрации устройств. Все действия работника можно проверить через веб-панель. Подробности — в [native-stub/README.md](native-stub/README.md).

**Производительность.** События WebSocket и резервный опрос рассчитаны на актуализацию панели в пределах 5 секунд. Цели кейса по числу нажатий и загрузке фото на мобильной сети не являются проведенными нагрузочными или полевыми замерами. Срок загрузки зависит от устройства, размера снимка и сети.

**Развертывание.** Текущая конфигурация предназначена для локального MVP с одним процессом API. Вход ограничен десятью неуспешными попытками за минуту для пары адрес/логин; лимит хранится в памяти процесса. Перед внедрением нужны учетные записи и парольная политика предприятия, HTTPS, централизованный лимит попыток, резервное копирование с проверкой восстановления, миграции для дальнейших изменений схемы, мониторинг и нагрузочная проверка. `SEED_DEMO=false` отключает заполнение демо; создание реальных пользователей и исходных справочников требует отдельной процедуры. Для нескольких процессов API понадобится общий канал событий, например Redis, и единственный планировщик уведомлений.
