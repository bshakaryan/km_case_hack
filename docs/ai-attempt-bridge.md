# Мост проверки конкретной сдачи

## D24: реализованный ограниченный фото-пакет v2

Версия 2 добавляет `POST /internal/v2/submission-review`. Версия 1 остаётся совместимым текстовым endpoint. Новый адаптер явно использует v2; автоматического переключения на v1 после ошибки нет. Дополнительный `photo_content` содержит `{id, data_base64}` в том же порядке, что и метаданные `photos`: только исходные JPEG, связанные с этой попыткой. SHA256 каждого снимка проверяется против сохранённого контекста, общий `input_sha256` покрывает также содержимое. Сервис не читает текущую карточку, пути, URL, общую БД или фото других нарядов.

Пределы v2: десять фото, до 4 MiB декодированных байтов каждого, до 4 000 000 пикселей, до 56 MiB JSON-запроса. Превышение не означает успешную проверку неполного набора; отчёт сохраняется, задача остаётся без результата. Ответ по-прежнему ограничен 64 KiB, общий deadline адаптера — 8 секунд. Авторизация предшествует чтению тела; JSON/base64/SHA обрабатываются вне event loop, максимум два активных разбора без очереди. CV использует один отдельный процесс и монотонный бюджет 5 секунд, включая старт, затем до 0.5 секунды обычной остановки. Большие байты передаются через созданную сервером временную shared memory, без медиафайлов и bulk pickle в spawn. Если ОС ещё не подтвердила остановку, отслеживаемый reaper удерживает память и область допуска до завершения; новая CV-задача не стартует. Отмена HTTP сразу возвращает управление, не освобождая чужую активную область. Запуск/остановка процесса ОС не являются доказанным жёстким SLA; сетевой лимит и ограничение допуска сохраняются независимо.

В `result.photo_check` сохраняются `status` (`checked`, `unavailable`, `no_after`), `method=local_cv`, `scope=submission_selected_pair`, `before_id`/`after_id`, nullable `duplicate_before`, `exact_duplicate_groups`, `equipment_status` (`different`, `unknown`), `model_available`, `capture_time_status=unknown`, `repair_status=unknown`, `history_status=not_checked`. Выбирается максимальный известный ID каждого вида в неизменяемом наборе; это технический выбор пары, не утверждение времени съёмки. SHA-дубли ищутся внутри всей попытки, перцептивное сравнение — только выбранной пары. Фото доработки не отбрасываются. `unavailable`/`no_after` не выдают положительных результатов сравнения.

Повторно используются локальные функции уже написанного фото-модуля. Проверка оборудования доступна только с установленными и проверенными по SHA256 весами; отсутствующая модель остаётся неизвестностью. Автоматической загрузки весов и внешнего vision/LLM нет. CV не доказывает ремонт, свежесть снимка или физическую идентичность оборудования. Поэтому v2 оставляет `source_verdict=needs_master_review`, `score=null`; окончательное решение и оценка принадлежат мастеру. `is_stub`/`llm_used` описывают текстовую модель, а отдельный `photo_check` — фактически выполненное локальное сравнение. Q01–Q06 этим пакетом не решаются.

Контракт зафиксирован перед реализацией. v2, проверка входа/результата, ограниченный процесс и показ фото-выводов в React/Flutter реализованы без новой миграции. Целевые испытания и их границы записаны в [verification](verification.md); общий CI выполняется для окончательного опубликованного коммита.

Пакет после интеграции `43ecb93` выполняется в прежней `feature/order-versions`. Основной сервер остаётся единственным владельцем прав, состояния наряда, очереди задач и финального решения мастера. Изолированный демонстрационный сервис и его `BackendDataSource` не получают общий доступ к рабочей базе.

## Первый пакет D23: текстовый v1

- Новая nullable `submission_attempts.ai_input` содержит известный контекст, сохранённый в транзакции сдачи: исходные поля наряда, версия на момент сдачи, назначение, справочник шифров и идентичность связанных фото. Старые попытки остаются с null; их исходное задание не восстанавливается из изменившейся карточки. Сам `payload` остаётся прежним отчётом с добавочным расходом попытки.
- Существующие `stub` задачи обслуживает прежняя заглушка. По D25 стандартный Docker Compose создаёт новые задачи с `provider=ai_service` и `AI_REVIEW_MODE=queued_service`; `queued_stub` остаётся явным compatibility/test fallback. Адрес и server-only токен обязательны. Смена настройки не перепривязывает уже сохранённые задачи.
- Stateless `POST /internal/v1/submission-review` принимает только server-generated envelope версии 1: `attempt_id`, `order_id`, frozen `context`, `report`, метаданные связанных `photos` и `input_sha256`. Хеш — SHA256 UTF-8 JSON без самого `input_sha256`, с `sort_keys=True`, `separators=(',', ':')`, `ensure_ascii=False`, `allow_nan=False`. Ответ повторяет версию/attempt/hash и содержит проверенный `result`. Ошибка идентичности не становится оценкой другой попытки.
- Сервис запускается отдельной лёгкой factory; существующие runtime-policy и запрет общего BackendDataSource сохраняются. Он повторно использует функции текстовой проверки уже написанного модуля. По умолчанию внешние LLM-запросы отсутствуют; выбор/разрешение внешней обработки Q01 остаются открытыми. Не называем реальные входные данные синтетическими ради обхода защиты.
- Этот ограниченный пакет передаёт ID/вид/SHA256 фото, а не пиксели, URL или пути. Содержимое изображений, глобальные дубликаты и оборудование этим endpoint не анализируются. CV/vision остаются следующим связным пакетом с отдельным бюджетом времени; существующее разрешение повторного использования фото после доработки сохраняется.
- Отсутствие утверждённых активных интервалов/материальных норм остаётся неизвестностью. `started_at → completed_at` не используется как реальное время работы. Рейтинг, нормы предприятия и правила Q02–Q05 не меняются.

## Результат и безопасность

`accepted → passed`, `accepted_with_remarks → needs_attention`, `needs_rework → needs_rework`, `needs_master_review → needs_attention` с `score=null`. Исходный `source_verdict`, `llm_used`, `is_recommendation=true` и фактический `is_stub` сохраняются в JSON попытки; численная оценка ИИ nullable и не подставляется вместо оценки мастера. Правила/fallback явно помечены заглушкой; модель не выбирает своё происхождение. Новая миграция сохраняет прежние численные оценки и связи. Финальный `close` по-прежнему требует ручную оценку мастера.

HTTP выполняется после commit захвата задачи, без SQL-lock на время обращения. Общий сетевой deadline 8 секунд меньше lease 30 секунд; injected семантический обработчик ограничен 6 секундами. Автоматических транспортных повторов, redirect и proxy из окружения нет, ответ ограничен. Сервисный токен не попадает в клиенты, результаты, ошибки или логи. Ответ принимается только при прежнем lease/текущей попытке/назначении; прежние ключи, отчёты, списания, фото и исходные версии не меняются. Подтверждённый SHA256 входа и версия протокола сохраняются вместе с результатом попытки.

## Запуск и границы готовности

Основной Docker Compose поднимает bridge как внутренний `ai-review:8010` и по умолчанию направляет туда новые сдачи. Сгенерируйте случайный `AI_SERVICE_TOKEN` в игнорируемом корневом `.env`; он передаётся только backend и внутреннему сервису. Для отдельного запуска установите `ai_service/requirements.txt`, затем из `ai_service/`: `AI_SERVICE_TOKEN=... uvicorn app.attempt_bridge:create_attempt_app --factory --host 127.0.0.1 --port 8010`. На основном сервере задаются одинаковый токен, `AI_SERVICE_URL` и `AI_REVIEW_MODE=queued_service`. Адаптер использует v2; старый v1 доступен явно как `AttemptServiceAdapter(..., version=1)`, без автоматического fallback. Не включать этот режим для чужого адреса; HTTP без TLS предназначен для доверенного loopback/внутренней сети, удалённая связь требует HTTPS. Внешний нейросетевой провайдер этим запуском не включается.

Настоящие локальные процедурные JPEG/CV/spawn и ASGI-композиция с серверной SQLite проверены в ограниченной области, указанной в verification. Это не socket/физическое устройство, установленный MobileNet, vision-оценка ремонта или завершение R21–R25. Веса MobileNet должны уже находиться локально и совпадать с известным SHA256; без них `model_available=false` и оборудование неизвестно. Общая история дублей, давность фото, разрешение внешней обработки/провайдер и зависимые доменные правила остаются отдельными работами. PR #5 уже слит; новые ветки/PR для пакета не создаются, CI ветки запускается вручную.
