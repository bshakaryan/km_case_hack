# Мост проверки конкретной сдачи

## D27: текущая проверка фото через OpenAI Vision

Новый путь v2 сохраняет проверку frozen-входа, SHA256 связанных фото и выбор по максимальному ID каждого типа, но больше не запускает локальный CV-процесс. Если фото `after` есть, в OpenAI Responses API отправляется только выбранная пара JPEG; когда `before` отсутствует — только `after`, а модель обязана оставить сравнение оборудования/дефекта неизвестным. Текст отчёта, данные карточки, имена и ID сотрудников, фото других сдач не попадают в OpenAI-запрос. Изображение само может содержать людей или читаемый текст.

Модель выдаёт строгий структурированный ответ о видимых признаках; численная оценка не вычисляется, итог всегда `source_verdict=needs_master_review`, `score=null`, решение принимает мастер. При отсутствии фото `after` сервис пропускает OpenAI и возвращает `no_after`. Без API-ключа и при ошибке провайдера возвращается фиксированный `503/502`, задача штатно повторяется и затем становится `failed`, но сдача не теряется.

В корневом игнорируемом `.env` задаются `OPENAI_API_KEY` и при необходимости `OPENAI_VISION_MODEL` (по умолчанию `gpt-6-astra`). Compose передаёт ключ только контейнеру `ai-review`; backend знает только признак конфигурации, веб и Flutter не получают секрет. `AI_SERVICE_TOKEN` — отдельный случайный bearer-секрет для вызова backend → `ai-review`, не OpenAI-ключ и не платный токен. Запрос выставляет `store:false`; это не заменяет и не подтверждает retention/processing-политику организации OpenAI. OpenAI API считает изображения входными токенами, поэтому расход зависит от выбранных снимков/детализации.

Ответ проверки содержит `photo_check` со статусом `checked|no_after`, `method=openai_vision`, выбранными ID, визуальным ответом, `capture_time_status=unknown` и `history_status=not_checked`. Текущая строгая схема дополнительно требует четыре категории видимых признаков: чистота/мусор, крепления/опоры, кожухи/ограждения и следы жидкости; для каждой возвращается `no_visible_issue|issue_visible|not_assessable` и короткое наблюдение. Формальная часть отдельно возвращает `report_checks`: наличие описания/шифра, словарные сопоставления, доступность норм материалов/времени, срок и фото после. Недоступные нормы или факты остаются `unknown`; совпадение слов — эвристика. Проверка идентичности оборудования, устранения дефекта и качества по фото остаётся предположительной; время съёмки, реальность ремонта и фото других нарядов не подтверждаются. Пакет не закрывает полностью R23–R27: в частности, нет доказательства времени съёмки/повторов, проверенной точности модели на размеченных примерах или отдельного ролевого состава отчёта.

## Историческое решение D24: локальное сравнение фото

Версия 2 добавляет `POST /internal/v2/submission-review`. Версия 1 остаётся совместимым текстовым endpoint. Новый адаптер явно использует v2; автоматического переключения на v1 после ошибки нет. Дополнительный `photo_content` содержит `{id, data_base64}` в том же порядке, что и метаданные `photos`: только исходные JPEG, связанные с этой попыткой. SHA256 каждого снимка проверяется против сохранённого контекста, общий `input_sha256` покрывает также содержимое. Сервис не читает текущую карточку, пути, URL, общую БД или фото других нарядов.

Исторический D24 предшествовал подключению OpenAI и использовал следующие внутренние детали; они не описывают активный provider. Пределы v2 остаются: десять фото, до 4 MiB декодированных байтов каждого, до 4 000 000 пикселей, до 56 MiB JSON-запроса. Превышение не означает успешную проверку неполного набора; отчёт сохраняется, задача остаётся без результата. Авторизация предшествует чтению тела; JSON/base64/SHA обрабатываются вне event loop, максимум два активных разбора без очереди.

Исторический D24 сохранял `method=local_cv` и метаданные дубликатов; текущие новые результаты используют структуру OpenAI из D27. Старые JSON-результаты не переписываются и отображаются как исторические; bridge больше не создаёт локальные CV-результаты.

Старый локальный модуль не доказывал ремонт, свежесть снимка или физическую идентичность оборудования. Его результаты остаются неизменёнными в истории; новые результаты имеют фактическое происхождение `openai_vision`. Q01 теперь выбран для внешней обработки конкретных фото, но обработка текста и политика персональных данных/хранения аккаунта остаются вопросами.

Контракт зафиксирован перед реализацией. v2, проверка входа/результата, ограниченный процесс и показ фото-выводов в React/Flutter реализованы без новой миграции. Целевые испытания и их границы записаны в [verification](verification.md); общий CI выполняется для окончательного опубликованного коммита.

Пакет после интеграции `43ecb93` выполняется в прежней `feature/order-versions`. Основной сервер остаётся единственным владельцем прав, состояния наряда, очереди задач и финального решения мастера. Изолированный демонстрационный сервис и его `BackendDataSource` не получают общий доступ к рабочей базе.

## Первый пакет D23: текстовый v1

- Новая nullable `submission_attempts.ai_input` содержит известный контекст, сохранённый в транзакции сдачи: исходные поля наряда, версия на момент сдачи, назначение, справочник шифров и идентичность связанных фото. Старые попытки остаются с null; их исходное задание не восстанавливается из изменившейся карточки. Сам `payload` остаётся прежним отчётом с добавочным расходом попытки.
- Существующие `stub` задачи обслуживает прежняя заглушка. По D25 стандартный Docker Compose создаёт новые задачи с `provider=ai_service` и `AI_REVIEW_MODE=queued_service`; `queued_stub` остаётся явным compatibility/test fallback. Адрес и server-only токен обязательны. Смена настройки не перепривязывает уже сохранённые задачи.
- Stateless `POST /internal/v1/submission-review` принимает только server-generated envelope версии 1: `attempt_id`, `order_id`, frozen `context`, `report`, метаданные связанных `photos` и `input_sha256`. Хеш — SHA256 UTF-8 JSON без самого `input_sha256`, с `sort_keys=True`, `separators=(',', ':')`, `ensure_ascii=False`, `allow_nan=False`. Ответ повторяет версию/attempt/hash и содержит проверенный `result`. Ошибка идентичности не становится оценкой другой попытки.
- Сервис запускается отдельной лёгкой factory; существующие runtime-policy и запрет общего BackendDataSource сохраняются. Он повторно использует функции текстовой проверки уже написанного модуля. По умолчанию внешние LLM-запросы отсутствуют; выбор/разрешение внешней обработки Q01 остаются открытыми. Не называем реальные входные данные синтетическими ради обхода защиты.
- Этот ограниченный пакет передаёт ID/вид/SHA256 фото, а не пиксели, URL или пути. Содержимое изображений, глобальные дубликаты и оборудование этим endpoint не анализируются. CV/vision остаются следующим связным пакетом с отдельным бюджетом времени; существующее разрешение повторного использования фото после доработки сохраняется.
- Отсутствие утверждённых активных интервалов/материальных норм остаётся неизвестностью. `started_at → completed_at` не используется как реальное время работы. Рейтинг, нормы предприятия и правила Q02–Q05 не меняются.

## Результат и безопасность

`accepted → passed`, `accepted_with_remarks → needs_attention`, `needs_rework → needs_rework`, `needs_master_review → needs_attention` с `score=null`. Исходный `source_verdict`, `llm_used`, `is_recommendation=true` и фактический `is_stub` сохраняются в JSON попытки; численная оценка ИИ nullable и не подставляется вместо оценки мастера. Правила/fallback явно помечены заглушкой; модель не выбирает своё происхождение. Новая миграция сохраняет прежние численные оценки и связи. Финальный `close` по-прежнему требует ручную оценку мастера.

HTTP выполняется после commit захвата задачи, без SQL-lock на время обращения. OpenAI-клиент имеет 20-секундный timeout, backend adapter — 25 секунд, lease остаётся 30 секунд. Redirect и proxy из окружения выключены; ответ ограничен, исключения/ключи провайдера не сохраняются. Межсервисный токен не попадает в клиенты, результаты, ошибки или логи. Ответ принимается только при прежнем lease/текущей попытке/назначении; прежние ключи, отчёты, списания, фото и исходные версии не меняются. Подтверждённый SHA256 входа и версия протокола сохраняются вместе с результатом попытки.

## Запуск и границы готовности

Основной Docker Compose поднимает bridge как внутренний `ai-review:8010` и по умолчанию направляет туда новые сдачи. Сгенерируйте случайный `AI_SERVICE_TOKEN` в игнорируемом корневом `.env`; он передаётся backend и внутреннему сервису. Там же задайте `OPENAI_API_KEY=...`; Compose передаёт OpenAI-ключ только bridge. Для отдельного запуска установите `ai_service/requirements-bridge.txt` и задайте обе переменные окружения. На основном сервере остаются `AI_SERVICE_URL` и `AI_REVIEW_MODE=queued_service`. Адаптер использует v2; старый v1 доступен явно как `AttemptServiceAdapter(..., version=1)`, без автоматического fallback. Не включать этот режим для чужого адреса; HTTP без TLS предназначен для доверенного loopback/внутренней сети, удалённая связь требует HTTPS.

Реальные запросы OpenAI и точность на производственных фото этой реализацией не подтверждены; тестовый транспорт заменяет внешний API. Нужна экспертная разметка реальных пар и отдельная оценка политик данных перед широким использованием. Время съёмки, качество ремонта, общий поиск дублей и связанные правила R21–R25 остаются открытыми. PR #5 уже слит; новые ветки/PR для пакета не создаются, CI ветки запускается вручную.
