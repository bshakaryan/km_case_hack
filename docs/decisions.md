PostgreSQL-приёмка и оставшиеся задачи этапа 2 фиксируются отдельно в плане/проверках, а не считаются закрытыми этой записью.

Срез D09/D10/D13 · ветка `feature/order-history`, 8 октября: новые назначения и сдачи сохраняются отдельными записями, решения мастера дополняют попытку без перезаписи её отчёта/ИИ. `completion.materials` остаётся накопленным расходом, материалы новой попытки — только добавочным. Снимок включает весь набор фото, доступный при сдаче; существующее разрешение повторного использования фото и лимит пять каждого вида на наряд сохраняются до решения правил свежести Q04. Для старых данных создаётся только `legacy_snapshot`, без выдуманного автора, предыдущих попыток и связей фото/расхода. Это реализация согласованных решений, а не закрытие Q01–Q06; подробности API и пределы проверки описаны отдельно.

Срез D07/D14 · `feature/ai-review-jobs`, 8 октября: отчёт и задача фиксируются общей транзакцией, обработчик получает данные конкретной попытки, а результат привязывается к ней один раз. Повторы, восстановление после перезапуска и просроченный захват задачи не должны создавать вторую оценку или менять более новую/отменённую сдачу. Основной режим — фоновая локальная заглушка, совместимый `inline_stub` явно включается для старого синхронного сценария и регрессий. Внешние AI API и отдельный `ai_service` к живым данным не подключены; Q01 сохраняется. Gateway чтения/повтора проверяет текущие права, service-token клиентам не выдаётся. Мастер принимает или возвращает работу вручную после результата; автоматическое закрытие/возврат и обход неудачной проверки не добавлены.

Порядок работы с ветками · решение владельца 8 октября: пока не объединять пакеты в main, создавать следующую зависимую ветку от предыдущей и направлять PR в неё. Независимые задачи не обязаны становиться частью этой цепочки. Изменение базы и последовательное слияние выполняются при отдельном решении о готовности интеграции.

### Офлайн-состояние и устойчивые данные Android-клиента

D17 · Принято 7 октября 2026: аккаунт и ранее загруженные данные переживают отсутствие сети, отправка без сети переходит в локальную очередь.

- Сессия восстанавливается без обращения к серверу: сетевой сбой при старте не сбрасывает вход; `401` по-прежнему завершает сессию. Снимок последних данных (наряды, справочники, работники, панель, уведомления, аналитика, профиль) хранится на устройстве и открывается офлайн с отметкой времени.
- Просмотренные фотографии нарядов кэшируются на диске с ограничением объёма; очередь отправленных фото хранит байты на диске до подтверждения сервером.
- Изменяющие команды (выдача, переходы, сдача, фото, прочтение уведомления) без сети сохраняются в локальной очереди и отправляются при восстановлении связи с зависимостями: фото до — после создания наряда, фото после и сдача — после нужного статуса.
- Повторы создания, перехода, сдачи и фото защищены серверными ключами `X-Client-Command-Id` (контракт: [api-contract.md](api-contract.md)); автоматический повтор этих POST использует прежний ключ. Отметка собственного уведомления прочитанным повторно устанавливает тот же флаг и не относится к четырём POST с ключами. Локально сохранённое действие не показывается подтверждённым сервером; конфликт (`409/422/403` при синхронизации) выводится пользователю и не разрешается молчаливой перезаписью (D08).
- Хранилище — `sqflite` + `path_provider` на Android; веб-превью остаётся в памяти (`kIsWeb`), веб-панель этим решением не меняется. Технология выбрана владельцем на этапе планирования вместе с полным объёмом кэша.

D17 реализован частично. 7–8 октября отдельный прогон подтвердил дисковое восстановление после force-stop при выключенном API на Android Emulator; это не вывод из наличия кода хранения и unit-тестов. Результаты и ограничения записаны в [verification.md](verification.md). Постоянные черновики ещё не отправленного ввода, полная матрица конфликтов и системная фоновая синхронизация этим решением не объявляются готовыми.

Уточнения D17 после аудита 7 октября, в рамках согласованного исправления:

- Снимки, фото, сопоставления локальных/серверных ID и очередь должны быть изолированы по полному нормализованному адресу API (включая схему, порт и путь) и ID пользователя. Совпадение ID работников на разных серверах не разрешает переносить данные или отправлять команды.
- Изменяющий запрос допускается после успешной постоянной записи команды и медиа. Ошибка дискового хранилища не заменяется незаметным переходом в память или сообщением об офлайн-сохранении.
- `401` останавливает отправку и завершает текущую сессию; ожидающая команда сохраняет свой ключ для повторного входа в тот же аккаунт на том же сервере. Выход очищает доступный кэш своей области; оставшуюся очередь другой аккаунт не видит и не отправляет. Синхронизация выполняется последовательно; отклонённая/конфликтная предыдущая команда блокирует зависимые действия по тому же наряду.
- Старые локальные данные без доказанного сервера/пользователя не присваиваются новой области автоматически. Старые команды сохраняются изолированными и не отправляются; старые кэши не читаются. Сохранённая сессия без ID владельца требует онлайн-проверки `/auth/me` перед доступом к кэшу. Это сознательное ограничение обновления, а не обещание безопасно восстановить неизвестное происхождение данных.

Готовность каждого уточнения определяется кодом и результатом проверки, а не добавлением этого правила в реестр.

### Ролевой доступ веба и API

D18 · Принято 8 октября 2026 по поручению владельца «Отдели роли как нужно». Веб показывает разделы согласно роли: мастер — обзор, наряды, сотрудники, аналитика, справочники для чтения и интеграции; исполнитель — личная работа и свои наряды; руководитель — обзор, наряды, сотрудники, аналитика и интеграции только для чтения; администратор — все разделы и управление справочниками. Для отчёта исполнителя сервер выдаёт только материалы и коды неисправностей из справочных данных. Список сотрудников доступен мастеру, руководителю и администратору; интеграции — тем же ролям. API аналитики для работника сохраняет только персональную выборку, используемую экраном его показателей в Flutter. Подробности и фактическая проверка — в [контракте](api-contract.md), [описании веба](web-ux.md) и [проверках](verification.md).

Уточнение владельца · 8 октября 2026: у исполнителя нет отдельной вкладки «Наряды»; назначенные ему активные и закрытые наряды остаются доступны внутри «Моя работа». Это изменение веб-навигации, а не серверного доступа к собственным нарядам.

### Действия исполнителя и понятная очередь

D19 · Принято 8 октября 2026 по поручению владельца переделать очередь и не позволять мастеру принимать наряд за рабочего. Исполнитель — единственная роль, которая принимает/отклоняет назначение, начинает, приостанавливает/продолжает и сдаёт работу; действие ограничено его назначенными нарядами. Мастер и администратор назначают/редактируют и отменяют наряды, возвращают работу или принимают результат, но не выполняют эти действия за исполнителя.

Принятие — единственное текущее задание рабочего, а не способ набирать несколько заданий разом. Если есть `accepted`, `in_progress`, `paused` или уже ожидающее задание, повторное принятие отклоняется с `409`; назначенное задание можно явно отправить кнопкой «В очередь». У очереди отдельный смысл: `queue` переводит `issued`, `rework` или `accepted` в `queued`; повтор для `queued` не меняет состояние. Рабочий может поставить в очередь несколько назначений, но одновременно принять/исполнять — только одно. Для старых записей с несколькими `accepted` API показывает верхнее задание как `accepted`, остальные как `queued` по серверному порядку; БД и прежний журнал не переписываются. Старые несколько `paused` можно продолжать по одному, но начать новую работу при паузе нельзя. Позиция рассчитывается сервером среди `accepted|queued` по приоритету `emergency → high → normal → planned`, затем по времени текущего назначения и ID. Начать можно только первое задание и только если нет другого `in_progress` или `paused`; попытка начать при занятом рабочем отклоняется с `409`, не маскируется успешным ответом «осталось в очереди». Следующий наряд автоматически не запускается — исполнитель начинает его сам. Ручного перетаскивания нет; изменение приоритета мастером/администратором пересчитывает позиции. `queue_position` вычисляется, в БД не хранится.

### FCM как провайдер push (Android)

D20 · Принято 8 октября 2026: push на Android доставляет Firebase Cloud Messaging через HTTP v1 API.

- Провайдер — FCM HTTP v1; Firebase-проект `km-case-hack` (номер `716637680468`), Android-пакет `kz.km.naryad_ai`. Android — первым; iOS/APNs в этот пакет не входят и остаются следующим шагом.
- Доставка устойчивая: `notify()` в одной транзакции с уведомлением БД создаёт запись в outbox `push_tasks`, фоновый диспетчер внутри процесса API отправляет ожидающие задания через FCM с повторами и нарастающей задержкой и отзывает недействительные токены в `device_tokens`. Это исполнение D14 (сохраняемое состояние и события после фиксации) для push. Уведомление и outbox создаются одной транзакцией; при неопределённом ответе FCM доставка может повториться.
- Учётные данные сервисного аккаунта передаются только через окружение: inline JSON в `FIREBASE_CREDENTIALS_JSON` (приоритет) либо путь к файлу в `FIREBASE_CREDENTIALS`; автоматического выбора ключа нет, доставка требует явного `PUSH_ENABLED=true` (по умолчанию `false`). Секреты в репозиторий не коммитятся. Конфигурация: `FIREBASE_PROJECT_ID` (по умолчанию `km-case-hack`), `PUSH_ENABLED`, `PUSH_DISPATCH_SECONDS`, `PUSH_MAX_ATTEMPTS`.
- Регистрация устройств — маршруты `POST /api/devices` и `POST /api/devices/unregister`; клиент ставит токен после входа/восстановления сессии и отзывает при выходе (контракт: [api-contract.md](api-contract.md)).
- Подтверждение аварийного уведомления исполнителем (полное выполнение R18, включая ответ на аварийное) в этот пакет не входит и отложено; приёмка доставки на физических устройствах остаётся отдельной проверкой.
- Решение частично закрывает **Q06**: push-провайдер для Android выбран. Брокер задач/событий и место его размещения, хранение медиа и масштабирование на несколько процессов в Q06 остаются открытыми.

| Q01 | Внешний ИИ API или локальная модель; доступные данные, стоимость и среда запуска. | Сохраняем абстракцию провайдера. До выбора работаем с синтетическими/обезличенными примерами; не подключаем платный сервис и не передаём реальные данные. PDF §9 требует обезличивания сотрудников. |
| Q02 | PDF §5.3 требует фото внепланового завершения, а §11.7 показывает отрицательный отчёт без фото. | Предложено: сохранять неполную попытку/черновик, показывать замечания и запрещать успешное завершение. Это ещё не принято; действующий `complete` продолжает возвращать 422 без фото. |
| Q03 | Отрицательный вердикт ИИ автоматически возвращает работу или ждёт мастера? | Предложено подтверждение мастером. До решения сохраняем текущий ручной `rework`; не добавляем автоматический переход по ответу модели. |
| Q04 | Кто фиксирует фактическую остановку/запуск, какой календарь смен, что считать активным временем и допустимой давностью фото? | До доменной реализации оформить сценарии с владельцем. EXIF и время телефона сами по себе не доказывают свежесть снимка. Офлайн-съёмка и загрузка имеют разные времена. |
| Q05 | Веса полного рейтинга, сложность работ, уважительные причины отказа, распределение личного вклада, нормы материалов и связь повторного дефекта с ремонтом. | Текущие 60/30/10 — только существующая формула. Нельзя выдавать её за полный рейтинг §6.6 или автоматически начислять бригадную оценку всем участникам. |
| Q06 | Размещение, нагрузка, брокер задач/событий, push-провайдер, хранение медиа, будущие ERP/1С-интерфейсы. | Не вводить неподтверждённые инфраструктурные зависимости. Фото в PostgreSQL допустимы для текущего прототипа; необходимость отдельного хранилища проверяется по объёмам. Push-провайдер для Android выбран в D20 (FCM HTTP v1); брокер и его размещение, хранение медиа и масштабирование остаются открытыми. |
| Q07 | Порядок аварийных заданий поверх обычной очереди и права её ручного изменения. | Решено в D19: серверная сортировка по приоритету, затем FIFO по текущему назначению; ручного изменения позиции нет. |

Вопросы Q01–Q06 не препятствуют исправлению миграций, таймера назначения, серверной валидации и подготовке регрессионных проверок. Перед реализацией зависящего сценария фиксируем решение здесь с датой и обновляем связанные документы.
