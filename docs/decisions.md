# Решения и открытые вопросы

Обновлено 8 октября 2026 года. Основание: исходный PDF и уточнения владельца проекта после аудита `322c3d4`.

`Принято` задаёт направление разработки; готовность функции проверяется отдельно в [плане](implementation-plan.md) и [API](api-contract.md). Рекомендации без подтверждённого решения не становятся требованиями автоматически.

## Принятые решения

### D27 · OpenAI Vision для фото конкретной сдачи · 8 октября 2026

По поручению владельца новые проверки фото выполняются OpenAI Responses API вместо локальной CV-модели. Отправляется только выбранная пара JPEG, уже связанная с неизменяемой попыткой (последние ID `before` и `after`); текст отчёта, имена/ID работников и данные карточки в OpenAI-запрос не включаются. Сами изображения могут содержать людей или читаемый текст — это не гарантированно обезличенный материал; пользователь должен учитывать внешнюю передачу фото. Запрос ставит `store:false`, но политика хранения/обработки аккаунта OpenAI задаётся отдельно и этим параметром не подтверждается.

Ключ `OPENAI_API_KEY` хранится только в игнорируемом корневом `.env` и передаётся только `ai-review`; `AI_SERVICE_TOKEN` остаётся отдельным случайным секретом межсервисной авторизации backend → `ai-review`, это не ключ OpenAI. Без OpenAI-ключа новая проверка фото завершается ошибкой, сдача остаётся сохранённой, мастер может повторить задачу после настройки. Результат всегда рекомендация: `needs_master_review`, `score=null`, окончательное решение принимает мастер. D27 выбирает провайдера для фото, но не включает внешнюю обработку текста, не доказывает точность на реальных ремонтах и не закрывает Q02–Q06/R23–R27.

Уточнение структуры результата · 8 октября 2026: формальные проверки отчёта (`report_checks`) и видимые признаки фото (`visual_criteria`) выдаются и показываются раздельно. Неизвестные нормы/времена остаются неизвестными; словарные сопоставления явно обозначены как эвристики. Список визуальных критериев не является проверкой технической безопасности и не означает полноту R23–R27: проверка свежести/повторов, тестирование качества на размеченной выборке и отдельный состав отчёта для ролей остаются незакрытыми.

### D26 · Убрать ложные статусы заглушек, не выдавая правила за ИИ · 8 октября 2026

По поручению владельца привести текущие интерфейсы и health/integrations к фактически работающим режимам. Обычный Compose показывает локальный модуль сдачи как подключённый; внешние LLM/vision остаются выключены до Q01. Push без FCM-конфигурации обозначается «не настроено», а не «заглушка». Аналитика показывает только вычисляемые по выборке агрегаты/группировки с явным `deterministic_rules`; не добавлять вымышленные причины неисправностей, нормативы или генеративные выводы. Исторические результаты, legacy stub-провайдер и открытые ограничения Q01/Q04/Q05 сохраняются без переписывания.

### D25 · Локальная проверка новой сдачи по умолчанию, 8 октября 2026

По поручению владельца обычный Docker Compose направляет новые сдачи в существующий защищённый `ai_service` bridge v2, а не в формальную заглушку. Включённые функции — локальные правила отчёта и ограниченное CV связанных JPEG; внешний LLM/vision-провайдер не включается и данные не отправляются стороннему API. `queued_stub` остаётся только явным fallback/test-режимом. Ранее сохранённые результаты и задания сохраняют исходный provider и не перепривязываются/не пересчитываются: отсутствие frozen-контекста старой попытки не восполняем текущими данными. Оценка остаётся неизвестной, финальное решение принимает мастер. Q01 остаётся открытым для выбора внешнего семантического/vision-провайдера, а также размещения за пределами локального Compose.

### D24 · Ограниченное локальное сравнение фото попытки, 8 октября 2026

После текстового моста D23 владелец поручил продолжить подключение фото-модуля. Версия 2 передаёт только JPEG, уже связанные с неизменяемой сдачей, и повторно использует локальное сравнение дублей/оборудования; [границы и протокол](ai-attempt-bridge.md) фиксируются до реализации. Повторное использование фото после доработки сохраняется. Без утверждённого vision-провайдера устранение дефекта и время съёмки неизвестны; CV не создаёт оценку, автоматическую доработку или закрытие. Старый v1 и формальная заглушка сохраняются для совместимости. Это технический пакет, не ответы Q01–Q06 и не подтверждение готовности настоящего ИИ.

### D23 · Технический мост конкретной сдачи, 8 октября 2026

По поручению владельца подключаем существующий ИИ по [протоколу попытки](ai-attempt-bridge.md), сохраняя основной сервер владельцем прав, истории и финального решения. Контекст известных новых сдач фиксируется в их транзакции; неизвестность старого контекста или результата не заменяется текущими полями/выдуманным баллом. Опциональный `queued_service` закрепляет провайдера задачи, default `queued_stub` сохраняется. Первый пакет повторно использует текстовые правила: внешний LLM не активируется, пиксели не передаются, runtime-policy прежнего сервиса не ослабляется. Это инженерная интеграция, не ответы Q01–Q06 и не готовность реального ИИ/всего кейса.

### D22 · Интеграция накопленной ветки в main, 8 октября 2026

Владелец разрешил перенаправить существующий [PR #5](https://github.com/bshakaryan/km_case_hack/pull/5) из `feature/ai-review-jobs` в `main` и выполнить обычное слияние с сохранением коммитов после проверки актуальной базы и CI. В интеграцию входит вся накопленная цепочка `feature/postgresql-ci → feature/order-history → feature/ai-review-jobs → feature/order-versions`, а не только последние изменения версий. PR #2–#4 сверяем с вошедшими коммитами и закрываем как заменённые общей интеграцией только после подтверждённого слияния. Эта запись фиксирует разрешение и порядок, а не уже выполненный merge.

Следующие пакеты продолжаем обычными коммитами в существующей `feature/order-versions`, без новых веток и переписывания общей истории. D21, оставшийся объём и открытые вопросы Q01–Q06 сохраняются: включение проверенной разработки в `main` не означает готовность всего кейса.

### D21 · Уточнение оставшегося объёма владельцем, 8 октября 2026

Владелец исключил дальнейшую генерацию и исправление демоданных: используем существующие наборы. Аудит `65c24d2` и его ограничения сохраняются как факты; это решение не объявляет R40 прошедшим все критерии PDF. Отменённый контракт fresh-only генератора не является следующей задачей.

ИИ и аналитика не создаются заново: подключаем существующий `ai_service` к сохраняемым задачам/попыткам основного приложения и его интерфейсам, затем доводим конкретные ограничения расчётов. Очередь, права, gateway чтения/повтора и основная аналитика уже реализованы. Выбор внешнего/локального провайдера, отрицательный сценарий, интервалы и формулы Q01–Q06 не определяются этим уточнением.

Приёмка на физическом Android переносится ближе к завершению функций. Для iOS владелец подтвердил установку на настоящий iPhone: конечная цель — подписанная device-сборка, одной сборки симулятора недостаточно. Владелец сообщил об отсутствии доступа к Mac/Xcode и аккаунту Apple Developer; подготовка проекта и неподписанной device-сборки на macOS CI остаётся независимой работой, установка ждёт способа подписи. Публикация в App Store не запрошена. QR, казахский язык, голос/ассистент/прогноз, размещение и материалы сдачи остаются в плане. Технические независимые проверки выполняются по законченным пакетам; ранее успешные тяжёлые сценарии без новой причины не повторяются.

Срез реализации D09/D13 · 7 октября: сервер добавил `assigned_at` и отсчёт непринятия от текущего назначения, независимую исходную миграцию и проверяемое Alembic-обновление при старте. Для старого назначения без достоверного события используется `created_at`; полная история не реконструируется. PostgreSQL-приёмка и оставшиеся задачи этапа 2 фиксируются отдельно в плане/проверках, а не считаются закрытыми этой записью.

Срез D09/D10/D13 · ветка `feature/order-history`, 8 октября: новые назначения и сдачи сохраняются отдельными записями, решения мастера дополняют попытку без перезаписи её отчёта/ИИ. `completion.materials` остаётся накопленным расходом, материалы новой попытки — только добавочным. Снимок включает весь набор фото, доступный при сдаче; существующее разрешение повторного использования фото и лимит пять каждого вида на наряд сохраняются до решения правил свежести Q04. Для старых данных создаётся только `legacy_snapshot`, без выдуманного автора, предыдущих попыток и связей фото/расхода. Это реализация согласованных решений, а не закрытие Q01–Q06; подробности API и пределы проверки описаны отдельно.

Срез D07/D14 · `feature/ai-review-jobs`, 8 октября: отчёт и задача фиксируются общей транзакцией, обработчик получает данные конкретной попытки, а результат привязывается к ней один раз. Повторы, восстановление после перезапуска и просроченный захват задачи не должны создавать вторую оценку или менять более новую/отменённую сдачу. Основной режим — фоновая локальная заглушка, совместимый `inline_stub` явно включается для старого синхронного сценария и регрессий. Внешние AI API и отдельный `ai_service` к живым данным не подключены; Q01 сохраняется. Gateway чтения/повтора проверяет текущие права, service-token клиентам не выдаётся. Мастер принимает или возвращает работу вручную после результата; автоматическое закрытие/возврат и обход неудачной проверки не добавлены.

Срез D05/D08 · `feature/order-versions`, 8 октября: серверная версия наряда и неизменяемое подтверждение успешной команды являются основанием актуальности. Первая офлайн-команда сохраняет известную версию, следующая в цепи ссылается на предыдущую команду этого пользователя/наряда. Новый GET не перепривязывает старый ввод/ключ/медиа. Точный успешный replay проверяется после текущих прав и до нового сравнения версии; никакого второго эффекта. Переназначение тому же человеку или уход/возврат назначения не возвращают старую версию. Это техническая реализация принятых решений, без новых правил Q01–Q06. Сервер сохраняет совместимость запросов старых клиентов без заголовков, но они не защищены версией; обновлённые клиенты не отправляют новые изменения без основания. Старые локальные команды без основания сохраняются в конфликте, не получают выдуманную свежую версию. Подробности — в API/verification.

Порядок работы с ветками · последнее решение владельца 8 октября — D22: накопленная цепочка направляется в `main` через существующий PR #5 с сохранением коммитов. Прежнее решение отложить слияние отменено; дальнейшая разработка остаётся в `feature/order-versions`, без новых веток для небольших пакетов. Перед push проверяем удалённую ветку и не перезаписываем работу коллег. Фактический результат интеграции фиксируется отдельно от разрешения.

### Офлайн-состояние и устойчивые данные Android-клиента

D17 · Принято 7 октября 2026: аккаунт и ранее загруженные данные переживают отсутствие сети, отправка без сети переходит в локальную очередь.

- Сессия восстанавливается без обращения к серверу: сетевой сбой при старте не сбрасывает вход; `401` по-прежнему завершает сессию. Снимок последних данных (наряды, справочники, работники, панель, уведомления, аналитика, профиль) хранится на устройстве и открывается офлайн с отметкой времени.
- Просмотренные фотографии нарядов кэшируются на диске с ограничением объёма; очередь отправленных фото хранит байты на диске до подтверждения сервером.
- Изменяющие команды (выдача, переходы, сдача, фото, прочтение уведомления) без сети сохраняются в локальной очереди и отправляются при восстановлении связи с зависимостями: фото до — после создания наряда, фото после и сдача — после нужного статуса.
- Повторы создания, перехода, сдачи и фото защищены серверными ключами `X-Client-Command-Id` (контракт: [api-contract.md](api-contract.md)); автоматический повтор этих POST использует прежний ключ. Отметка собственного уведомления прочитанным повторно устанавливает тот же флаг и не относится к четырём POST с ключами. Локально сохранённое действие не показывается подтверждённым сервером; конфликт (`409/422/403` при синхронизации) выводится пользователю и не разрешается молчаливой перезаписью (D08).
- Хранилище — `sqflite` + `path_provider` на Android; веб-превью остаётся в памяти (`kIsWeb`), веб-панель этим решением не меняется. Технология выбрана владельцем на этапе планирования вместе с полным объёмом кэша.

D17 реализован частично. 7–8 октября отдельный прогон подтвердил дисковое восстановление после force-stop при выключенном API на Android Emulator; это не вывод из наличия кода хранения и unit-тестов. Результаты и ограничения записаны в [verification.md](verification.md). Постоянные черновики ещё не отправленного ввода, полная матрица конфликтов и системная фоновая синхронизация этим решением не объявляются готовыми.

Уточнения D17 после аудита 7 октября, в рамках согласованного исправления:

- Снимки, фото, сопоставления локальных/серверных ID и очередь должны быть изолированы по полному нормализованному адресу API (включая схему, порт и путь) и ID пользователя. Совпадение ID работников на разных серверах не разрешает переносить данные или отправлять команды.
- Изменяющий запрос допускается после успешной постоянной записи команды и медиа. Ошибка дискового хранилища не заменяется незаметным переходом в память или сообщением об офлайн-сохранении.
- `401` останавливает отправку и завершает текущую сессию; ожидающая команда сохраняет свой ключ для повторного входа в тот же аккаунт на том же сервере. Выход очищает доступный кэш своей области; оставшуюся очередь другой аккаунт не видит и не отправляет. Синхронизация выполняется последовательно; отклонённая/конфликтная предыдущая команда блокирует зависимые действия по тому же наряду.
- Старые локальные данные без доказанного сервера/пользователя не присваиваются новой области автоматически. Старые команды сохраняются изолированными и не отправляются; старые кэши не читаются. Сохранённая сессия без ID владельца требует онлайн-проверки `/auth/me` перед доступом к кэшу. Это сознательное ограничение обновления, а не обещание безопасно восстановить неизвестное происхождение данных.

Готовность каждого уточнения определяется кодом и результатом проверки, а не добавлением этого правила в реестр.

Продолжение D08/D17 в той же `feature/order-versions`: черновики выдачи и сдачи сохраняют ввод, подготовленные фото, частичный результат и исходное основание отдельно от кэша/очереди. Android использует схему v4, React — IndexedDB; новая запись на сервере не создаётся восстановлением формы. Прерванная отправка требует проверки результата, не молчаливого повторения. Другие диалоги и Flutter web-превью пока остаются в памяти. Q02 о серверной неполной попытке остаётся открытым: клиентский черновик его не закрывает.

### Ролевой доступ веба и API

D18 · Принято 8 октября 2026 по поручению владельца «Отдели роли как нужно». Веб показывает разделы согласно роли: мастер — обзор, наряды, сотрудники, аналитика, справочники для чтения и интеграции; исполнитель — личная работа и свои наряды; руководитель — обзор, наряды, сотрудники, аналитика и интеграции только для чтения; администратор — все разделы и управление справочниками. Для отчёта исполнителя сервер выдаёт только материалы и коды неисправностей из справочных данных. Список сотрудников доступен мастеру, руководителю и администратору; интеграции — тем же ролям. API аналитики для работника сохраняет только персональную выборку, используемую экраном его показателей в Flutter. Подробности и фактическая проверка — в [контракте](api-contract.md), [описании веба](web-ux.md) и [проверках](verification.md).

Уточнение владельца · 8 октября 2026: у исполнителя нет отдельной вкладки «Наряды»; назначенные ему активные и закрытые наряды остаются доступны внутри «Моя работа». Это изменение веб-навигации, а не серверного доступа к собственным нарядам.

### Действия исполнителя и понятная очередь

D19 · Принято 8 октября 2026 по поручению владельца переделать очередь и не позволять мастеру принимать наряд за рабочего. Исполнитель — единственная роль, которая принимает/отклоняет назначение, начинает, приостанавливает/продолжает и сдаёт работу; действие ограничено его назначенными нарядами. Мастер и администратор назначают/редактируют и отменяют наряды, возвращают работу или принимают результат, но не выполняют эти действия за исполнителя.

Принятие — единственное текущее задание рабочего, а не способ набирать несколько заданий разом. Если есть `accepted`, `in_progress`, `paused` или уже ожидающее задание, повторное принятие отклоняется с `409`; назначенное задание можно явно отправить кнопкой «В очередь». У очереди отдельный смысл: `queue` переводит `issued`, `rework` или `accepted` в `queued`; повтор для `queued` не меняет состояние. Рабочий может поставить в очередь несколько назначений, но одновременно принять/исполнять — только одно. Для старых записей с несколькими `accepted` API показывает верхнее задание как `accepted`, остальные как `queued` по серверному порядку; БД и прежний журнал не переписываются. Старые несколько `paused` можно продолжать по одному, но начать новую работу при паузе нельзя. Позиция рассчитывается сервером среди `accepted|queued` по приоритету `emergency → high → normal → planned`, затем по времени текущего назначения и ID. Начать можно только первое задание и только если нет другого `in_progress` или `paused`; попытка начать при занятом рабочем отклоняется с `409`, не маскируется успешным ответом «осталось в очереди». Следующий наряд автоматически не запускается — исполнитель начинает его сам. Ручного перетаскивания нет; изменение приоритета мастером/администратором пересчитывает позиции. `queue_position` вычисляется, в БД не хранится.

### FCM как провайдер push (Android)

D20 · Принято 8 октября 2026: push на Android доставляет Firebase Cloud Messaging через HTTP v1 API.

- Провайдер — FCM HTTP v1; Firebase-проект `km-case-hack` (номер `716637680468`), Android-пакет `kz.km.naryad_ai`. Android — первым; iOS/APNs в этот пакет не входят и остаются следующим шагом.
- Доставка устойчивая: `notify()` в одной транзакции с уведомлением БД создаёт запись в outbox `push_tasks`, фоновый диспетчер внутри процесса API отправляет ожидающие задания через FCM с повторами и нарастающей задержкой и отзывает недействительные токены в `device_tokens`. Это исполнение D14 (сохраняемое состояние и события после фиксации) для push. Уведомление и outbox создаются одной транзакцией; при неопределённом ответе FCM доставка может повториться.
- Учётные данные сервисного аккаунта передаются только через окружение: inline JSON в `FIREBASE_CREDENTIALS_JSON` (приоритет) либо путь к файлу в `FIREBASE_CREDENTIALS`; автоматического выбора ключа нет, доставка требует явного `PUSH_ENABLED=true` (по умолчанию `false`). Секреты в репозиторий не коммитятся. Конфигурация: `FIREBASE_PROJECT_ID` (по умолчанию `km-case-hack`), `PUSH_ENABLED`, `PUSH_DISPATCH_SECONDS`, `PUSH_MAX_ATTEMPTS`.
- Регистрация устройств — маршруты `POST /api/devices` и `POST /api/devices/unregister`; клиент ставит токен после входа/восстановления сессии и отзывает при выходе (контракт: [api-contract.md](api-contract.md)).
- Подтверждение аварийного уведомления исполнителем (полное выполнение R18, включая ответ на аварийное) в этот пакет не входит и отложено; приёмка доставки на физических устройствах остаётся отдельной проверкой.
- Решение частично закрывает **Q06**: push-провайдер для Android выбран. Брокер задач/событий и место его размещения, хранение медиа и масштабирование на несколько процессов в Q06 остаются открытыми.

Срез D04 · 8 октября: неизменяемая миграция 0007_assignment_participants фиксирует работников бригады на смене и их имена. responsible_id выбирается явно либо автоматически по прежней нагрузке; assignee_id остаётся ответственным. Переназначение заменяет права, изменение справочника их не меняет. Legacy знает только прежнего исполнителя. Участник добавляет фото с автором; переходы и общий отчёт выполняет ответственный. Очередь/занятость и существующие личные показатели основаны на assignee_id; общий результат не копируется другим участникам. Назначение/статус уведомляют состав, напоминания сроков — ответственного и мастера. Оставшиеся правила времени и личного вклада — Q04/Q05.
