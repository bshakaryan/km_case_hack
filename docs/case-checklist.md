# Полный чек-лист соответствия кейсу «НарядAI»

Дата аудита: **5 октября 2026 года**. Проверенная версия: **42fc3e4**, ветка `main`.

Источник: все 8 страниц PDF «Кейс №1. Костанайские минералы», включая схему десяти статусов на странице 3, требования разделов 1–12, демо-сценарий и состав сдачи. Проверены исходники веб-панели, сервера, модели БД, миграции, генератор данных, нативная заглушка, инфраструктура и документация. Наличие функции в README само по себе не считалось доказательством реализации.

**Вывод:** в проекте есть работающий основной цикл веб-приложения, сервер и PostgreSQL. Однако полное соответствие PDF пока не достигнуто: помимо согласованных заглушек есть недостающие функции веб-панели и ошибки расчётов/поведения сервера. Этот файл фиксирует состояние проекта, а не выполняет перечисленные доработки.

## Как читать чек-лист

- `[x] Готово` — функция найдена в коде; для ключевых сценариев есть тесты. Это не означает прохождение испытаний на производстве.
- `[ ] Частично` — есть основа, но конкретная часть требования отсутствует или работает иначе.
- `[ ] Нет` — реализация не найдена.
- `[ ] Заглушка` — демонстрационный адаптер вместо реальной функции.
- `[ ] Проверить` — реализация или предпосылки есть, но требуемый результат не измерен.
- `[ ] Условно` — пункт применим только при дополнительном условии из PDF.

**Границы заказа:** пользователь первоначально попросил полноценные веб-панель, сервер и БД, а для нативки и ИИ — заглушки. Поэтому строки «Заглушка» не являются нарушением этого заказа, но не закрывают соответствующие требования полного кейса. При этом часть ИИ-возможностей не имеет даже отдельного демонстрационного интерфейса — это отмечено отдельно.

Приоритеты взяты из PDF. В нём есть неоднозначности: например, рейтинг бригад назван MVP в §7, а в итоговом §10 указан только рейтинг исполнителей; экспорт указан в общем требовании §7, но отнесён к желательному в §10. Такие пункты сохранены, а не исключены из аудита. PDF допускает **APK или PWA**, **PDF или Excel**, а также выбор одного из рекомендованных стеков: отсутствие второго варианта само по себе не является недоработкой. Повторения между разделами оставлены для трассировки; процент готовности по числу галочек не рассчитывается.

## 14. Подтверждённые ошибки и порядок доработки веба/сервера

Эти пункты не зависят от подключения реального ИИ или нативного приложения.

### Сначала исправить данные и поведение

- [ ] **P1 — таймер после переназначения.** В [изменении наряда](../backend/app/main.py#L344) меняются исполнитель и статус, но не время текущего назначения; [монитор](../backend/app/services.py#L93) считает 3/10 минут от `created_at`. Воспроизведение на отдельной БД: наряд возрастом 20 минут переназначить новому работнику и сразу вызвать монитор — появляются два сообщения о непринятии. Нужно отдельное время назначения/принятия с сохранением исходной даты выдачи.
- [ ] **P1 — период отчёта/рейтинга.** [Отбор](../backend/app/main.py#L506) только по дате выдачи пропускает выполненные в периоде переходящие задания. Проба: созданный два дня назад и завершённый пять минут назад наряд отсутствует в отчёте за последний час, хотя `dashboard.completed` его учитывает. Нужны явные правила периода для выдачи, выполнения, закрытия и простоев.
- [ ] **P1 — отчёт по бригаде теряет индивидуальные назначения.** Новый наряд работнику из бригады сохраняется с `brigade_id=null`; фильтр бригады не находит его. Нужно согласовать семантику «наряд назначен бригаде» и «работу выполнил член бригады», сохраняя историю принадлежности.
- [ ] **P1 — двойной простой оборудования.** [Расчёт](../backend/app/services.py#L139) складывает длительности нарядов. Проба: два одновременных часовых ремонта одной единицы дают два часа простоя. Для времени недоступности оборудования нужны объединение интервалов и обрезка по периоду; трудозатраты можно считать отдельно.
- [ ] **P2 — обязательное описание на сервере.** [Схема](../backend/app/schemas.py#L20) разрешает пустое описание, несмотря на обязательность в PDF и форме. Валидация UI и API должна совпадать.
- [ ] **P2 — порядок очереди.** Нет позиции/времени постановки и операции добавления в конец; две последовательные постановки возвращаются API в обратном порядке создания. Нужна явная очередь и её отображение, а также кнопка постановки из принятого состояния.
- [ ] **P2 — согласовать определение простоя.** Счётчик панели и длительности сервиса охватывают разные статусы; плановые остановки и реальные моменты остановки/запуска не фиксируются.
