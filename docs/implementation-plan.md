# План полной реализации

Обновлено 8 октября 2026 года. Порядок определяется зависимостями, без неподтверждённых календарных сроков и оценок состава команды. Решения: [реестр](decisions.md). Состав: [требования](requirements.md). Текущее поведение: [API](api-contract.md).

## Исходная точка

На `322c3d4` есть веб-прототип, FastAPI, PostgreSQL в Compose, локальный SQLite, серверные роли, основной цикл наряда и базовые отчёты. Flutter-приложения, реального ИИ, push и офлайн-синхронизации нет. Независимо повторены 20 серверных тестов на SQLite, сборка веба и проверка типов TS-заготовки. Это не приёмка полного кейса; детали и ограничения — [verification.md](verification.md).

## Текущий приоритет после уточнения владельца

6 октября по D15 добавлен первый Flutter-сценарий на действующем API: вход → выдача → выполнение → фото/материалы → сдача → приёмка. Мобильный дизайн и границы — [mobile-ux.md](mobile-ux.md), запуск — [mobile/README.md](../mobile/README.md). Это частичное выполнение этапа 6, не готовность push, офлайна, бригадной модели или реального ИИ.

Следующее подтверждение «Делай» закреплено в D16: выполнен клиентский веб-пакет в едином стиле с Flutter. В него входят приоритеты мастера, контекстная выдача, приёмка, адаптация журнала, WebSocket reconnect, защита от ответов прежней сессии, актуализация открытой аналитики и её текущих границ. Подробности и ограничения — [web-ux.md](web-ux.md). Это частичное выполнение этапа 5: HTTP/БД не менялись, дефекты серверных метрик, назначений и миграций остаются открытыми. Факты браузерной приёмки записываются отдельно и не предполагаются по готовности кода.

8 октября по D18 добавлена матрица доступа веба: вкладки видны согласно роли, для закрытой вкладки используется доступный обзор, сервер ограничивает список сотрудников/интеграций и состав справочных данных исполнителя. Flutter обновлён для работы с ограниченным ответом и не запрашивает список сотрудников для исполнителя. Проверки этого изменения фиксируются отдельно; этап 5 в целом остаётся частичным.

8 октября по D19 права действий разделены на сервере: исполнитель принимает и выполняет свою работу, мастер/администратор не могут принимать или начинать её за него. Ручная кнопка «В очередь» убрана; очередь принятых незапущенных работ сортируется сервером по приоритету и времени текущего назначения, позиция вычисляется и отображается в клиентах. Ручной перестановки и автозапуска нет. Очередь первого уровня не требует миграции; история назначений и интервалы работы остаются задачами этапа 3.

Первый общий онлайн-сценарий подтверждён без телефона: Android Emulator принимает и выполняет наряд, веб-модуль API возвращает на доработку и закрывает повторную сдачу, Android показывает итог. Добавлены воспроизводимые связанные тесты; точные результаты и границы — [verification.md](verification.md). Физические устройства, камера/галерея, push, офлайн и iOS ещё требуют отдельной приёмки.

7 октября исправлена основа очереди D17: сервер связывает ключ с операцией и нарядом; Flutter сохраняет команду и медиа до HTTP, разделяет их по серверу/аккаунту и продолжает отправку после повторного входа. Локальные действия явно ждут подтверждения сервера. Добавлены проверяемые миграции и время текущего назначения; полный этап 2 ещё не завершён. Результаты конкретных прогонов — в [verification.md](verification.md).

7–8 октября отдельный Android-сценарий подтвердил обновление локальной схемы, восстановление защищённой сессии, кэша, четырёх команд с прежними ключами и файлов фото после force-stop при выключенном API. После возвращения того же сервера очередь отправлена без повторного отчёта/расхода, мастер закрыл наряд с оценкой 5. Это проверка настоящего Android-хранилища на эмуляторе; расширенная матрица конфликтов, физические устройства и постоянные черновики формы остаются впереди.

Порядок ближайших работ: оставшиеся дефекты основы сервера (этап 2) → согласованно развивать модель и контракт (3–4) → подключить push и завершить офлайн → ИИ и расширенная аналитика по зависимостям ниже. Проверка на физических устройствах проводится по мере готовности функций; общий онлайн-сценарий уже можно проверять автономно на Android Emulator.

## Выполненный пакет серверной основы

Общий план опубликован коммитом `b0d5853`; затем по поручениям владельца добавлены мобильный и веб-интерфейсные пакеты D15/D16. 7 октября выполнен пакет, не зависящий от выбора ИИ и правил отрицательного демо:

1. Исходная миграция стала самостоятельным снимком схемы; startup обновляет новую и распознанную существующую БД через Alembic, отклоняя несовместимую схему без изменений.
2. Добавлено время текущего назначения. Для старых записей используется достоверное последнее событие назначения текущему исполнителю/бригаде либо created_at; этот запасной вариант не восстанавливает утраченную историю.
3. На SQLite проверены переназначение, повторное назначение тому же работнику, дедупликация уведомлений, сохранность старых записей, откат миграции и повторный upgrade.
4. API и описание схемы обновлены. Полный этап 2 остаётся открытым; PostgreSQL-конкуренция этим прогоном не подтверждена.

## Последующие дефекты этапа 2 и веба

- Безопасная модель выполнения SQL и обработки фото, короткие блокировки, конкурентные тесты PostgreSQL.
- Обязательное содержательное описание в API, согласованное с формой.
- Номер наряда с гарантией уникальности и обработкой конфликта.
- Полная серверная пагинация/поиск вместо ограниченного клиентского снимка. Веб уже запрашивает до 5000 и предупреждает о достижении лимита; это не решает полноту истории.
- Проверка добавленных клиентских механизмов: открытая аналитика и текущая граница периода, WebSocket reconnect, объединение запросов обновления, игнорирование прежней сессии. Код добавлен в D16; подтверждение сценариев и производительности фиксируется в журнале испытаний.

Изменение семантики периодов, фактических простоев, очереди и бригадных рейтингов выполняется вместе с соответствующей моделью этапов 3–5, а не скрытой заменой одной формулы.

## Работа команды и проверка результата

Для каждой задачи фиксируем этап, изменяемые контракты, файлы и критерий проверки. Данные/миграции ведёт один исполнитель пакета, клиентские изменения можно делать параллельно по опубликованному контракту. Тестируем поведение: обычный цикл, отказ/доработку, потерю сети, повтор/конфликт, изоляцию ролей и обновление старой базы. Результаты привязываем к Git-версии и окружению; прошлый успешный тест не является результатом новой версии.

Технические проверки запускаются в каждом пакете. PostgreSQL-конкуренция, физические телефоны, push/ИИ и измерение времени явно остаются непроверенными, пока соответствующее испытание не проведено.
