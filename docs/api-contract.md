## Flutter-клиент · 6 октября 2026

Клиент `mobile/` использует описанные маршруты; оперативный снимок запрашивает `limit=5000`, его локальные фильтры явно сообщают о достижении лимита. Отдельный экран полного журнала использует `/orders/page` без этого общего ограничения; прочитанные страницы не заменяют оперативный снимок и очередь. Опрос каждые 5 секунд обновляет наряды, справочные данные, dashboard, уведомления и персональные/общие показатели. Исполнитель получает только справочники материалов и неисправностей, не запрашивает список сотрудников и видит аналитику только по своим нарядам. Регистрация устройств и Android push добавлены по D20; health сообщает текущие режимы AI/push, а не фиксированное значение `stub`.

Первый онлайн-пакет не повторял POST автоматически: он различал отказ 4xx и неопределённый результат сети/5xx, сохранял подтверждённый ID при частичной загрузке фото. Более поздний пакет D17 добавил очередь Android и повтор четырёх POST с тем же ключом, как описано ниже. Состояние «в очереди» не является подтверждением серверной записи. PATCH наряда в мобильном клиенте не подключён; его редактирование остаётся в веб-панели. Текущий административный каталог использует PATCH справочников отдельно от этих команд.

8 октября: транспорт Flutter допускает один повтор GET без тела, если настоящий HTTP-клиент сообщает известный обрыв соединения **до получения заголовков**. Повтор использует исходные URL/headers/options и укладывается вместе с первым запросом и чтением тела в прежний общий лимит 8 секунд. Закрытый клиент, смена токена, истёкший лимит, HTTP-отказ, потеря тела ответа и другие транспортные ошибки повтор не запускают. POST/загрузка фото и остальные изменения не получают автоматического повтора на этом уровне. Опрос остаётся каждые 5 секунд; новый GET не меняет ключи, payload, версии или зависимости сохранённых команд/форм. Методика и фактические границы замера — в [verification](verification.md).

### Частичный Android-офлайн · 7 октября 2026

Полученные данные и профиль сохраняются в локальном снимке, просмотренные фото — в файловом кэше, команды/фото отправки — в постоянной очереди `sqflite`/файлов. Синхронизация соблюдает зависимости создания, переходов, фото и сдачи. Прочтение уведомления тоже можно отложить; оно повторно устанавливает тот же флаг, но не относится к четырём маршрутам мобильной очереди с `X-Client-Command-Id`. Более поздний пакет сохраняет неотправленные формы выдачи и сдачи в Android-схеме v4 и React IndexedDB; остальные диалоги и Flutter web-превью остаются в памяти. Версии нарядов и подтверждённые зависимости команд добавлены в `feature/order-versions`, как описано ниже; массовой синхронизации и системного фонового worker нет. Результаты реальных испытаний хранилища/перезапуска/сети — отдельно в [verification.md](verification.md).

Ключи снимков/фото/сопоставлений и область очереди включают полный нормализованный адрес API и числовой ID пользователя; каждая новая команда хранит `server_url` и `owner_id` локально. Эти поля не добавляются в серверный JSON запроса. Старая локальная очередь без доказанного сервера/владельца изолируется без автоматического переноса; старые кэши не читаются. Сессия без сохранённого ID владельца сначала требует онлайн `/auth/me`.

Команда и байты медиа сохраняются до HTTP-записи; при отказе локального хранилища запрос не отправляется. `ApiException.statusCode = 507` в этом случае — внутренний сигнал мобильного клиента, а не новый ответ API. Одновременные вызовы синхронизации используют один проход; отклонённая предыдущая команда блокирует последующие по тому же наряду. `401` оставляет ключ ожидающей команды и завершает сессию; вход в ту же область продолжает отправку. Выход очищает свой кэш, сохраняя свою очередь/сопоставления для повторного входа. Восстановление после force-stop при выключенном API подтверждено на Android Emulator: [verification.md](verification.md). Фоновая доставка и полная приёмка на физических устройствах остаются впереди.

## Реализовано: общие правила

- Базовый путь `/api`; JSON, кроме загрузки фотографий и экспорта. Идентификаторы — целые числа. Время в ответах — ISO 8601 с UTC; `deadline` в запросе требует часовой пояс. Календарные даты и смены сервер трактует в `Asia/Almaty`.
- Роли: `master`, `worker`, `manager`, `admin`. Мастер и администратор управляют всеми нарядами, а не только созданными ими. `manager` читает данные и может отметить собственное уведомление прочитанным. Исполнитель видит и изменяет наряды только при `assignee_id == user.id`; принадлежность к `brigade_id` сама по себе доступа не даёт.
- Разделы и чувствительные чтения ограничены ролью. `GET /employees` и `GET /integrations` доступны `master|manager|admin`. `GET /reference` для `worker` возвращает пустые массивы `areas`, `equipment`, `employees`, `brigades`, `time_norms` и только материалы с кодами неисправностей; другим ролям возвращает полный набор. Изменять справочники может только `admin`.
- Запросы с типизированными телами запрещают неизвестные поля и обрезают крайние пробелы строк. Для справочников действуют отдельные проверки. HTTP-ошибки имеют `detail`: строка для бизнес-ошибок, массив ошибок валидации FastAPI либо объект с `code/message` для конфликтов актуальности ниже. Общего типизированного формата всех ошибок пока нет.
- Основные коды: `200` — успех; `201` — создание наряда, фото, записи справочника или регистрации устройства; `401` — отсутствующая/неверная/истёкшая сессия; `403` — права; `404` — объект не найден; `409` — недопустимое текущее состояние или конфликт записи справочника; `422` — поля/связи/правила; `413` — фото слишком большое; `429` — ограничение входа; `503` — исчерпаны попытки выделения уникального номера наряда, с `Retry-After: 1`.
- `/openapi.json` и `/docs` генерируются FastAPI. Сейчас OpenAPI описывает входные модели, но многие ответы возвращаются обычными словарями и не имеют полных `response_model`. Поэтому он пока не является полным источником схем для генерации клиента.
- Ключи идемпотентности реализованы для четырёх исходных POST, ручного повтора ИИ и PATCH наряда. Версия наряда защищает обновлённые клиенты от устаревшей записи; точный успешный replay не исполняет действие снова. Сохраняемые задания есть для проверок сдачи и Android push; журнал поддерживает постраничные курсоры. Массовая синхронизация и задания сводок остаются впереди. Клиент не должен автоматически повторять неизвестно завершившуюся запись без такого ключа как безопасную операцию.

## Реализовано: вход и справочники

| Метод и путь | Запрос и ответ |
|---|---|
| `GET /health` | Публично: `{status:"ok", database:"connected", ai:"ai_service"|"queued_stub"|"inline_stub", native:"fcm"|"disabled"}`. AI отражает `AI_REVIEW_MODE`; `native` становится `fcm` только при рабочей конфигурации отправителя, иначе `disabled`. Также доступен без префикса по `/health`. |
| `POST /auth/login` | `{login, pin}` → `{token, user:Employee}`. `login`: 1–80 символов, `pin`: 4–32. Сессия на 12 часов; не более 10 попыток за минуту для пары IP+login в памяти процесса. |
| `GET /auth/me` | `Employee`. Для всех защищённых HTTP-маршрутов нужен `Authorization: Bearer <token>`. |
| `POST /auth/logout` | Отзывает текущую сессию → `{ok:true}`. |
| `GET /reference` | Для `master|manager|admin`: `{areas, equipment, employees, brigades, fault_codes, materials, time_norms}`. Для `worker` все массивы, кроме `fault_codes` и `materials`, пусты. |
| `POST /reference/{collection}` | Только `admin`. Создаёт запись, возвращает её, HTTP `201`. |
| `PATCH /reference/{collection}/{id}` | Только `admin`. Изменяет переданные поля, возвращает запись. Удаления нет. |
| `GET /employees` | Только `master|manager|admin`. Работники: `Employee` + `{status, current_order, queue_count, rating, completed_count}`. |

`Employee = {id, name, login, role, specialty, grade, brigade_id:int|null, on_shift:bool}`. PIN и его хеш не возвращаются. Демоданные: `master`, `master2`, `worker`, `worker2`…`worker15`, `manager`, `admin`; PIN `1234` — только для демосреды.

Объекты справочников:

- `areas`, `brigades`: `{id, name}`.
- `equipment`: `{id, name, inventory_number, area_id, type, criticality}`.
- `employees`: `Employee`; при создании обязателен `pin`, при обновлении необязателен. Административный PIN: 4–12 цифр; `grade`: 0–8; `on_shift`: boolean; `brigade_id` допускает `null`.
- `fault_codes`: `{id, code, name}`; `materials`: `{id, name, unit}`; `time_norms`: `{id, name, hours}`, `0 < hours <= 1000`.

В POST справочника обязательны `name`; дополнительно для оборудования — `inventory_number, area_id, type`, для работника — `login, role, pin`, для кода — `code`, для материала — `unit`, для норматива — `hours`. Остальные поля используют серверные значения по умолчанию. PATCH должен быть непустым; неизвестные поля запрещены, `id` не изменяется. Строковые поля непустые, длины ограничены колонками моделей; связи проверяются.

Для оборудования пределы строк: `name` — 120, `inventory_number` и `type` — 80, `criticality` — 40 символов. Инвентарный номер уникален; `area_id` — целое число существующего участка, boolean/null недопустимы. `criticality` — свободная непустая строка с серверным значением по умолчанию `medium`, не новый enum. Для материала `name` — до 180, `unit` — до 30 символов; название и единица не уникальны, единицы не ограничены списком. Наличие материала не означает складской остаток или утверждённую норму расхода.

### Flutter: каталог администратора · текущий пакет 8 октября

Во Flutter подключены просмотр/поиск, создание и изменение оборудования и материалов через существующие `/reference` POST/PATCH. Участки используются только для выбора; доступ к редактору требует именно `admin`, не общего `isMaster`. Нет DELETE, редактирования сотрудников/ролей/бригад/норм или новых серверных маршрутов/схем. PATCH отправляет только изменённые поля. Сервер блокирует текущую запись на время изменения, но у справочников нет версии/CAS или подтверждения `X-Client-Command-Id`: более поздний PATCH может заменить переданные поля, а `409` коллизии инвентарного номера не означает проверку устаревшей формы.

Запись только онлайн, вне очереди нарядов и без автоматического повтора или перехода по HTTP-редиректу. Полный проверенный ответ `201` для POST или `200` для PATCH подтверждает сохранение; PATCH-ответ должен содержать запрошенный ID. Известные ошибки полей/записи 4xx оставляют редактируемый ввод; смена прав/сессии обрабатывается отдельно ниже. Обрыв/таймаут, HTTP `408`, `5xx`, перенаправление `3xx` или некорректный успешный ответ оставляют операцию с неизвестным исходом и блокируют её повтор даже после GET или закрытия/повторного открытия редактора. Поля этой операции удерживаются только в памяти текущей сессии, постоянного черновика справочника нет. Совпавшая запись после GET, особенно материал без уникального ключа, не доказывает исход первоначального POST/PATCH.

Подтверждённое сохранение, обновление списка и запись best-effort локального снимка — разные результаты: ошибка дальнейшего GET не возвращает форму создания в состояние повторной отправки, ошибка снимка не отменяет серверный ACK и не подтверждает дисковую сохранность. Общий write lease исключает параллельную отправку/восстановление очереди; session/API/owner/token epoch/role ограничивают поздние результаты. `401` завершает текущую сессию; полученный `403` закрывает защищённые представления и блокирует каталог до нового входа. Смена справочников не заменяет основание, payload, ключи или медиа прежних нарядов/черновиков. Факты проверки текущего пакета — в [verification.md](verification.md); наличие кода не подтверждает испытание на телефоне.

Статус работника: `free|busy|queued|off_shift`; `current_order` — номер наряда в `in_progress` или `paused`, иначе `null`. `queue_count` считает только принятые задания, ожидающие начала (`accepted|queued`). Очередь сортируется по приоритету `emergency → high → normal → planned`, затем по времени текущего назначения и ID. В исходной реализации рейтинг здесь считается по всем имеющимся нарядам, без действующего ограничения последними 90 днями.

## Реализовано: чтение нарядов

`GET /orders` → массив `Order`, сортировка `created_at DESC`. Параметры: `area_id, equipment_id, assignee_id, brigade_id, priority, status, search, from_date, to_date, limit`. `limit` по умолчанию 1000, диапазон 1–5000; `offset`, курсора и общего числа записей нет. `search` до 200 символов ищет подстроку в номере, заголовке и описании. Оперативный снимок клиентов запрашивает `limit=5000`; его локальные группы/поиск ограничены полученным набором, при достижении лимита показывается предупреждение. Полный журнал и история ремонтов используют отдельный маршрут ниже.

`from_date`/`to_date` фильтруют **дату создания**, включая границы. При `YYYY-MM-DD` берутся начало/конец дня в `Asia/Almaty`; также принимается ISO 8601. Обратный период даёт `422`. Для работника дополнительно применяется доступ по ответственному или участнику последнего подтверждённого назначения; параметр assignee_id по-прежнему фильтрует ответственного, не всех участников.

### Условное чтение оперативного массива

`GET /orders` проверяет действующую сессию, одну из четырёх разрешённых ролей, фильтры и текущую видимость D04 при каждом запросе, затем заново вычисляет весь ответ. `200` содержит прежний массив и сильный ASCII `ETag`. Валидатор связан с сессией, ролью, пользователем, нормализованными параметрами и точными JSON-байтами ответа, включая просрочку, очередь, имена и участников. Это не номер версии наряда и не серверный кэш SQL.

Совпадающий `If-None-Match` возвращает `304` без тела. Для чтения поддержаны слабое сравнение `W/`, список тегов, повторные строки заголовка и отдельный `*`; неверный или суммарно превышающий 4096 символов заголовок игнорируется с обычным `200`. На `200` и `304` передаются `ETag`, `Cache-Control: private, no-cache`, `Vary: Authorization`; CORS разрешает `If-None-Match` и открывает `ETag`. Ошибки авторизации, прав, фильтров или построения ответа сохраняются даже с `*`, без успешного валидатора. Без условия старые клиенты получают прежний `200`.

Flutter использует этот протокол только для `/orders?limit=5000`, React — для GET `/orders` с полным фактическим запросом. Сохранённое JSON-тело живёт в памяти клиента и изолировано по адресу API, авторизации и эпохе сессии; каждому вызывающему возвращается новая копия. Вход, выход, смена токена, включая A → B → A, и закрытие мобильного API сбрасывают область. Поздний ответ не восстанавливает старый кэш. React запрашивает `cache: no-store`, чтобы его приватный кэш не подменялся HTTP-кэшем браузера.

Клиент принимает `304` только при пустом теле, совпадающем теге и доступной соответствующей копии. Иначе показывает ошибку `304`; дополнительного скрытого запроса или подстановки данных при `401/403/404/5xx`, сетевой ошибке и неверном JSON нет. Следующий обычный опрос может заново получить `200`. Внутренний клиентский `409` с `code: read_context_changed` отменяет чтение `/orders` из сменившейся сессии; это не HTTP-ответ сервера и не конфликт версии записи. Ошибка старого `401` не завершает новый вход.

Опрос сохраняет период 5 секунд, полный состав и прежний лимит. Журнал `/orders/page`, детали, черновики и очередь команд не используют этот валидатор; исходные ключи, payload, версии и предшественники не меняются по GET. Миграций, TTL, фоновой доставки и сокращения SQL этим протоколом не добавлено.

```text
  id, number, source:live|legacy_snapshot,
  assignee_id, assignee_name, brigade_id:int|null, brigade_name:string|null,
  assigned_by_id:int|null, assigned_by_name:string|null, assigned_at,
  ended_at:datetime|null,
  participants:[Participant], participants_source:live|legacy_snapshot
}
SubmissionAttempt = {
  id, number, source:live|legacy_snapshot, assignment_id:int|null,
  submitted_at:datetime|null, author_id:int|null, author_name:string|null,
  assessment_id:int|null, completion:{work_done, fault_code_id, comment, materials},
  ai_review:object|null, ai_job:AIReviewJob|null, photos:[Photo],
  materials:[{id, material_id, name, unit, quantity, author_id, author_name, created_at}],
  decisions:[{id, actor_id, actor_name, action:close|rework,
    score:number|null, comment, created_at}]
}
```

`number` — последовательный номер внутри наряда; ID попытки стабилен. История отсортирована по номеру от ранних к поздним. `completion.materials` **попытки live** содержит только дополнительный расход этой сдачи с названиями/единицами на момент сдачи; `materials` связывает его с фактическими списаниями. `photos` фиксирует все фотографии, доступные при сдаче, и не пополняется последующими загрузками. Фото может входить в несколько попыток; обязательность нового фото после доработки не утверждена. Снимок `ai_review` не меняется при решении мастера: его оценка/причина дописываются в `decisions`. Верхние `OrderDetail.completion`/`ai_review` сохраняют прежнее текущее представление и накопленный расход.

При явном назначении, включая повторное назначение тому же человеку, создаётся запись истории и закрывается предыдущее назначение. Правка текста/срока/приоритета этого не делает. При закрытии или отмене завершается текущее назначение. История не предоставляет прежним участникам новых прав: чтение карточки и фото проверяет **последнее** назначение, в том числе завершённое у закрытого/отменённого наряда. Поля participants хранят имена на момент назначения; старый legacy_snapshot знает только исполнителя и имя на момент миграции, а не полный прошлый состав. Если история не соответствует текущим полям назначения, безопасный fallback — только сохранённый assignee_id.

Миграция `0004_order_history` и демо-seed создают `legacy_snapshot` только из текущих сохранённых полей. У старого отчёта неизвестны автор, назначение и конкретная оценка; связи с фото/списаниями пусты. Если `completed_at` отсутствует, `submitted_at=null`. Его `completion.materials` — сохранённый накопленный расход, **не расход доказанной отдельной попытки**. `assigned_by_id` старого назначения и достоверная граница его окончания неизвестны. Это один снимок, не восстановление всех прежних сдач и назначений; старый аудит/фото/списания сохраняются.

`priority = emergency|high|normal|planned`; `work_type = planned|unplanned`. Статусы перечислены в таблице переходов. Просрочка — вычисляемый флаг при истёкшем `deadline`, исключающий `completed`, `ai_review`, `closed`, `cancelled`.

`queue_position` вычисляется для принятых, но ещё не начатых нарядов (`accepted|queued`) и равен `null` в остальных состояниях. Это очередь ответственного, включая его бригадные наряды; поле не хранится в БД и пересчитывается при изменении назначения/приоритета/статуса.

`assigned_at` — непустой ISO 8601 UTC-момент текущего назначения в списке и карточке. У нового наряда он равен `created_at`; назначение/переназначение меняет только `assigned_at`, исходное время создания сохраняется. Для старых записей миграция `0003_assignment_time` берёт последнее достоверное `edit → issued` с полем назначения в начале старого аудита, допустимым исходным статусом, совпадающей текущей целью и временем не раньше создания. Если подтвердить это нельзя, используется `created_at`. Эта совместимость не означает полной восстановленной истории назначений.

Приёмка, возврат и отмена остаются у мастера/администратора.

Другие нарушения ограничений не маскируются этой обработкой. При бригадном назначении сервер сохраняет состав работников выбранной бригады на смене и `brigade_id`. ## Реализовано: идемпотентные повторы команд · 7 октября 2026

Шесть изменяющих маршрутов принимают необязательный `X-Client-Command-Id` — устойчивый идентификатор команды (8–64 символа из `[A-Za-z0-9._:-]`, например UUID): четыре исходных `POST /orders`, `POST /orders/{id}/transition`, `POST /orders/{id}/complete`, `POST /orders/{id}/photos`, а также `POST /orders/{id}/submissions/{attempt_id}/ai-review/retry` (`ai_review_retry`) и `PATCH /orders/{id}` (`order_update`). Некорректное значение — `422`. Заголовок необязателен; мобильная постоянная очередь по-прежнему обслуживает четыре исходных POST, ручной повтор ИИ выполняется онлайн, PATCH остаётся веб-сценарием.

- Ключ действует в пределах вошедшего пользователя: пара `employee_id + client_id` уникальна.
- Повтор с тем же ключом, операцией, целевым нарядом, содержанием и основанием актуальности возвращает сохранённый статус и тело первоначального ответа. Отпечаток v2 остаётся для запросов без основания; v3 дополнительно включает ожидаемую версию либо ключ предыдущей команды. JSON нормализуется; для фото учитываются вид, ID наряда и `sha256` исходных байтов, для повтора ИИ — также ID попытки. Изменение версии или предшественника под уже использованным ключом не является повтором и получает `409`.
- Тот же ключ с другим содержанием, видом операции или целевым нарядом — `409` с пояснением; действие не выполняется повторно. Ключ остаётся в области пользователя, а не становится отдельным разрешением на доступ.
- Авторизация роли и доступа к целевому наряду выполняется до возврата сохранённого ответа. Проверка повторного ключа идёт **до** остальной бизнес-валидации: уже принятая команда может вернуть прежний результат, даже если её содержание сейчас не прошло бы проверку (например, истёкший срок); это не обход отзыва доступа или сессии.
- Бизнес-работа, запись ключа и ответ фиксируются одной транзакцией: отказ валидации откатывает и заявку ключа, поэтому повтор после ошибки возможен; сбой между применением команды и сохранением ответа не оставляет «полукоманды».
- Конфликт уже занятого ключа возвращает `409`. Обработка конкурентного захвата опирается на уникальность пары в БД. Одновременные создание/сдача с одинаковым ключом проверены на PostgreSQL 17: единственный эффект и последующий сохранённый ответ; детали и границы — [verification.md](verification.md). Версии устаревших команд и нагрузочная приёмка остаются отдельными задачами.
- Срок хранения ключей сейчас не ограничен; правило очистки остаётся отдельной частью этапа 4 плана.
- Совместимость с уже сохранёнными результатами не требует изменения схемы. Для старого отпечатка всегда проверяется совпадение операции; для `transition`/`complete` дополнительно требуется доказанный целевой наряд: поле `id` сохранённого ответа — именно целое число нужного наряда. Неоднозначная старая запись получает `409`, не исполняется заново. Прежний отпечаток фото уже включал целевой наряд. Старые записи команд не переписываются автоматически.

Клиент хранит ключ вместе с командой в локальной очереди и переиспользует его при любой повторной отправке, в том числе после перезапуска приложения.

## Реализовано: версии нарядов и актуальность команд · feature/order-versions

`version` — положительный серверный номер изменений агрегата наряда, в списке и карточке. Миграция `0006_order_versions` начинает прежние наряды с `1`, не выдумывая число прошлых изменений. Дальше версия растёт при изменении наряда, назначении, переходе, сдаче, фото, решении мастера и изменениях публичного состояния задачи проверки. Номер не равен времени или ID назначения; вычисляемые `is_overdue`/`queue_position`, изменения справочников и отдельные уведомления не дают новую версию. Безрезультатный отказ, replay и переход `queue` без изменения не увеличивают её.

Обновлённые клиенты передают для существующего наряда одно основание:

- `X-Expected-Order-Version: <целое 1–2147483647>` — версия, на которой было подготовлено действие; десятичная запись без ведущих нулей. Применимо к PATCH, переходу, сдаче, загрузке фото и ручному повтору ИИ.
- `X-Previous-Client-Command-Id: <ключ>` — альтернатива для следующей команды мобильной цепочки. Требует собственного `X-Client-Command-Id`. Сервер находит успешно зафиксированную предыдущую команду **этого пользователя и этого наряда** и сравнивает текущую версию с её подтверждённой версией. Создание без основания тоже формирует подтверждение для зависимых команд.

Оба заголовка одновременно или неверный формат дают `422`. После проверки роли/текущего доступа сервер сначала возвращает точный сохранённый успешный replay; только новое выполнение проверяет основание под блокировкой наряда. Подтверждение команды (`client_commands.order_id/order_version`) фиксируется вместе с результатом, не обновляется после ИИ или чужих действий. Старые подтверждения остаются `null`, их версия не восстанавливается из текущей карточки. Фото POST добавляет `order_version` к ответу; чтение исторических фото не получает текущую версию. Gateway чтения/повтора ИИ также возвращает `order_version`.

При несовпадении версии: `409`, `detail={code:"order_version_conflict", message, expected_version, current_version}`. При отсутствии подходящего успешного подтверждения предшественника: `409`, `detail={code:"order_precondition_unavailable", message}`. Чужая команда не раскрывает автора, содержимое или наряд. Ошибки доступа сохраняют прежние `401/403/404`. Другие бизнес-ошибки пока не имеют общего типизированного формата.

Основание хранится до первой HTTP-отправки вместе с ключом, телом и медиа; повтор после неизвестного исхода не заменяет его свежим GET. Последующая команда цепочки использует подтверждение предыдущей, поэтому собственные офлайн-переходы не блокируют друг друга, а чужое изменение между ними останавливает цепь. Повтор сдачи может вернуть прежний pending-ответ после готового ИИ: это ожидаемый replay, карточка обновляется отдельно, подтверждение не переписывается.

Flutter-хранилище v3 сохраняет основание. Старые команды изменения наряда без него изолируются как конфликт с сохранением текста/фото/ключа; автоматического назначения свежей версии нет. `mark_read` не относится к версии наряда. Для конфликта актуальности повтор со свежей версией под старым ключом запрещён: пользователь просматривает текущий доступный наряд и начинает новое действие явно. Удаление локальной цепи не отменяет уже сохранённый сервером эффект. Черновики выдачи и сдачи сохраняются локально отдельно от очереди; открытая и восстановленная форма сохраняет исходное основание, фоновые GET его не заменяют. Подтверждённое собственное фото может продвинуть основание формы через своё подтверждение.

Совместимость ограничена: сервер всё ещё принимает запросы прежних клиентов без этих заголовков с прежними правами/статусами, **они не получают защиты версии**. Новые React/Flutter передают основание; старый кэш без `version` не разрешает новую запись без обновления. Это не массовый sync и не полная приёмка физических устройств. Постоянные черновики основных форм описаны ниже; другие диалоги пока не сохраняются.

## Реализовано: разбор сохранённых мобильных команд

Клиентский пакет после 0dbb5cb в той же feature/order-versions/PR #5. HTTP-протокол, серверные права и локальная схема v4 не меняются. Фактические результаты и пределы проверки — в [verification.md](verification.md).

- Просмотр очереди читает сохранённые текст, материалы, основание и доступные подготовленные фото только текущего аккаунта/API. Смена сессии/токена/роли прекращает прежний просмотр. Копирование переносит текст в системный буфер по отдельному действию пользователя; просмотра достаточно для разбора, он ничего не отправляет на сервер.
- Статус наряда из кэша явно отделяется от сохранённой команды и не считается свежим ответом сервера. GET не заменяет исходные key/version/previous_command_id и не разрешает повтор неизвестного результата. Отсутствующее или нечитаемое медиа показывается как ограничение сохранённой копии, не стирает отчёт.
- Повтор означает подтверждённую локальную постановку той же команды в pending, не успешное серверное выполнение. Действующая canRetry-политика сохраняется: конфликт версии/отсутствующее основание нельзя исправить автоматическим повтором; 403 может повториться с тем же основанием после восстановления прав, сервер проверяет их заново.
- Удаление требует явного подтверждения просмотренной цепочки. Изменившийся набор или снимок команды требует повторного просмотра; активная отправка/запись блокирует разбор с изменением данных. Выбранные записи и относящиеся к удаляемой локальной выдаче сопоставления ID удаляются атомарно; другие области, наряды и черновики сохраняются. Удаление не отменяет действие, уже принятое сервером.
- Ошибка до commit сохраняет очередь и медиа и не объявляется успехом. Очистка файлов после commit отделена от результата удаления записей: её сбой даёт предупреждение о сохранённых остаточных файлах. Новые операции не смешиваются с sync/enqueue; поздний результат прежней сессии не обновляет интерфейс новой.
- Блокировка активной записи отделена от экранного saving и переживает смену сессии. Повторный вход ждёт завершения прежней отправки перед восстановлением running-команд; неизвестный ответ сохраняет прежний ключ/основание, а не превращается в разрешение новой команды.

## Реализовано: локальные черновики выдачи и сдачи · продолжение PR #5

Это клиентское хранение до отправки; новых HTTP-маршрутов или серверной миграции нет. Android использует отдельную таблицу `form_drafts` локальной схемы v4, React — IndexedDB `naryad-form-drafts`. Сжатые фото входят в запись: base64 в Android JSON, File/Blob в браузере. Черновик отделён от кэша, очереди команд и серверного подтверждения. Flutter web-превью остаётся в памяти.

- Область включает полный адрес API, ID пользователя, вид формы и ID наряда (либо `new` для выдачи). Для каждой области одна форма; контекстная выдача не создаёт второй независимый черновик. Выход сохраняет черновики владельца, но другой аккаунт/API их не открывает. Данные не синхронизируются между устройствами; удаление приложения/данных браузера их удаляет.
- Сохраняются поля, шаг выдачи, выборы, исходные количества материалов, подготовленные фото и их состояния, уже созданный наряд, основание версии/предыдущей команды. Восстановление не назначает свежую версию по GET; собственное подтверждённое фото продвигает основание существующим механизмом.
- Записи сериализованы, сообщение о сохранении появляется после подтверждения локального хранилища. Ошибка чтения/записи видна и блокирует новую отправку. Повреждённая запись не заменяется пустым черновиком. В браузере ревизия записи защищает от перезаписи из второй вкладки; в Flutter старый дескриптор формы прекращает работу после смены сессии/открытия другой формы той же области.
- Перед каждым изменяющим запросом форма дожидается записи маркера отправки. После прерывания его результат считается неизвестным, ввод и фото остаются, повтор из формы заблокирован. Это консервативная защита: даже остановка до HTTP может потребовать ручной проверки. В Android уже переданная команда продолжает существующую очередь с прежним ключом; черновик не создаёт её заново. React не имеет постоянной очереди HTTP-команд.
- Удаление черновика явно отделено от закрытия формы и требует предупреждения при неизвестном/частичном результате. Оно не отменяет серверный наряд, сдачу, расход или мобильную очередь. Подтверждённая/переданная в очередь сдача освобождает черновик; частичная выдача хранит ID и состояния фото до завершения.

Это две основные формы, не постоянное хранение каждого диалога и не завершение этапа 7. Заполненные Android v1/v2/v3 → v4 и восстановление основных черновиков после force-stop подтверждены отдельным эмуляторным прогоном в verification; unit-тесты с MemoryLocalStore его не подменяют. Расширенные сетевые конфликты, остановка посреди активной записи/HTTP и физические устройства остаются отдельной приёмкой.

## Реализовано: полная матрица переходов

`POST /orders/{id}/transition` с `{action, reason?, comment?, score?}` → `OrderDetail`. `reason/comment` до 3000 символов; по умолчанию пустые. `score` допускает дробное число 1–5 или `null`; при `close` число обязательно. Недопустимый исходный статус — `409`.

| Действие | Исходные статусы | Новый статус | Дополнительное правило |
|---|---|---|---|
| `accept` | `issued, rework` | `accepted` | Только ответственный `worker`; `409`, если у него уже есть принятое, выполняющееся, приостановленное или ожидающее задание |
| `queue` | `issued, rework, accepted` | `queued` | Только ответственный `worker`; явная постановка; повтор для `queued` без изменения |
| `reject` | `issued, accepted, queued` | `rejected` | Только ответственный `worker`; непустая `reason` |
| `start` | `accepted, queued` | `in_progress` | Только ответственный `worker` на смене; `409`, если другой наряд `in_progress|paused` или если это не позиция 1 |
| `pause` | `in_progress` | `paused` | Только ответственный `worker`; непустая `reason` |
| `resume` | `paused` | `in_progress` | Только ответственный `worker`, на смене и без другого `in_progress` |
| `close` | `ai_review` | `closed` | Только `master/admin`, обязательна `score` |
| `rework` | `ai_review` | `rework` | Только `master/admin`, непустая `reason` |
| `cancel` | `issued, accepted, queued, rejected, in_progress, paused, completed, ai_review, rework` | `cancelled` | Только `master/admin`, непустая `reason` |

Действия исполнителя доступны только назначенному работнику. Мастер/администратор не могут принять, начать, приостановить, отклонить или сдать работу за исполнителя; они создают/переназначают/отменяют наряды и принимают результат. `accepted` — единственное принятое задание рабочего; `queued` — отдельное ожидание, куда дополнительные назначения помещает сам рабочий действием `queue`. Оба статуса участвуют в позиции очереди. Для прежних записей, где принято несколько заданий, ответ API нормализует все, кроме первого по позиции и только если нет текущей работы, в `queued`; данные и журнал БД не меняются. Принять новое задание нельзя, пока есть другое `accepted|queued|in_progress|paused`; начать нельзя, пока другое задание `in_progress|paused`. Нарушение возвращает `409`, состояние очереди не меняется. Старое приостановленное задание можно продолжить, если нет другого `in_progress`, даже если есть ещё одна старая пауза; новый старт при чужой паузе запрещён. Начало следующего наряда не запускается автоматически: после освобождения исполнитель открывает позицию 1 и начинает её. `rejected` не терминальный: возможны отмена или переназначение через PATCH. `closed/cancelled` терминальные. `started_at` записывается один раз, интервалы работы/пауз отдельно не хранятся. При `rework` очищаются `completed_at` и `score`; затем исполнитель должен принять или явно поставить доработку в очередь.

## Реализовано: сдача, фотографии и материалы

`POST /orders/{id}/complete` → `OrderDetail`; только ответственный `worker`, только `in_progress`:

```text
{work_done, fault_code_id, materials?:[{material_id, quantity}], comment?}
```

`work_done`: 10–5000 символов; существующий `fault_code_id`; `materials` по умолчанию `[]`, до 100 разных материалов, без повторов идентификаторов; количество конечное и `0 < quantity <= 1000000`. `comment` до 3000 символов, по умолчанию `""`.

Для внепланового наряда требуется хотя бы одно ранее загруженное фото `after`, иначе `422`. Стандартный Docker Compose использует `AI_REVIEW_MODE=queued_service`: в одной транзакции сохраняются попытка, добавочный расход, связи фото и задача локального модуля. HTTP `200` подтверждает сдачу со статусом `completed`, `ai_review=null` и задачей `pending`; результат появляется позже. Сдача с тем же ключом возвращает **точно этот прежний ответ**, даже если обработчик уже закончил; клиент перечитывает карточку. Фоновый результат для актуальной попытки переводит наряд в `ai_review`. Мастер принимает его вручную; автоматического закрытия/возврата нет.

`queued_stub` остаётся только явным compatibility/test fallback; он проверяет заполненность и наличие пары типов фото и не анализирует изображения. `inline_stub` — явный прежний синхронный сценарий. Оба режима возвращают `is_stub:true`; неизвестный режим останавливает запуск. `queued_service` обрабатывает новые попытки локальными текстовыми правилами и ограниченным CV связанных JPEG; внешний LLM/vision не включается. Результаты `ai_service` являются рекомендацией, v2 не задаёт численный балл, окончательное решение остаётся у мастера. Задания и результаты старого provider не перепривязываются при смене конфигурации.

**Повторная сдача после доработки содержит только дополнительный расход материалов.** Сервер добавляет новые списания и суммирует их с предыдущими; передача прежнего общего количества удвоит расход. Верхние `completion.work_done`, `fault_code_id`, `comment` заменяются; `submission_attempts` сохраняет отдельный неизменяемый отчёт каждой новой сдачи, её фото, расход и оценку. Повтор с тем же `X-Client-Command-Id` возвращает прежний ответ и не создаёт вторую попытку/списание; без ключа автоматический повтор по-прежнему небезопасен.

`POST /orders/{id}/photos`: multipart `file`, `kind=before|after` → объект фото, HTTP `201`. Роли `worker|master|admin`; работнику нужен доступ по текущему подтверждённому составу назначения. Запрещено для `ai_review|closed|cancelled`. Мобильная карточка поддерживает также completed по существующему правилу сервера; React сохраняет более строгий запрет добавления в completed. До 5 фото каждого типа **на наряд**, не на попытку; максимум 10 МиБ входного файла. Pillow проверяет содержимое, применяет EXIF-поворот, уменьшает до 1920×1920 и сохраняет JPEG quality 82 в БД. Невалидное изображение — `422`, превышение размера — `413`.

Чтение и сжатие файла выполняются без блокировки строки наряда. После подготовки сервер повторно проверяет действующую сессию, роль, назначение и текущее состояние под блокировкой перед записью. Переназначение или выход во время обработки не дают сохранить фото с прежними правами. Ключ повтора по-прежнему использует отпечаток исходного файла, а не сжатого JPEG.

`GET /photos/{id}` → `image/jpeg` с Bearer-авторизацией и проверкой доступа к наряду, `Cache-Control: private, no-store`. `url` в объекте фото — `/api/photos/{id}`; это не публичная ссылка. Веб получает Blob через авторизованный запрос. Удаления/замены фото нет. Новая сдача сохраняет связи с доступными фото, но прежние исторические связи не реконструируются.

## Реализовано: задачи проверки сдачи · feature/ai-review-jobs

```text
AIReviewJob = {
  id, attempt_id, status:pending|running|succeeded|failed|superseded,
  provider:"stub"|"ai_service", attempts, max_attempts, next_attempt_at,
  lease_expires_at:datetime|null, last_error_code:string|null,
  created_at, finished_at:datetime|null, retry_allowed:bool
}
```

В карточке `ai_review_job` относится к последней попытке; `submission_attempts[].ai_job` — к соответствующей исторической. Старый API/кэш может не содержать этих полей; отсутствие не означает сбой. Миграция не создаёт задания для прежних попыток. После новой сдачи снимок оценки и `assessment_id` сначала `null`, успешный результат привязывается **однократно**; отчёт, списания и набор фото не изменяются. Оценка мастера по-прежнему дописывается решением, не заменяет снимок результата.

- `GET /orders/{id}/submissions/{attempt_id}/ai-review` → `{attempt_id, order_version, ai_review:object|null, job:AIReviewJob|null}`. Авторизованное чтение с текущими правами на наряд; чужая попытка другого наряда — `404`, недоступный работнику наряд — `403`. Секретный маркер захвата и service-token не возвращаются.
- `POST /orders/{id}/submissions/{attempt_id}/ai-review/retry` без обязательных полей (пустое тело или `{}`) → такой же объект. Только `master|admin`, последняя попытка со статусом наряда `completed`, задача `failed`, результата ещё нет; иначе `409`. Возобновляет ту же задачу, сбрасывает счётчик **текущего цикла** попыток, записывает автора в аудит. При наличии ключа повтор возвращает прежний ответ без второго эффекта. Клиенты выполняют действие явно онлайн, сервер не закрывает наряд при неудаче проверки.

Обработчик в процессе API делает паузу 1 с между проходами. Захват действует 30 с, максимум три попытки в одном цикле; задержка после ошибки — `min(2^attempts, 60)` с. Истёкший захват можно восстановить после перезапуска, но его прежний обработчик уже не может применить ответ. Данные адаптера берутся только из отчёта и фото-связей этой попытки. Во время вызова адаптера транзакция закрыта. При записи сервер повторно проверяет маркер/срок, последнюю попытку, назначение и `completed`; устаревшая задача становится `superseded` без новой оценки, смены статуса или уведомления о приёмке.

Результат проверяет допустимый вердикт `passed|needs_attention|needs_rework`, конечную оценку 1–5 либо неизвестную `null`, непустое объяснение до 2000 символов и фактическое происхождение; модель не может задать оценку мастера. Для `stub` сохраняется прежний обязательный численный балл и `is_stub=true`. Для `ai_service` согласованные `source_verdict`, `llm_used`, `is_recommendation=true`, `bridge_version=1|2` и `input_sha256` проверяются вместе с основной рекомендацией; `needs_master_review` даёт `needs_attention` и `score=null`. v2 требует ограниченный `photo_check` по связанным ID: выбранная пара, дубли внутри попытки, неизвестные время съёмки/ремонт и непроверенная общая история. Без vision v2 всегда требует мастера и не создаёт численную оценку. Неизвестное не становится нулём или оценкой мастера. Ошибки сохраняются только фиксированными кодами (`invalid_result`, `provider_error`, `attempt_limit`), без исходного исключения/текста отчёта/ключей. Сбой не теряет сдачу; окончательный `failed` показывает мастеру возможность повтора. Принятие без результата не добавлено.

В стандартном Docker Compose `AI_REVIEW_MODE=queued_service` связывает новые задачи с отдельным endpoint существующего ИИ-модуля; `queued_stub`/`inline_stub` сохраняются как явные compatibility/test modes. Прямой запуск backend без переменной пока сохраняет `queued_stub` для прежних тестовых сценариев. Миграция `0008_ai_attempt_input` допускает неизвестную оценку и добавляет внутренний nullable снимок контекста попытки, который не выдаётся в пользовательском API; старые данные остаются без выдуманного контекста. Фото-пакет не требует новой миграции. Адрес/токен настраиваются только на сервере; Compose передаёт запросы по внутренней сети и не публикует порт bridge. I/O ограничен 8 секундами при lease 30 секунд, без redirect/транспортных повторов. Контракт v2 передаёт связанные JPEG и выполняет ограниченное локальное CV; v1 остаётся текстовым. Без проверенных весов оборудование неизвестно; внешние LLM/vision не включаются, выбор Q01 сохраняется. Точный внутренний протокол, лимиты и границы — в [ai-attempt-bridge](ai-attempt-bridge.md).

## Реализовано: показатели и экспорт

`GET /dashboard` → `{issued, completed, overdue, downtime_count, active, total, avg_rating, shift_label}`. Смена: 08:00–20:00 или 20:00–08:00 в `Asia/Almaty`. `issued` считает созданные с начала смены, `completed` — с `completed_at` с начала смены. `active` исключает только `closed|cancelled`; `total` и средняя оценка относятся ко всем доступным нарядам, а не только смене. `downtime_count` — число разных единиц оборудования с активными внеплановыми нарядами в `in_progress|paused|rework`.

`GET /analytics` и `GET /reports/export` принимают `days` (по умолчанию 90, 1–731), `from_date, to_date, area_id, equipment_id, assignee_id, brigade_id`. Начало по умолчанию `now-days`, конец `now`; обратный период или период более 731 целого дня отвергается. Для `worker` выборка ограничена его назначенными нарядами; мобильный клиент использует её для личных показателей. Веб-аналитика и экспорт работнику не показываются. **Вся выборка сейчас ограничивается `Order.created_at`, включая показатели закрытия и материалов. Это известная ошибка для переходящих работ, а не целевое правило.**

```text
Analytics = {
 summary:{total, closed, on_time_percent, avg_score, downtime_hours},
 trend:[{date, planned, unplanned}],
 by_area:[{name, count, downtime_hours}],
 rankings:[{id, name, specialty, brigade, score, quality, on_time, closed_count, rework_rate}],
 equipment:[{id, name, area_name, orders, downtime_hours}],
 materials:[{name, unit, quantity}],
 insights:[{title, description, severity}], insight_method:"deterministic_rules", summary_text:string
}
```

Текущий рейтинг закрытых нарядов: `quality / 5 × 60 + on_time_percent × 0.3 + (100 - rework_rate_percent) × 0.1`; это демонстрационная формула, не окончательная модель личного/бригадного вклада. Материалы берутся из накопленного `completion`. Простой внеплановых работ считается от создания до сдачи/отмены либо текущего времени, затем суммируется по нарядам без объединения пересечений и без обрезки по периоду — известное завышение. Поэтому длительность помечается как рассчитанная и не является фактическим простоем. Инсайты показывают только наибольшую рассчитанную длительность и группы оборудования с двумя и более внеплановыми нарядами; они не устанавливают причины поломок и не сравнивают расход материалов с нормативом. `insight_method` явно указывает детерминированные правила, `summary_text` не является AI-текстом. Поля `is_stub` и `ai_summary` удалены из аналитического ответа.

Экспорт: `format=csv|xlsx` (по умолчанию CSV); CSV с UTF-8 BOM и `;`, XLSX с листами нарядов и сводки. Строки защищаются от интерпретации как формулы. Действуют те же фильтры и ограничения доступа, что у аналитики. Веб использует запрос последней успешно загруженной выборки; экспорт блокируется при замене фильтра/обновлении. Переход к исходным нарядам переносит её период и фильтры, включая закрытые статусы; полнота списка всё ещё ограничена клиентским лимитом.

## Реализовано: уведомления и обновление клиентов

- `GET /notifications` → последние 200 собственных уведомлений: `{id, title, message, kind, order_id:int|null, created_at, read}`; сортировка по времени и id убывающе.
- `POST /notifications/{id}/read` → `{ok:true}`; чужое/неизвестное уведомление даёт `404`.
- `read` означает отметку уведомления текущего получателя, а не принятие назначения или receipt ACK. Чтение, tap, доставка push и локальная очередь не меняют статус наряда и таймер непринятия. Рабочий ответ использует существующие `accept|queue|reject` с актуальными правами ответственного D04, состоянием D19 и исходным основанием/ключом команды.
- Монитор запускается внутри API с интервалом ожидания 5 секунд; фактический интервал зависит от длительности обработки. Сохраняет дедуплицированные `due_soon`, `overdue`, `unaccepted` для исполнителя и мастера. По умолчанию предупреждение за 30 минут, принятие за 10 минут или 3 минуты для аварийного приоритета. `unaccepted` считается от `assigned_at` выданного наряда и использует ключ наряд/исполнитель/момент назначения; явное повторное назначение не наследует прежнюю дедупликацию. `due_soon`/`overdue` по-прежнему связаны со сроком наряда.
- Native push: уведомление в БД дополняется outbox-задачей `push_tasks` в той же транзакции, а отправку на устройство выполняет фоновый диспетчер процесса API через FCM (раздел «Реализовано: push и регистрация устройств · 8 октября 2026»). Без конфигурации FCM отправки нет.
- `GET /integrations` доступен `master|manager|admin` и возвращает `{ai:{mode,status,description}, native:{mode,status,description}, realtime:{mode,status,description}}`. При `AI_REVIEW_MODE=queued_service` AI имеет `ai_service/configured`; явные `queued_stub`/`inline_stub` обозначаются как `fallback` (тестовый режим), а не как подключённый модуль. `native` имеет `fcm/configured`, когда заданы учётные данные FCM и `PUSH_ENABLED=true`; успешная доставка отдельно зависит от зарегистрированного устройства и ответа FCM. Иначе — `disabled/not_configured`. Realtime — `websocket/active`.
- WebSocket `/api/ws?token=…`, также `/ws?token=…`: `{type:"connected"}` или `{type:"orders.updated"|"notifications.updated", order_id?}`. Нет подробного содержимого наряда; события рассылаются всем подключённым клиентам, HTTP повторно проверяет доступ. Недействительная сессия закрывает WS кодом `1008`; повторная проверка как минимум каждые 30 секунд.
- Веб опрашивает справочники, наряды (`limit=5000`), dashboard и уведомления каждые 5 секунд, даже при работающем WS; список работников запрашивается только для `master|manager|admin`. Одновременные вызовы обновления одной сессии объединяются с выполняющимся запросом. WS дополнительно обновляет данные и после разрыва переподключается через 1/2/4/8/15 секунд, далее каждые 15 секунд; успешное соединение сбрасывает задержку. Heartbeat — каждые 30 секунд. Ответы прошлой сессии после выхода/смены токена не применяются.
- Открытая веб-аналитика реагирует на версию общего обновления; устаревший HTTP-запрос отменяется через `AbortController`, ответ старого фильтра игнорируется. Для текущих смены/дня и последних 7/30/90 дней границы пересчитываются при обновлении, правая граница — текущий момент. Пользовательский период сохраняет заданные границы. Это клиентская актуализация; серверный отбор по `created_at` остаётся прежним.
- События WS недолговечны, воспроизведения пропущенных событий нет. `ApiError.statusCode/requestMayHaveSucceeded` — внутренний клиентский тип для отказов и неизвестного результата записи, а не новые поля серверного ответа. React-панель автоматически не повторяет POST/PATCH и пока не передаёт серверные ключи, добавленные мобильным офлайн-пакетом.

## Реализовано: push и регистрация устройств · 8 октября 2026

Провайдер — Firebase Cloud Messaging, HTTP v1 API, только Android (решение D20: [decisions.md](decisions.md)). Firebase-проект `km-case-hack` (номер `716637680468`), Android-пакет `kz.km.naryad_ai`. Отправка не выполняется внутри HTTP-запроса: `notify()` рядом с уведомлением БД в одной транзакции создаёт запись в outbox `push_tasks`, а фоновый диспетчер в процессе API отправляет ожидающие задания через FCM с повторами и нарастающей задержкой и отзывает недействительные токены в `device_tokens`. Повтор до `PUSH_MAX_ATTEMPTS` (по умолчанию 8), задержка растёт экспоненциально и ограничена часом; затем задача помечается `failed`. Если активных устройств у исполнителя нет, задача тоже помечается `failed` (`no_active_device`), а уведомление в БД остаётся. Диспетчер, как и монитор сроков, работает в одном процессе API и запускается только когда отправка настроена; согласование нескольких процессов не реализовано.

Конфигурация сервера: учётные данные FCM — `FIREBASE_CREDENTIALS_JSON` (inline JSON, приоритет) либо `FIREBASE_CREDENTIALS` (путь к файлу ключа), `FIREBASE_PROJECT_ID` (по умолчанию `km-case-hack`), `PUSH_ENABLED` (по умолчанию `false`, для отправки явно `true`), `PUSH_DISPATCH_SECONDS` (по умолчанию `3`), `PUSH_MAX_ATTEMPTS` (по умолчанию `8`). Отправка требует явного включения и учётных данных. Пути в таблице приведены с общим базовым префиксом `/api`.

| Метод и путь | Запрос и ответ |
|---|---|
| `POST /api/devices` | Bearer. `{token, platform:"android", app_version?}` → HTTP `201` и `{id, token, platform, app_version, created_at, last_seen_at}`. `token` — 8–4096 символов, `platform` только `android`, `app_version` до 40 символов или `null`. Обновление по `token`: повторная регистрация того же токена другим сотрудником перепривязывает его к текущему пользователю и возвращает в работу. Некорректное тело — `422`. |
| `POST /api/devices/unregister` | Bearer. `{token}` → `{ok:true}`. Идемпотентно; затрагивает только токен текущего пользователя, отозванный токен исключается из рассылки. Некорректное тело — `422`. |

Состав полей записи устройства соответствует таблице `device_tokens`; клиент не должен опираться на не описанные здесь поля до их закрепления в OpenAPI. `platform` на сейчас поддерживается `android`; iOS/APNs не подключены.

Push-полезная нагрузка (отдельного HTTP-маршрута нет):

- Каналы Android: `naryad_default` — обычные уведомления, `naryad_emergency` — аварийные. Аварийный канал применяется, когда приоритет наряда `emergency` либо `kind` уведомления `unassigned`; для него `android.priority = "high"`, иначе `"normal"`. Звук — `default`.
- Ключи data-сообщения: `order_id`, `notification_id`, `kind`, `emergency` (`"true"`/`"false"`; используется клиентом для выбора аварийного канала в foreground), `route="order"`.
- Нажатие на уведомление открывает наряд (deep link по `route`/`order_id`); если пользователь не вошёл в приложение, переход применяется после входа.
- Регистрацию/отзыв токена выполняет клиент после входа/восстановления сессии, при выходе и при истечении/отзыве сессии (401); фоновый и закрытый показ, разрешение на уведомления и деградация без конфигурации Firebase описаны в [mobile-ux.md](mobile-ux.md).

### Flutter R18: реализованный ограниченный переход

Ограниченный клиентский пакет по [UX-контракту](mobile-ux.md) не меняет HTTP: push/уведомление ведут к существующему `GET /orders/{id}` и явным рабочим действиям. Текущий запрос повторно проверяет доступ; ID уведомления не даёт прав. `401/403/404`, переназначение, закрытие и отмена не заменяются прежними данными как будто права подтверждены. Доступные офлайн-данные маркируются отдельно. Ошибка `POST /notifications/{id}/read` не запрещает авторизованный просмотр; её результат и отложенный маршрут связываются с исходным API/владельцем/ролью/session/token epoch, а не применяются к новому аккаунту. Те же проверки добавлены к поздним результатам карточки, общего refresh, write lease, отдельному повтору ИИ-проверки и отправке сохранённых команд; это клиентская защита контекста, не новый серверный статус или основание записи. Поздний исход очереди сохраняет оригинальную команду без изменения key/payload/основания или увеличения attempts из-за смены области; поздний `401` не отзывает новую область.

Текущая ошибка карточки `403/404` запоминается по ID и захваченной области в памяти контроллера. Пока область та же, offline snapshot и повторное открытие маршрута не дают вновь использовать скрытую карточку/действия; только текущий успешный HTTP `GET /orders/{id}` снимает этот маркер. Отказ не удаляет данные, черновики или outbox и не является постоянным локальным журналом авторизации после process restart. В той же карточке установленный общий offline-флаг может консервативно задерживать отображение положительного повторного чтения до успешного общего refresh (период 5 секунд, без обещания SLA).

`PushService.orderTaps` передаёт только положительный order ID и не сохраняет `notification_id`, получателя или исходный API. Cold-start переход после входа может проверить лишь доступ выбранной текущей сессии; он не подтверждает, кому изначально доставлен push. Клиент не переключает сервер/аккаунт автоматически. Повторные taps не создают одинаковые ожидающие переходы/копии push-карточки, сохранённые формы и активные записи остаются защищены. Состояния серверного read, локально ожидающего read, локально сохранённой команды ответа и подтверждённого сервером рабочего перехода разделяются. Красная иконка события определяется известным текущим аварийным приоритетом из оперативного снимка; без него историческая аварийность не выдумывается. Испытания и ограничения фиксируются отдельно в verification; новых receipt-маршрутов, полей/миграций или правил таймера этот контракт не вводит. Физическая доставка и звук здесь не подтверждаются.

## Планируемый контракт: реализовывать по этапам

Следующие пункты описывают оставшуюся работу по согласованному направлению, **не готовые маршруты и поля**. Уже выполненная часть ключей/очереди помечена отдельно; она не закрывает весь пункт. До подключения нового контракта нужно зафиксировать схемы в OpenAPI и тестах, согласовать их с [решениями](decisions.md) и [планом](implementation-plan.md).

1. Полные типизированные ответы/ошибки и проверка совместимости OpenAPI. Ключи, версии нарядов и подтверждённые зависимости команд уже реализованы; остальные ответы/ошибки и массовая синхронизация остаются.
2. Учёт индивидуального вклада участников бригады после решения Q05. Состав назначения, общий доступ, фото участников и сдача ответственным реализованы по D04; миграция 0007 сохраняет только известного исполнителя для прежних назначений. Очередь D19 остаётся очередью ответственного; назначение не начисляет общий результат остальным участникам.
3. Реальная оценка выбранного AI-адаптера после Q01. Асинхронная очередь и защита результата конкретной попытки уже реализованы для локальной формальной заглушки; отчёт/расход/фото не перезаписываются. Интервалы фактической работы, пауз и остановки оборудования ведутся отдельно; правила свежести фото остаются Q04.
4. Постоянные черновики остальных диалогов и оставшаяся приёмка офлайна. *Частично сделано:* черновики выдачи/сдачи Android/React, ключи, версии самого наряда, подтверждённые зависимости и постоянная очередь команд/фото, включая локальный наряд после создания; новые попытки имеют стабильный ID и связи с фото. Файлы очереди сохраняются до подтверждения; повтор фото с тем же ключом не создаёт второй снимок. Правила свежести медиа остаются Q04. Настоящее восстановление/миграция хранилища и сеть проверяются отдельно; хеш не заменяет права или анализ сходства.
5. При синхронизации сервер заново проверяет сессию, текущую роль, назначение, статус и версию. Истёкшая сессия приостанавливает отправку до входа; переназначение/закрытие не обходятся правами, сохранёнными офлайн. Типизированный конфликт должен сообщать причину и доступное текущее состояние без раскрытия чужого наряда; пользователь сохраняет локальный отчёт и разрешает конфликт явно.
6. Задания сводок, воспроизведение событий, серверная пагинация/полный поиск и координация нескольких процессов приложения. *Частично сделано:* `ai_review_jobs` сохраняет задачу попытки и защищает захват/результат, `push_tasks` повторяет Android push и отзывает токены (D20). Это не решает общий канал WebSocket, многопроцессный push/монитор, подтверждение исполнителем и доставку результатов реального провайдера. Уведомление в БД, доставка push и подтверждение — разные события.
7. Отчёты получают явные правила периода для выдачи, сдачи, приёмки, списаний и простоя. Пересекающиеся остановки одного оборудования объединяются и обрезаются границами отчёта. Источник каждого показателя остаётся проверяемым.

Flutter: сначала Android, затем iOS; роли мастера/исполнителя, камера/галерея, сжатие фото, защищённая сессия, локальные данные, настоящий push и офлайн-синхронизация. `native-stub` — прежняя заготовка, не готовый мобильный продукт. ## Открытые решения

- Внешний ИИ API или локальная модель: выбор и допустимость передачи текстов/фото ещё не подтверждены. Нужен заменяемый адаптер; интеграция внешнего провайдера не считается утверждённой.
- Сохранять ли отчёт без обязательного фото как неполную попытку: рекомендация есть, решения нет. До принятия решения действует текущий `422` для внеплановой сдачи без `after`.
- Вердикт ИИ «требует доработки»: автоматический возврат или подтверждение мастером не утверждены. Текущая реализация ждёт решения мастера; это нельзя незаметно менять при подключении настоящего ИИ.

Открытые вопросы ведутся в [decisions.md](decisions.md); разработчик не закрывает их предположением в коде или клиенте.
