# НарядAI · Flutter

Flutter-клиент для Android: мастер выдаёт наряд, исполнитель принимает и выполняет, отправляет фото/материалы, мастер принимает или возвращает работу. Пакет D17 добавил частичный офлайн: ранее загруженные данные и фото, постоянную очередь отправки и ключи повторов. `ios/` — подготовленный проект, его сборка и проверка требуют macOS/Xcode. `web/` служит превью того же Flutter UI с хранилищем в памяти; существующая React-панель сохраняется отдельно.

## Справочники администратора · текущий пакет 8 октября

У `admin` в рабочем экране доступна кнопка «Справочники»: поиск/просмотр оборудования и материалов, создание и изменение через существующий API. Оборудование содержит название, уникальный инвентарный номер, существующий участок, тип и свободную строку критичности (по умолчанию `medium`); материал — название и свободную единицу измерения. PATCH отправляет изменённые поля. DELETE, складские остатки/нормы, управление сотрудниками/ролями и редактирование участков не добавлены. Сервер по-прежнему проверяет права и значения; версий/CAS для справочников нет.

Запись доступна только онлайн и не попадает в очередь нарядов. При известной ошибке полей/записи поля остаются редактируемыми; отказ прав/сессии закрывает защищённый контекст, как описано ниже. Потеря ответа, 5xx или некорректный ACK дают неизвестный исход: ввод удерживается только в памяти текущей сессии, повтор заблокирован и после обновления списка/возврата к операции. Постоянного черновика каталога нет; закрытие несохранённой формы требует подтверждения. После проверенного ACK показывается сохранённая запись; неудачный GET предлагает обновить список, а не повторить создание. Ошибка best-effort снимка не отменяет серверное сохранение и не подтверждает дисковую сохранность.

Отправка/синхронизация/восстановление очереди исключают параллельную запись каталога. Смена аккаунта/API/token epoch/роли закрывает защищённые представления; полученный `403` блокирует каталог до нового входа, `401` завершает текущую сессию. Обновлённые справочники не заменяют основание и данные прежних черновиков/команд нарядов. Код текущего пакета и испытания на устройстве — разные уровни готовности; конкретные результаты публикуются в [verification](../docs/verification.md).

## Запуск

Проверенная версия SDK: Flutter 3.47.0 / Dart 3.13.0. Android SDK/JDK должны проходить соответствующие проверки `flutter doctor`. Все зависимости фиксирует `pubspec.lock`.

Сначала запустите API по корневому README, затем:

```sh
cd mobile
flutter pub get
flutter run -d <android-device-id> --dart-define=API_BASE_URL=http://10.0.2.2:8000
```

`10.0.2.2` — адрес компьютера из Android Emulator. На физическом телефоне укажите доступный ему адрес сервера в одной сети; при необходимости запустите API с `--host 0.0.0.0`. Адрес также настраивается на экране входа в разделе «Подключение к серверу». Для поставки используется HTTPS. HTTP разрешён только Android debug-манифестом для локального тестирования; production не должен использовать демо-ПИНы.

Демо: `master` / `1234`, `worker2` / `1234`. Вход выполняется настоящим API, переключателя ролей с локальной имитацией нет. `worker` в исходном наборе уже выполняет наряд, поэтому для нового сквозного сценария удобнее `worker2`.

```sh
flutter build apk --debug
# Результат: build/app/outputs/flutter-apk/app-debug.apk
```

Это отладочный APK. Для production нужны HTTPS, согласованные настройки окружения, собственная release-подпись и проверка на устройствах. Gradle ограничен одним worker и 1 ГБ heap для машин с небольшим объёмом RAM; при необходимости эти лимиты можно увеличить.

Веб-превью:

```sh
flutter run -d chrome --web-port=5173 --dart-define=API_BASE_URL=http://localhost:8000
# либо статическая сборка:
flutter build web --dart-define=API_BASE_URL=http://localhost:8000
python -m http.server 5173 --directory build/web
```

Порт 5173 входит в текущий CORS API. Токен в веб-превью живёт только в памяти вкладки; в Android/iOS используется защищённое хранилище, ПИН не сохраняется. Токены и фото не записываются в журналы клиента.

## Push (FCM, Android)

`mobile/android/app/google-services.json` отслеживается Git: Firebase-проект `km-case-hack` (номер `716637680468`), пакет `kz.km.naryad_ai`. Это публичная клиентская конфигурация — только идентификаторы проекта и приложения плюс Android API-ключ, серверного секрета она не содержит. Файл заменяем: при смене Firebase-проекта его пересоздают для `applicationId kz.km.naryad_ai`, а серверный ключ сервисного аккаунта и `FIREBASE_PROJECT_ID` обновляют соответственно. Клиент использует `firebase_core`, `firebase_messaging` и `flutter_local_notifications`; `PushService` внедряется в приложение и работает как заглушка на веб-превью и в тестах.

- После входа и восстановления сессии клиент запрашивает системное разрешение на уведомления и регистрирует FCM-токен на сервере (`POST /api/devices`); при выходе отзывает (`POST /api/devices/unregister`). Токен, уже зарегистрированный другим сотрудником, сервер перепривязывает к вошедшему.
- Уведомление, полученное в фоне или при закрытом приложении, показывает системный трей FCM (сообщение содержит notification-полезную нагрузку) со звуком канала: `naryad_default` — обычные, `naryad_emergency` — аварийные; `flutter_local_notifications` показывает уведомления в открытом приложении и data-only сообщения. Нажатие открывает наряд; если пользователь не вошёл, переход применяется после входа. Подробности и границы — в [mobile-ux](../docs/mobile-ux.md).
- Без настроенного Firebase клиент работает как прежде: push просто отключён, остальная работа не меняется.

Отправляет сервер, которому нужен ключ сервисного аккаунта: раздел «Push-уведомления (FCM, Android)» в [корневом README](../README.md) — два канала `FIREBASE_CREDENTIALS_JSON` (inline JSON, приоритет) и `FIREBASE_CREDENTIALS` (путь к файлу в `backend/secrets/`), явное `PUSH_ENABLED=true` и исходящий HTTPS к `oauth2.googleapis.com` и `fcm.googleapis.com`. Доставка на физическом устройстве, iOS/APNs и подтверждение аварийного уведомления не проверялись.

`psycopg[binary]` в `backend/requirements.txt` — `3.3.6` для Python 3.14 (PostgreSQL нужен только полному запуску, не тестам и не FCM-смоуку).

## Проверки

```sh
flutter analyze
flutter test
# Только на отдельной демобазе: создаёт синтетический наряд и фото.
flutter test test/live_api_test.dart --dart-define=LIVE_API_URL=http://127.0.0.1:8000
```

Последняя команда работает из Flutter test на компьютере, поэтому использует `127.0.0.1`, а не адрес эмулятора. Обычный прогон пропускает live-тест. Фактические результаты и границы — в [verification](../docs/verification.md).

Целевые проверки разбора офлайн-конфликтов без телефона/API:

```sh
flutter test --concurrency=2 test/offline_recovery_test.dart test/offline_recovery_ui_test.dart test/brigade_recovery_test.dart test/local_store_recovery_sqlite_test.dart
```

Последний файл использует настоящую временную SQLite через dev-зависимость `sqflite_common_ffi` и внедряемый `DatabaseFactory`: проверяет rollback после сбоя удаления, сравнение снимка, границу сессии и сохранность чужих файлов. Рабочая БД не открывается; production продолжает использовать Android `sqflite`. Основа процедуры — [официальная инструкция SQLite-тестов](https://github.com/tekartik/sqflite/blob/master/sqflite_common_ffi/doc/testing.md). Это проверка транзакций и UI на компьютере; остановка Android посреди HTTP, физические устройства и доставка FCM требуют отдельных испытаний.

### Приёмка потери HTTP-ответа после серверного commit

Этот desktop opt-in тест использует настоящий HTTP, локальный fault proxy и SQLite-FFI. API отвечает upstream после commit, proxy обрывает downstream до заголовков; сохранённая команда переживает GET и close/open, затем точный replay подтверждается независимо по серверной БД. Это не Android process-death, защищённое восстановление сессии или физическая сеть. Фото «После» загружено и подтверждено до сдачи.

Из корня репозитория с установленными backend-зависимостями подготовьте **новый marker** и свободный loopback-порт. Фикстура располагается в отдельной соседней папке вне Git; CLI отказывается менять существующую БД. PowerShell, терминал 1:

```powershell
$httpRunMarker = 'run-20261008-unique01'
$httpFixtureParent = Split-Path -Parent (Get-Location).Path
$httpFixtureFolder = Join-Path $httpFixtureParent "http-uncertainty-$httpRunMarker"
$httpFixtureDb = 'sqlite:///' + (Join-Path $httpFixtureFolder 'fixture.sqlite').Replace('\', '/')
python backend/tests/live_http_uncertainty_fixture.py prepare --database-url $httpFixtureDb --run-marker $httpRunMarker --api-url http://127.0.0.1:8021/api
python backend/tests/live_http_uncertainty_fixture.py serve --database-url $httpFixtureDb --run-marker $httpRunMarker
```

Serve читает адрес из manifest, отключает демозасев, push и monitor; используется queued_stub без внешнего ИИ. После появления сообщения о запуске сервера откройте терминал 2 из корня репозитория и укажите **абсолютный путь fixture.json**, напечатанный prepare:

```powershell
cd mobile
flutter test --no-pub test/live_http_uncertainty_test.dart '--dart-define=LIVE_HTTP_FIXTURE_FILE=C:/absolute/http-uncertainty-run-20261008-unique01/fixture.json'
```

После успешного теста остановите serve через Ctrl+C в терминале 1 и выполните:

```powershell
python backend/tests/live_http_uncertainty_fixture.py verify --database-url $httpFixtureDb --run-marker $httpRunMarker
```

Verify требует финальный подтверждённый replay, два complete POST и пустую локальную очередь, сравнивает request/response хеши и открывает SQLite только для чтения. Результат — ровно одна попытка, MaterialWriteoff quantity=2, complete event, AI job и receipt с исходными связями; складской остаток текущая схема не моделирует. Прерванный/неудачный прогон оставляет свидетельства для разбора, новый запуск требует новую фикстуру. Без LIVE_HTTP_FIXTURE_FILE обычный flutter test намеренно пропускает этот сценарий; он не вызывает рабочий API. Сведения о настоящем прогоне — в verification.

### Связанный тест Android Emulator и веб-клиента API

Физический телефон не нужен. Заранее запустите Android Emulator `emulator-5556`, API на `8000` и Vite на `5174` с прокси к этому API. Используйте отдельную демобазу с исходными справочниками: у `worker2` не должно быть текущей работы (`in_progress` или `paused`). Тест создаёт синтетические данные и не исправляет чужие назначения.

Оба терминала открываются из корня репозитория. Выберите **новый уникальный `BRIDGE_TITLE` для каждого запуска** и подставьте одинаковое значение в оба блока. Пример PowerShell, терминал 1:

```powershell
cd mobile
$bridgeTitle = 'bridge-20261006-153000'
flutter test integration_test/web_bridge_test.dart -d emulator-5556 --dart-define=API_BASE_URL=http://10.0.2.2:8000 "--dart-define=BRIDGE_TITLE=$bridgeTitle"
$LASTEXITCODE
```

Дождитесь строки `BRIDGE_STEP WAIT_WEB_CREATE` в первом терминале, затем запустите терминал 2. Не запускайте координатор во время сборки Android: ожидания ограничены.

```powershell
cd frontend
$env:LIVE_DEMO = '1'
$env:LIVE_WEB_URL = 'http://127.0.0.1:5174'
$env:BRIDGE_TITLE = 'bridge-20261006-153000'
node --experimental-strip-types tests/live_bridge.mjs
$LASTEXITCODE
```

Дальше сценарий идёт автоматически: мастер через настоящий веб-клиент API выдаёт наряд, Flutter UI принимает, начинает, приостанавливает и продолжает работу, отправляет отчёт; мастер возвращает на доработку и принимает повторный результат. Проверяются итоговая оценка 5, расход материалов 2 + 1 = 3, приватные JPEG и запреты чужого доступа. Оставьте `BRIDGE_PAUSE` включённым: координатор ожидает события паузы и продолжения. Наряд ожидается до 90 секунд, каждая внешняя приёмка — до 120 секунд; последнее можно изменить через `--dart-define=BRIDGE_WAIT_SECONDS=240`.

Успех требует **кода завершения 0 у обеих команд и `BRIDGE_STEP PASS` у Flutter**. Успех только веб-координатора не подтверждает мобильный UI. Без `BRIDGE_TITLE` тест пропускается. Эта инструкция не является результатом прогона.

Фотографии создаются синтетически и загружаются настоящим `AppController`/API; камера и системная галерея не проверяются. Координатор импортирует `frontend/src/model.ts`, но не управляет React-интерфейсом браузера. Эмулятор также не подтверждает работу на физическом телефоне, фоновой push или офлайн.

#### Вариант при недостатке RAM: сборка и запуск отдельно

При 6 ГБ RAM совместная работа Gradle и Android Emulator может вызвать интенсивный обмен с диском. Остановите тестовый эмулятор на время сборки. Из `mobile/` соберите APK с новым уникальным заголовком:

```powershell
$bridgeTitle = 'bridge-20261006-154000'
flutter build apk --debug --target=integration_test/web_bridge_test.dart --target-platform=android-x64 --dart-define=API_BASE_URL=http://10.0.2.2:8000 "--dart-define=BRIDGE_TITLE=$bridgeTitle"
```

Не добавляйте `INTEGRATION_TEST_SHOULD_REPORT_RESULTS_TO_NATIVE`: этот вариант передаёт результаты SDK-драйверу. После успешной сборки снова запустите `emulator-5556` и дождитесь загрузки Android, затем из того же каталога:

```powershell
flutter drive --no-pub --no-dds --driver=test_driver/web_bridge_test.dart --target=integration_test/web_bridge_test.dart --use-application-binary=build/app/outputs/flutter-apk/app-debug.apk -d emulator-5556
$LASTEXITCODE
```

SDK-драйвер ждёт результат до 12 минут; он не управляет браузером. Если увеличиваете `BRIDGE_WAIT_SECONDS`, при необходимости согласованно увеличьте timeout в `test_driver/web_bridge_test.dart`: определение не меняет лимит драйвера. `API_BASE_URL` и `BRIDGE_TITLE` уже встроены в APK: для другого заголовка пересоберите его. Во втором терминале запускайте тот же Node-координатор после `BRIDGE_STEP WAIT_WEB_CREATE`, установив `BRIDGE_TITLE` из сборки. Критерии успеха и границы проверки остаются прежними.

Для раннего обнаружения сбоя Android координатору можно передать `BRIDGE_NATIVE_LOG` — абсолютный путь к **UTF-8 логу текущего Android-прогона**. Перед каждым запуском очищайте файл или выбирайте новый путь: старый `PASS`/`TEARDOWN` исказит результат. Например, в первом терминале PowerShell 7 задайте `$bridgeNativeLog = Join-Path $env:TEMP "$bridgeTitle-android.log"` и добавьте к команде `flutter drive` перенаправление `2>&1 | Tee-Object -FilePath $bridgeNativeLog`. Для других версий PowerShell обеспечьте запись именно UTF-8.

Во втором терминале перед `node` можно задать оба необязательных пути:

```powershell
$env:BRIDGE_NATIVE_LOG = Join-Path $env:TEMP ($env:BRIDGE_TITLE + '-android.log')
$env:BRIDGE_REPORT = Join-Path $env:TEMP ($env:BRIDGE_TITLE + '-web.json')
```

При `TEARDOWN` без `PASS` координатор прекращает ожидание, не дожидаясь шестиминутного таймаута, и отменяет **только свой созданный наряд**, если тот ещё не `closed`/`cancelled`. Без `BRIDGE_NATIVE_LOG` действует ограниченное ожидание с такой же очисткой незавершённого тестового наряда. `BRIDGE_REPORT` сохраняет JSON результата веб-координатора; этот файл сам по себе не подтверждает Android `PASS` и не заменяет проверку обоих кодов завершения.

### Приёмка дисковой очереди: два запуска Android-процесса

`integration_test/offline_persistence_test.dart` использует настоящие HTTP, Android secure storage, `sqflite` и файлы медиа. Прогон требует **отдельной свежей SQLite-демобазы**, свободного `worker2` и собственного тестового API на `8017`. Обычный API и чужие базы не останавливаются. Нужен один тестовый эмулятор `emulator-5556`; не запускайте этот сценарий на пользовательском телефоне. Инструкция описывает процедуру, результаты конкретного прогона — в [verification](../docs/verification.md).

В терминале API с активированным Python-окружением проекта, из `backend/`:

```powershell
$offlineRun = 'offline-20261007-02'
$offlineDb = Join-Path $env:TEMP ($offlineRun + '.sqlite')
$env:DATABASE_URL = 'sqlite:///' + $offlineDb.Replace('\', '/')
$env:SEED_DEMO = 'true'
python -m uvicorn app.main:app --host 127.0.0.1 --port 8017
```

Метка новая для каждой пары запусков, 1–48 символов `[A-Za-z0-9_-]`; файл базы с этим именем не должен уже существовать. Путь и окружение терминала нужно сохранить: при восстановлении запускается **та же команда API с той же базой**. В другом терминале, из `mobile/`, соберите один APK с той же меткой (при недостатке RAM — до запуска эмулятора):

```powershell
$offlineRun = 'offline-20261007-02'
flutter build apk --debug --target=integration_test/offline_persistence_test.dart --target-platform=android-x64 --dart-define=API_BASE_URL=http://10.0.2.2:8017 "--dart-define=OFFLINE_RUN=$offlineRun"
flutter drive --no-pub --no-dds --keep-app-running --driver=test_driver/offline_persistence_test.dart --target=integration_test/offline_persistence_test.dart --use-application-binary=build/app/outputs/flutter-apk/app-debug.apk -d emulator-5556
$LASTEXITCODE
```

В **обеих** командах `flutter drive` обязателен `--keep-app-running`: в Flutter 3.47 драйвер по умолчанию после завершения останавливает и удаляет установленное им приложение вместе с данными. Флаг оставляет приложение установленным и работающим после SDK-результата. Поэтому `PHASE_A_PASS`/код 0 без этого флага не подтверждает сохранность между процессами: последующая установка APK начнёт новую фазу A после потери SharedPreferences и `sqflite`. Для проверки восстановления сохраняют данные установленного приложения и отдельно выполняют `am force-stop`; повторная установка APK сама по себе не является такой проверкой.

Первый запуск проверяет обновление старой локальной схемы, входит, получает тестовый наряд и сохраняет просмотренное фото. При `OFFLINE_STEP WAIT_API_OFF` остановите **этот тестовый API** через `Ctrl+C` в его терминале. API остаётся выключенным: тест ставит принятие/начало/фото после/сдачу в дисковую очередь. Дождитесь `OFFLINE_STEP PHASE_A_PASS` и кода **0** SDK-драйвера. Не удаляйте приложение, его данные, базу или метку и не пересобирайте APK между фазами.

После завершения первой команды остановите только тестовое приложение на эмуляторе и снова запустите тот же APK:

```powershell
& "$env:LOCALAPPDATA\Android\sdk\platform-tools\adb.exe" -s emulator-5556 shell am force-stop kz.km.naryad_ai
flutter drive --no-pub --no-dds --keep-app-running --driver=test_driver/offline_persistence_test.dart --target=integration_test/offline_persistence_test.dart --use-application-binary=build/app/outputs/flutter-apk/app-debug.apk -d emulator-5556
$LASTEXITCODE
```

Второй процесс при выключенном API должен восстановить профиль, кэш и четыре команды с прежними ключами. Только после `OFFLINE_STEP RESTORED_OFFLINE` и `OFFLINE_STEP WAIT_API_ON` запустите прежнюю команду API в прежнем терминале. Тест синхронизирует очередь, повторяет сдачу тем же ключом и проверяет отсутствие повторного расхода/события, затем мастер закрывает наряд с оценкой 5. Успех требует `PHASE_A_PASS`/код 0 SDK-сбора первой фазы и `OFFLINE_STEP PASS`/код 0 второй с той же меткой и нарядом. Ожидание отключения API ограничено 2 минутами, восстановления — 3 минутами; весь host-сбор результата ограничен 12 минутами. Внутренний timeout SDK requestData только предупреждает, поэтому драйвер дополнительно использует `Future.timeout` и возвращает ошибку при превышении.

Если native-тест уже напечатал завершённый `All tests passed`, но host-драйвер завис, одного маркера недостаточно. Сохраните приложение запущенным и данные нетронутыми; остановите только зависший host-драйвер. В текущем работающем тестовом приложении можно собрать **его завершённый результат** официальным SDK без установки/перезапуска:

```powershell
$offlineVmService = '<текущий VM service URI этого тестового приложения>'
flutter drive --no-pub --no-dds --keep-app-running "--use-existing-app=$offlineVmService" --driver=test_driver/offline_persistence_test.dart --target=integration_test/offline_persistence_test.dart -d emulator-5556
$LASTEXITCODE
```

URI берётся из текущего SDK-подключения/диагностики собственного приложения; прежний URI после уничтожения процесса не подходит. При таком восстановлении нужно отдельно записать код исходной команды и код SDK-сбора: успешен только сбор завершённого результата с кодом 0. Затем выполняется тот же force-stop между фазами. Это не способ игнорировать ошибку native-теста; незавершённый/ошибочный тест остаётся неуспешным. Пример фактически выполненного сбора — в [verification.md](../docs/verification.md).

После завершения второй команды остановите только тестовое приложение тем же `adb -s emulator-5556 shell am force-stop kz.km.naryad_ai`. Флаг оставил его работающим; удаление приложения или очистка данных для завершения этого прогона не нужны.

Это недоступность настоящего TCP-сервера и новый Android-процесс. Режим полёта/Wi-Fi Android, физическая мобильная сеть, камера/галерея, фоновой push и PostgreSQL этим тестом не проверяются. Снимки синтетические; тестовый APK не является APK для пользователей.

## Устройство и границы

- `lib/data/`: HTTP API, основные типы, сессия и общие данные. `lib/screens/`: рабочие экраны. `lib/ui.dart`: тема, карточки и производственное время `Asia/Almaty`.
- Главная мастера: аварии, просрочки, приёмка, непринятые назначения, смена и занятость. Главная работника: текущий наряд, поступления, очередь и проверка.
- Выдача в два этапа, фильтр оборудования по участку, видимая занятость исполнителя, до 5 фото до работ. После подтверждённого создания повторная отправка фото не создаёт второй наряд.
- Камера/галерея через `image_picker`; JPEG до 1920 px до передачи. Реальная камера и восстановление результата после уничтожения Android-процесса ещё требуют испытания/доработки.
- Сдача: код неисправности, поиск материалов, количества, фото после, комментарий. Внеплановое завершение без фото блокируется по текущему API. При доработке материалы означают только дополнительный расход.
- Неотправленные поля и подготовленные фото выдачи/сдачи сохраняются в отдельном Android-черновике; остальные диалоги и Flutter web-превью остаются в памяти. Отправленные при потере связи действия сохраняются в Android-очереди вместе с ключом и медиа: локальное сохранение обозначает ожидание, а не подтверждение сервером. Полученные данные и просмотренные фото доступны из постоянного кэша; данные, которые раньше не загружались, офлайн недоступны. Для четырёх POST повтор использует тот же `X-Client-Command-Id`; конфликт не приводит к молчаливой перезаписи; неизвестный результат POST не повторяется автоматически, UI предлагает проверить результат. Полный набор реальных испытаний хранилища/перезапуска/сети приведён в [verification](../docs/verification.md), этап 7 ещё не закрыт.
- Опрос каждые 5 секунд при открытом приложении. Push на Android подключён через FCM (раздел выше), но его доставка на физическом устройстве не подтверждена; iOS-push и WebSocket ещё не подключены. Интервал опроса сам по себе не доказывает обновление не дольше 5 секунд.
- ИИ остаётся серверной заглушкой. Приёмка и оценка мастером отдельны. Реальные фото/описания внешнему ИИ не отправляются.
- Бригадное назначение использует текущее серверное правило: выбирается один работник. Общий доступ участников, позиции очереди и отдельные версии сдачи ещё впереди.
- Мобильные PATCH/переназначение, редактор справочников и экспорт пока доступны только через существующую веб-панель. Производственные отчёты ждут исправления серверных периодов/простоя/рейтинга.
- Поиск фильтрует до 5000 загруженных нарядов; при достижении лимита показывает предупреждение. Полная серверная пагинация запланирована.
- 6 нажатий/1 минута выдачи, 10 секунд фото, две реальные Android-модели и iOS ещё не приняты. Демо-маркировка относится к текущему этапу; реальное окружение потребует конфигурации этого признака с сервера.

## Частичный офлайн Android · 7 октября 2026

Клиент хранит снимки нарядов, справочников, работников, панели, уведомлений, аналитики и профиля в `sqflite`. Просмотренные фото лежат в файловом кэше; фото ожидающих команд хранятся отдельно до подтверждения. При старте профиль можно открыть до проверки токена: сетевой сбой оставляет офлайн-режим, ответ `401` завершает сессию. Веб-превью не подтверждает работу этих Android-плагинов.

Область локальных данных — полный нормализованный адрес API (схема, хост, порт и полный путь API) и числовой ID аккаунта. Один ID работника на разных серверах не объединяет данные. Этот же адрес и владелец сохраняются в каждой новой команде; чужая область не показывается и не отправляется.

Очередь включает создание, переходы, сдачу, загрузку фото и отметку уведомления прочитанным. Зависимые фото ждут создания наряда на сервере, сдача — допустимого состояния и необходимых фото. Экран очереди показывает ожидание, а для конфликтов — повтор/удаление. Повтор четырёх POST нарядов/фото использует исходные ключи; отметка прочтения повторно устанавливает тот же флаг. Это не разрешение повторять произвольный POST без ключа. Отправка выполняется работающим приложением, фоновой Android-службы синхронизации нет.

Команда и медиа записываются **до** изменяющего HTTP-запроса, в том числе при доступной сети. Ошибка открытия/записи Android-хранилища прекращает отправку с локальной `ApiException.statusCode = 507`; это внутренний код клиента, не ответ сервера. Незаметного перехода в память на Android нет. После устранения ошибки открытие можно повторить. Синхронизация выполняется одним проходом; отказ предыдущей команды блокирует последующие по тому же наряду. Удаление конфликтной команды удаляет и последующие зависимые действия; это не отменяет уже подтверждённый результат на сервере.

При `401` отправка останавливается, команда возвращается в ожидание с прежним ключом. Повторный вход в тот же аккаунт на тот же сервер позволяет продолжить. При выходе очищаются профиль, снимки и кэш просмотренных фото своей области; очередь с медиа, черновики выдачи/сдачи и сопоставления локальных/серверных ID сохраняются отдельно. Flutter web-превью может отправлять свою очередь в открытой вкладке, но её память теряется при перезагрузке.

Обновление локальной схемы до v2 не угадывает происхождение старых данных: кэши/сопоставления без области не читаются; команды без сервера/владельца сохраняются изолированными и не отправляются автоматически. Старая сохранённая сессия без ID владельца требует онлайн-проверки `/auth/me`, прежде чем клиент сможет использовать кэш. Поэтому первый офлайн-старт после такого обновления не является поддержанным восстановлением старого кэша.

Постоянная очередь отправленного действия и постоянный черновик ещё не отправленной формы — разные возможности. Черновики основных форм и версии записей реализованы в текущей ветке; миграции заполненных схем v1/v2/v3 → v4 и восстановление этих форм после force-stop подтверждены отдельным эмуляторным прогоном. Остальные диалоги, расширенные сетевые конфликты/активный HTTP и полный офлайн на физических устройствах остаются в плане. Новые проверки и их результат фиксируются отдельно в verification; старый онлайн-прогон не доказывает устойчивость нового офлайн-пакета.

## Локальные черновики основных форм · продолжение PR #5

Выдача и сдача восстанавливают поля, выборы, исходные количества материалов и сжатые фото после закрытия формы. Android хранит их отдельной записью `form_drafts` схемы v4, независимо от снимков и outbox. Область включает полный API, пользователя, вид формы и наряд; для выдачи используется один черновик `new`. Flutter web-превью остаётся в памяти.

Форма показывает сохранение после записи; ошибка хранилища запрещает отправку. Перед каждой выдачей/сдачей/загрузкой фото сохраняется маркер отправки. Прерванный запрос восстанавливается как неизвестный результат и не создаётся заново из формы; уже поставленные команды продолжают очередь с прежним ключом. Сохраняются созданный ID и состояния фото. Исходное основание версии не меняется по свежему GET. Удаление локального черновика не отменяет серверные операции или очередь. Остальные диалоги пока не сохраняются. Реальные испытания схемы v4, сети и устройств описываются отдельно в verification.

### Приёмка черновиков на Android после остановки процесса

`integration_test/form_draft_persistence_test.dart` проверяет настоящий `sqflite`, миграции заполненных схем v1/v2/v3 → v4 и восстановление основных форм в новом процессе. Используйте отдельную свежую демобазу API на `8017`, свободного `worker2` и тестовый эмулятор `emulator-5556`. Процедура не предназначена для пользовательского телефона. Запускайте API с `PUSH_ENABLED=false`, без access-log; сохраняйте логи вне Git.

Из `mobile/` соберите один APK до запуска эмулятора, задав новую метку для каждого полного прогона:

```powershell
$draftRun = 'draft-20261008-070000'
flutter build apk --debug --no-pub --target=integration_test/form_draft_persistence_test.dart --target-platform=android-x64 --dart-define=API_BASE_URL=http://10.0.2.2:8017 "--dart-define=DRAFT_RUN=$draftRun"
```

После загрузки эмулятора запустите первую фазу:

```powershell
flutter drive --no-pub --no-dds --keep-app-running --driver=test_driver/form_draft_persistence_test.dart --target=integration_test/form_draft_persistence_test.dart --use-application-binary=build/app/outputs/flutter-apk/app-debug.apk -d emulator-5556
$LASTEXITCODE
```

Дождитесь `DRAFT_STEP PHASE_A_PASS` и кода SDK-драйвера **0**. Выполните `adb -s emulator-5556 shell am force-stop kz.km.naryad_ai`, убедитесь, что процесс завершён, затем повторите **ту же команду drive с тем же APK и `--keep-app-running`**. Не удаляйте приложение и не очищайте его данные между фазами. Успех требует кода **0** обеих команд и `DRAFT_STEP PASS` второй фазы; один native PASS без результата SDK недостаточен. Без `DRAFT_RUN` тест пропускается.

Чтобы во второй фазе пропустить повторную установку APK, после force-stop можно запустить тот же установленный пакет и подключить SDK к новому процессу:

```powershell
adb -s emulator-5556 shell am start -a android.intent.action.MAIN -c android.intent.category.LAUNCHER -f 0x20000000 --ez enable-dart-profiling true --ez enable-checked-mode true --ez verify-entry-points true --ez start-paused true -n kz.km.naryad_ai/.MainActivity

# $freshHostVmUri: URI нового VM, замените только порт, сохранив его путь.
flutter drive --no-pub --no-dds --keep-app-running "--use-existing-app=$freshHostVmUri" --driver=test_driver/form_draft_persistence_test.dart --target=integration_test/form_draft_persistence_test.dart -d emulator-5556
```

Не используйте URI прежнего процесса; убедитесь, что PID изменился. SDK сам продолжит paused-isolate. После завершения удалите созданный вами проброс через `adb -s emulator-5556 forward --remove tcp:<порт компьютера>`. Критерии успеха те же: новый процесс, сохранённые данные и код SDK **0**.

Текст и исходное количество материала вводятся через настоящий Flutter UI; HTTP и авторизация настоящие. Подготовленные фото добавляются в черновик тестом; частичная выдача использует реальные подтверждения создания/загрузки. Маркер `submitting` записывается до HTTP: проверяется консервативный запрет новой отправки после остановки, а не разрыв соединения посреди запроса. Проверка другого адреса API относится только к локальной области хранения. Камера/галерея, физические устройства, FCM, iOS и производительность больших фото в этот сценарий не входят. Результат конкретного прогона — в [verification](../docs/verification.md).

## Замер оперативного опроса на desktop

`test/live_polling_measurement_test.dart` запускается только с `LIVE_POLLING_FIXTURE_FILE`. Используется настоящий loopback HTTP, production `NaryadApp` и неизменённые таймеры контроллера/карточки. `LiveTestWidgetsFlutterBinding.fullyLive` и монотонный `Stopwatch` дают отдельно 60 реальных секунд обзора мастера и открытой карточки; вход, прогрев и переход между экранами исключены. Обычный CI намеренно пропускает этот сценарий.

Из корня репозитория подготовьте новую фикстуру вне checkout; замените путь, уникальную метку и свободный порт:

```powershell
$pollingMarker = 'poll-20261008-unique01'
$pollingDbUrl = "sqlite:///C:/temporary/polling-baseline-$pollingMarker/fixture.sqlite"
python backend/tests/live_polling_fixture.py prepare --database-url $pollingDbUrl --run-marker $pollingMarker --api-url http://127.0.0.1:8022/api
python backend/tests/live_polling_fixture.py serve --database-url $pollingDbUrl --run-marker $pollingMarker
```

В другом терминале из `mobile/`:

```powershell
flutter test --no-pub test/live_polling_measurement_test.dart --dart-define=LIVE_POLLING_FIXTURE_FILE=C:/temporary/polling-baseline-poll-20261008-unique01/fixture.json
```

CLI отказывается изменять существующие DB/manifest/result. Сервер отключает seed, монитор, push и фоновый ИИ. Фикстура содержит ровно 500 синтетических SQL-состояний: 350 closed, 100 cancelled, 42 issued, 8 queued; один мастер, один исполнитель, без фото и попыток сдачи. Перед изменениями тест сверяет маркеры, количество, распределение и версии через API. В каждой фазе около 31-й секунды внешний мастер выполняет один version-checked PATCH. Задержка считается от получения полного 200-ответа до наблюдения нового текста и соответствующей версии в отрисованной Flutter-сцене; реальный интервал last-absent/first-present сохраняется при сэмплировании около 50 мс.

`result.json` рядом с manifest содержит нормализованные маршруты, статусы, логические байты ответов, полную длительность ответа, одновременность и вызовы `putSnapshot`. Причины ошибок — фиксированные категории, без текста исключений; headers, токены и payload туда не попадают. Запрос относится к фазе по времени начала; ответ, завершившийся после её конца, остаётся в этой фазе и помечается явно. Отдельно учитываются HTTP-попытки и здоровье приложения: один потерянный до заголовков GET может успешно повториться внутри общего лимита 8 секунд. Успех приложения требует наблюдаемого обновления, отсутствия sampled offline/error и изменений очереди; ошибочные попытки остаются в метриках. JSON сохраняется до итоговой проверки здоровья.

После добавления условного `/orders` метрики отдельно сохраняют полностью прочитанные `304` и реально полученные байты их тела. Test-only подкласс API считает успешно возвращённые массивы и их длину; это не самостоятельная трассировка каждой операции кэша. Сохранённый JSON не прибавляется к сетевым байтам. Вход и прогрев исключены и могут заранее заполнить кэш; это сравнение опроса, а не экономии первой загрузки. При каждой повторной приёмке создавайте ещё одну новую фикстуру; старые файлы не перезаписываются.

Логические body bytes не равны сетевому трафику. Локальное хранилище, secure storage/preferences и push подменены платформенными заглушками: число snapshot-вызовов не измеряет диск, fsync или батарею. Это offscreen Flutter scene/layout/paint на Windows test VM, не физический экран, Android-приёмка или нагрузочный SLA. После прогона остановите только собственный временный сервер; для повторения создавайте новую фикстуру. Фактические результаты и границы — в [verification](../docs/verification.md).

### Запись снимков в настоящую SQLite на desktop

Для этого режима дополнительно задайте `LIVE_POLLING_SQLITE_DIRECTORY`: абсолютный путь к ещё не существующему прямому дочернему каталогу свежей фикстуры с именем `snapshot-sqlite-<run-marker>`. Тест создаёт каталог, отказывается от существующего, ссылки или пути внутри Git; созданные данные и лог остаются для проверки. Сначала подготовьте и запустите новую синтетическую серверную фикстуру процедурой выше, затем из `mobile/`:

```powershell
flutter test --no-pub test/live_polling_measurement_test.dart --dart-define=LIVE_POLLING_FIXTURE_FILE=C:/temporary/polling-baseline-poll-unique02/fixture.json --dart-define=LIVE_POLLING_SQLITE_DIRECTORY=C:/temporary/polling-baseline-poll-unique02/snapshot-sqlite-poll-unique02
```

Используются production `SqfliteLocalStore` и настоящая SQLite-FFI. Публичный SDK SQL logger передаёт уже сериализованные аргументы `INSERT OR REPLACE`; безопасный callback сохраняет только агрегаты, не печатает события/аргументы и не выполняет второй JSON encode в измеряемом пути. По секциям считаются начало/успех/ошибка put и завершённые SQL, логические UTF-8 JSON bytes, точное совпадение сериализованной строки с последним успешным scoped payload и отдельно совпадение `updated_at`. Начало put задаёт фазу; поздние SQL events сохраняются в ней через Zone. На границе измеряется реальный put-inflight; точный SQL-inflight неизвестен и записан как null.

SQL Stopwatch SDK измеряет await wrapper/lock/isolate, исключая JSON encode и observer callback; put включает эти затраты и overhead observer, время callback записано отдельно. SQL-start из stopped Stopwatch приблизительный, процентили — nearest rank. Drain учитывает HTTP, вошедшие put и 100 мс реального отсутствия активности. После фаз UI/controller timers останавливаются, вошедшие записи дожидаются завершения. Без `flushSnapshot` или restore проверяются семь scoped строк, точные payload/timestamps последних успешных SQL, актуальные детали и пустые отдельные таблицы; readonly close/reopen повторяет проверку. Содержимое проверяется приватно и не попадает в JSON.

Это обычное закрытие и открытие desktop SQLite, не аварийное завершение, fsync, физические disk bytes, Android plugin, защищённая сессия или батарея. Не вошедшие в put приватные отложенные captures могут отмениться при dispose; такой drain не доказывает их сохранность. Обычный CI пропускает live сценарий; конкретный фактический прогон и выводы публикуются в verification/benchmarks. Прежний режим без дополнительного define продолжает измерять MemoryLocalStore.
